## 0. ⭐⭐ 这一条压着整份设计：不降级，不丢字

**Ocean 2026-08-17 原话**：

> 「不能降级，用户打包一个文件说明他自己知道这是超长上下文，spool 不能损失信息，
> 可以使用提供文件目录的形式让 ai 更好读文字内容，可以选择性读取所需部分，类似代码阅读，
> 或者有其他节省上下文技巧也可以，**但是文字内容不应该损失**。」

⚠️ 我当时提的两个方案**都被否掉了**，而且否得对：

| 我提的 | 为什么错 |
|---|---|
| 自动降级（照抄 MCP 那侧的 `budgeted_pack`） | 那是**替用户做取舍**。用户主动打包一整个文件夹，说明他已经知道这会很长 —— 这时候悄悄砍掉一半，砍掉的正是他要的那部分 |
| 只报字符数，让用户自己减 | 把问题原样还给用户，等于没解决 |

**正确的方向是换形状,不是换分量**：省上下文靠「**目录 + 按需打开**」，靠 AI 只读它需要的那几份，
**不靠 Spool 事先删**。

⭐ 这条通则值得记在打包之外：**「太长了」不一定要靠删来解决,可以靠让对方能挑着读来解决。**

## 1. 拍板结果

| # | 问题 | 他定的 |
|---|---|---|
| 1 | 打包整个文件夹 / 挑项目打包，走哪种交互？ | **乙：从文件夹自己触发** |

### 1.1 入口：左栏文件夹行（方案乙）

左栏工作区行**悬停时已经有 ＋（新建项目）和 🗑（删除工作区）**（`Sidebar/WorkspaceGroup.tsx`），
所以加一个打包图标是**沿用现成的悬停模式，不需要发明新菜单**。

点它打开的对话框，顶上是一张**勾选清单，默认全勾**：

```
┌ 打包「升学」 ────────────────────────────┐
│ 4 个项目，含 1 个子工作区                 │
├──────────────────────────────────────────┤
│ ☑ 申请规划              18 块 · 12,400 字 │
│ ☑ Georgia Tech MS…       9 块 ·  6,100 字 │
│ ☑ 材料准备（子工作区）                    │
│    ☑ 文书              22 块 · 18,900 字 │
│    ☐ 推荐信             5 块 ·  2,300 字 │
├──────────────────────────────────────────┤
│ 打包范围?  [全部] 置顶  近7天  近30天      │
├──────────────────────────────────────────┤
│ 3 个项目 / 49 块 · 37,400 字符   [导出]   │
└──────────────────────────────────────────┘
```

⭐ **「整个文件夹」和「挑几个」是同一个动作**：不动就是整包，取消勾选就是挑。
这正是他一句话里同时要的两件事，不用做成两个功能。

### 1.2 交付：一个真的文件夹

```
spool-升学-20260817/
  INDEX.md
  01-申请规划.md          18 块
  02-Georgia-Tech-MS.md    9 块
  材料准备/
    01-文书.md            22 块
    02-推荐信.md           5 块
```

- **子工作区就是子目录** —— 嵌套结构天然映射，不需要另发明一套表达；
- **每个 `.md` 的正文 = 现在单项目打包的正文**，一个字不改，所以 `assemble()` 直接复用；
- 用户把这个文件夹交给 Claude Code / Codex，**AI 用它自己的文件工具按需打开** ——
  这就是他说的「类似代码阅读」。上下文只装它真读的那几份，而库里的字一个没少。

⚠️ **纯本地组装这条承诺不变**：写文件是写到用户自己选的目录，Spool 仍然不出网
（对话框那句「纯本地组装 · 直接粘贴给 AI 即可」要跟着改口径，见 §3）。

## 2. ⚠️ 一个必须现在就想清楚的陷阱：权威规则会被绕过

单项目打包时，「怎么读这份上下文」的说明（`INSTRUCTION_HEADER`）在**同一份文本的开头**，
读了内容就一定读过规则。

**拆成文件夹之后这个保证没了**：AI 完全可能直接打开 `01-申请规划.md` 而**根本没读 `INDEX.md`**。
于是 📖 Reference（机构来源 = ground truth）和 🧩 Synthesis（别的 AI 写的 = 只是框架，不是事实）
这条分界**在它眼里不存在** —— 而这正是 `DESIGN_FOLLOW_UP` §1.2 和
`DESIGN_CONTEXT_HYGIENE` 反复在防的「权威污染」。

三条路，**开工前要 Ocean 拍一条**：

| | 做法 | 代价 |
|---|---|---|
| 甲 | 每个 `.md` 顶上都带完整的 `INSTRUCTION_HEADER` | 最稳，但每份文件都长一截（现在约 1.5k 字符），10 个项目就重复 10 遍 |
| 乙 | 每个 `.md` 顶上带**一句话 + 指回 INDEX.md**，完整规则只在 INDEX.md | 省，但赌 AI 会去打开 INDEX.md |
| 丙 | 只在 INDEX.md 里写，别的文件不带 | 最省，**但等于把这条防线交给运气** |

⭐ 我倾向**甲**：这条规则的存在理由就是「一次记错会以最高权威坐在库里」，
而重复 1.5k 字符换的是它在每个入口都成立。**但这是他的判断，不是我的。**

## 3. 还没定的（都不挡开工，但开工时会撞上）

1. **导出到哪里** —— 弹系统目录选择器？还是默认桌面 + 弹一个「已导出，打开文件夹」的 toast？
   （后者更省事，但用户可能找不到；前者多一步。）
2. **单项目打包怎么办** —— 保持现状（粘贴对话框）不动？还是也给一个「导出成文件」的口子？
   ⚠️ 他这次只选了「导出成文件夹」，**没有**选「一份长文本 + 目录」，
   所以**多项目一律是文件夹**；单项目那条粘贴通路目前的理解是**不动**。
3. **`INDEX.md` 里每个项目那一行写什么** —— 摘要？块数？最近更新时间？跟进条目？
   （它是 AI 决定「要不要打开这一份」的唯一依据，写什么直接决定它读得准不准。）
4. **范围选择器（全部/置顶/近7天/近30天）在文件夹导出里还成不成立** ——
   成立的话是「所有项目一个范围」还是「逐项目一个范围」？
5. **导出是一次性快照** —— 明确不做同步。导出之后库变了，文件夹不会跟着变。
   这一条要写进 `INDEX.md`（带上导出时间），否则用户会拿三周前的文件夹当现状。

## 4. 工作区嵌套那一半（backlog §1.3，本设计的前置）

⚠️ **工作区目前是平的**，嵌套要动 schema。按四块估：

| 块 | 内容 |
|---|---|
| schema | `workspaces` 加 `parent_id`（自引用，可空）；⚠️ **只做加法，绝不重建表** —— 2026-05-29 清库事故的根子就是重建分支（见 `DB_BACKUP_AND_RECOVERY.md`） |
| 迁移 | 现有工作区 `parent_id = NULL`，一步到位，行为中性 |
| UI | 左栏树形展开/收起、拖动归属、`WorkspaceGroup` 递归渲染；⚠️ 别破坏 `Sidebar/SectionLabel` 那条「所有行落在同一条左边缘」的规矩 —— 层级用别的方式表达，不要靠缩进把行推走 |
| MCP 输出 | `list_threads` 的分组、`get_digest`、项目板、Pack 的工作区名 —— 所有按工作区聚合的地方都要认识父子 |

另外 backlog §1.3 还有一条**纯 UI、可以顺手做**的：**左侧边栏项目名按首字母排序**。
