### 0-latest.4 ⭐⭐ 「CPU 旁证」这条验收方法改了,别再用旧的

**旧做法**(`ps -o %cpu` 采两次)**不可靠**。`ps %cpu` 是**最近用量的衰减平均**,
启动那几秒的真实开销(首次渲染 + 开库,约 5 秒 CPU)会让它读出 **3–15%**,几分钟后才衰减下来。
本窗第一次量到 14.8%,差点当成 bug 去查。

✅ **新做法:量累计 CPU 时间在一个窗口里的差值。**

```
t0=$(ps -p <pid> -o time= | tr -d ' '); sleep 60; t1=$(ps -p <pid> -o time= | tr -d ' ')
# 换算成秒相减;60 秒里用掉 <0.5 秒 = 空闲
```

本窗三次装机都用它量了:0.01 秒 / 0.23 秒 / 0.04 秒(每次 60–90 秒窗口)—— **都是 0.0%**。
⚠️ **量之前先让 app 跑满一分钟**,否则窗口里含启动尾巴(第一次量到 2.4% 就是这么来的)。

### 1-quater ⭐ 圆圈徽章第二轮:数字居中 + 圆圈缩到和旁边的字一样大(08-10 晚上一窗的代码活)

**Ocean 看完上一轮的成品又提了两条**:「数字标记里面的数字没有居中」「圆圈的大小需要和边上的
时间和文字一致」。**两条是同一个病根:这个徽章是用 `em` 量的。**

改的只有一个文件:`SeqBadge.tsx`,一行 class。
`h-[1.5em] / text-[0.9em] / px-[0.32em]` → **`h-[13px] / min-w-[13px] / text-[9px] / px-[3px]`**。

- ⚠️⚠️ **`em` 会乘起来**:0.9em 的字装在 1.5em 的盒子里,在更正那一行(11px)就是
  **9.9px 的数字装在 14.85px 的圆里** —— 两个都不是整像素。居中要分的那点余量、
  以及数字自己的栅格化,**会朝着这一行恰好落在哪半个像素上四舍五入**。
  实测(2 倍屏)**数字偏上 1.5px,而且行一动它就变**。换成整像素之后剩 **0.5px**,
  那 0.5 是**字体自己的 overshoot**(圆头的 `2` 会冒过 cap 线),不是排版能修的。
- **圆圈变大也是同一个乘法**:14.85px 的圈,旁边 11px 的字其实只有 7.8px 高。
  **13px 这个数是对着「旁边的字」挑的,不是对着字号挑的** —— 它下沿和文字的下伸部齐,
  上沿比 cap 线高约 2px,所以读起来是这一行上的东西,不是浮在上面的泡泡。
- ⚠️ **现在是「两处共用一个写死的尺寸」,不再跟着行的字号走。** 两个调用点是 10px(块头)
  和 11px(更正那一行),13px 在中间。**不要为此加一个 size 参数** —— 加了小数就回来了;
  真有第三个调用点,就在这个文件里再写一个整像素的值。

⭐⭐ **怎么验的(这一条对下一窗最有用,配方在 §6.2-sexies)**:
**四条基线一条都看不见这种 bug** —— `tsc` 干净、324 个测试全过、两侧渲染器的 golden 平价
测试更是压根不看界面,**改之前改之后一模一样**。而 §6.2-bis 说的「app 截图这条路在这台机器上
是断的」也还断着。**办法是把这一小块 markup 单独拿去渲染**(真字体 + 真色板),
**圆圈画红色、数字画蓝色,再用 Python 量两个墨迹包围盒相减**,上下差多少个物理像素当场是个数。
⚠️ **它只证明这一小块,不证明装起来的那一屏** —— 「长得对不对」仍然只有 Ocean 能看。
台账 §3.22 / §3.23。

**⚠️⚠️ 第二轮(同一天更晚):Ocean 说「数字有点偏上,没有对准圆心」—— 他是对的,
而且第一轮我用错了量具。**

| | Chrome 量的 | **WKWebView 量的(app 真正跑的)** |
|---|---|---|
| 第一轮改完 | 偏上 0.5px「看着修好了」 | **偏上 1.5px —— 根本没修好** |

**两个内核把基线放在行盒里的位置不一样**,拿 Chrome 量这个 app 等于量另一个程序。
换成 WKWebView 重量之后:

  1.5px 正好抵消 WebKit 抬上去的那 1.5px。**这个数是量出来的,不是估的。**
