### D2 · 一个项目的压缩结果，在别的项目里能点

**原话**：「一个项目的压缩在另外一个项目里竟然能够点击跳转，应该是每个项目有自己的压缩操作区。」

**现状**：**属实，而且是设计成这样的。** `results` 是 store 里一个**全局数组**（[compressStore.ts:138](src/stores/compressStore.ts#L138)），`CompressRail` 无条件把整个数组渲染出来（[CompressRail.tsx:170-177](src/components/Compress/CompressRail.tsx#L170-L177)），**不按当前项目过滤**。点一下 `openResult(i)` 就把别的项目的核对桌开在你现在这个项目上。

**为什么当初这么写**：夜间队列（§9.6.4）—— 睡前排三个项目、早上起来一次看完。全局单子是为那个场景服务的。

**实质**：**两个场景被塞进了同一张单子。** 「我现在在这个项目里」和「昨晚那一批的收件箱」是两件事，右侧栏是前者的地盘。

**修法**：右栏只显示**当前项目**的结果；夜间那一批另开一个地方（比如现有的待审面），或者在右栏里明确分成两段并写清楚哪段是别的项目。

### D3 · 一份还在审核中，又能开跑同一个项目

**原话**：「成功压缩一次后会有按钮压好了等你核对，这时候再次点击压缩这个项目，会导致原来的压缩内容还在审核中，后台却在运行新的一次压缩，有歧义。」

**现状**：「压缩这个项目」只在 `running || batchRunning` 时禁用（[CompressRail.tsx:69](src/components/Compress/CompressRail.tsx#L69)）。**「这个项目已经有一份结果在等核对」不在禁用条件里。** 点下去 `openProject` 直接用新 session 覆盖当前 session。

**实质**：**同一个项目可以同时存在两份互不知道对方的压缩稿**，而用户界面上只有一张桌子。这是"沉默的失败"那一类 —— 屏幕上不会有任何东西告诉你上一份去哪了。

**修法**：同一个项目已有未处理结果时，按钮改成「上一份还没核对完」并指回那一份；真要重压，先明确丢弃旧的。

### D4 · 结果报告是一堵墙，看不懂它想说什么

**原话**：「压缩操作区写了一大堆文字，但是根本看不懂想表达什么，用户需要理解一大段文字才能明白压缩结果，摩擦极大。」

**现状**：核对桌顶部那一段（[CompressBoard.tsx:230-315](src/components/Compress/CompressBoard.tsx#L230-L315)）按顺序连着排了：块数 / 字符数 / 百分比 / 目标档位没达标 / 秒数 / 少了 N 条批注 / 少了 N 条自己写的 / 少了 N 条引用关系 / 引号被改写 / 它凭空写的批注全文列出 / 它自己说删了什么（整段原文）/ token 数 / 缓存命中 / 钱。**全部是同一号字、同一个颜色、没有分组、没有主次。**

**实质**：**每一条单独看都是对的，合起来没有回答用户唯一想问的那个问题 —— 「这一份能不能用？」**
这一段是四轮实测的产物：每查出一个毛病就往上加一行。**加的时候每一行都有理由，从来没有人退后一步看整体。**

**D4-a 修法**：最上面先给一句结论（例如「不建议用：丢了 3 个日期」/「可以用：省了 16%，没丢东西」），细节收在结论下面。**先判断，后证据。**

**D4-b 另一件事（不是文案问题，是核对器的缺陷）**：
那 13 条「凭空写的批注」和 13 条「少了的批注」**是同一批东西**——原批注被改写后的样子。
现在的核对器（[compress.ts](src/lib/ai/compress.ts) 里 `missingNotes` / `fabricatedNotes`）拿**整条字符串精确比对**，
改一个字就同时算「原来那条丢了」+「多出一条没写过的」。

> **后果**：警报数目翻倍，而且把最严重的那类（真的凭空捏造）淹没在改写里。
> §9.9 判定「不解锁写入」时用的正是这两个数 —— **那两个数偏高，但方向不变**
> （丢日期那条结论是靠 `missingNumbers` 撑的，不受这个影响）。
> ⛔ **不要因为这条就去放松核对**：正确修法是**把「改写」单列成第三类**，不是把它算成没事。

### D5 · 「压多狠」这个旋钮自相矛盾

**原话**：「这个提示自相矛盾，又说不取决于你选哪一档，又给出选择按键。并且充斥的 ⚠️ 让 ui 看起来很紧张，不友好。」

**现状**：档位条上三个按钮（只删重复 / 保留结论和数字 / 压到最短），紧跟着一行写死的话（[CompressBoard.tsx:162](src/components/Compress/CompressBoard.tsx#L162)）：

> 「⚠️ 实测：压多少主要取决于这个项目里有多少重复，不取决于你选哪一档。」

**这句话是对的**（§9.9 一 的实测结论），但它和它上面那三个按钮**直接打架**。

**实质**：**当初把一条实测结论直接贴到界面上，当成了"诚实"，其实是把一个没解决的问题丢给了用户。**
真正的结论不是"档位没用"，而是 **§9.10 十 第 1 条那个还没做的东西**：
**压之前先本地算一遍这个项目有多少重复**（`find_similar_blocks`，本地、免费、不出网），
算出来接近 0 就直接告诉他"这个项目压不动，别花这个钱"。
**那条做了，这句自相矛盾的话就不用写了 —— 它会变成一个具体的判断。**

**D5-b · ⚠️ 太多**：这一屏上 `⚠️` 出现了七八处。**警告符号一多就不再是警告，是背景噪声。**
规矩定成：**一屏最多一个 ⚠️，留给"这一份不能用"那一类**；其余用文字说清楚。

### D7 · 数字没了，光提醒不够

**原话**：「提示⚠️ 这一块里有 3 个数字/日期没了：2025-09-17、100、101，有提醒不够，需要能帮用户一键加回去才是真的有用的功能。」

**现状**：[EntryCard.tsx:123-130](src/components/Compress/EntryCard.tsx#L123-L130) 只把丢掉的数字列出来，没有任何动作。

**实质**：**这条比它看起来重要得多 —— 它可能是解锁压缩写入的那把钥匙。**
§9.9 判定不解锁的理由是：「它压得动的时候会丢日期，它不丢日期的时候等于没压，而两种结果长得一模一样。」
§9.9 八·1 给的解法是**把「数字一个不少」变成硬闸门**（丢了数字就不许存，只能重跑）。

> **Ocean 这条给的是第三条路，比重跑好**：**丢了就补回去。**
> 数字和它所在的那句话在原文里都还在，**这是一个纯本地、不花钱、不问模型的动作。**
> 补回去之后那份稿子就过闸了 —— 不用重跑，不用等模型配合。

**修法**：每一条「少了的数字」后面给一个「加回去」；一次点完把原句插回压缩稿对应位置。
⚠️ **插哪儿是这条唯一的难点**（原句在压缩稿里可能已经被合并掉了），要先想清楚再动手。

### D8 · 前后对比不许折叠

**原话**：「压缩前后对比，被删除的的文字和新增的文字直接显示在对比上，不要折叠隐藏，不会有人点进去看的。」

**现状**：按块核对时，删掉/新增的句子收在一个默认关闭的折叠里（[EntryCard.tsx:145-172](src/components/Compress/EntryCard.tsx#L145-L172)，`changesOpen` 初值 `false`），标题是「压掉 N 句 · 它自己写了 M 句」。

**实质**：**这是整个核对流程的要害。** 核对界面存在的全部理由就是让人看见改了什么；
把改了什么折叠起来，等于**做了这个功能又把它关上**。
"不会有人点进去看的"是对的 —— 而没人点，核对就是走过场。

**修法**：默认全部展开。真怕太长，就限制每块显示的行数并给"看全部"，**但删改内容本身必须一眼可见**。

### D10 · 估算不准就别显示

**原话**：「压缩的价格预估和压缩程度预估准确度没有保证，测试如果能够保证准确才能写，不然就不显示。」

**现状**：两处估算：
- **钱**：右栏夜间队列里「{k} 千字 · 约 ¥X」和合计（[CompressRail.tsx:130-160](src/components/Compress/CompressRail.tsx#L130-L160)），按字符数线性外推。
- **压缩程度**：档位说明写「实测压完剩 60–100%」，核对桌用 `LEVEL_TARGET` 报「这一档的目标是压到 50–75%」（[CompressBoard.tsx:89](src/components/Compress/CompressBoard.tsx#L89)）。

**这条他说得对，而且有实测撑着**：
- 钱的估算**只按输入字符算**，而 D0-二 那次证明**输出 token 可以和输入一样多**，
  且输出单价是未命中输入的 3 倍。**按字符外推系统性偏低。**
- 「目标 50–75%」这个数**§9.5 已经写明是空话**（「两个档位的目标百分比，是空话」），
  他这次实测 84%，界面还在报"没达标"—— **拿一个已知不成立的目标去判一份稿子不合格。**

**修法（按他的规矩：测准了才写，测不准就不显示）**：
1. **压缩程度的"目标"整个撤掉**，界面不再判"达标/没达标"。要显示就显示实测分布（60–100%），并说清楚它取决于项目里有多少重复。
2. **钱的估算要么重做（把输出 token 算进去，用四轮实测回归一条），要么只显示字数不显示钱**，跑完之后报真实账单。
3. 无论哪种，**估算和账单在界面上必须分得出来**。
