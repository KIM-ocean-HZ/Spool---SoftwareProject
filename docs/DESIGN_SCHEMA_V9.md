## 1. H-1:给块一个人能看见的编号

### 1.1 为什么需要它(这条比「拦不拦」更根本)

现在的硬规则是「内部 id 只是工具参数,永远别让用户看见」。理由是对的:
`sbC2zgToKq9XmNp3Vr7Yz` 对人是纯噪声。

但**需求是真的**:AI 要指着某一块说话,用户要能找到那一块。现在唯一的办法是引用预览
(把那块的前 40 个字念出来)。**库里有一模一样的重复块时,预览根本指不准**——
实验室里就有三条同样的话。

Ocean 的原话:

> 「没有办法把内部编号映射到用户可以看见的数据上吗,比如给每个 block 一个独立的编号,
> 或者点击高亮显示该 block,从 UI 界面来接受 id。」

**这一条把矛盾解掉了**:块有了人能看的号,AI 就再也没有理由去写裸 id。
于是「add_block 检测到裸 id 就硬拒绝」(D-1)从此不再有代价 ——
**顺序必须是:先做可见编号,再把写入改成硬拒。**

### 1.2 便宜路线(几乎零成本)

pack 里每一块本来就打着 `[2026-06-29 10:00]`,App 的块流里也看得见时间。
把「时间戳 + 项目标题」正式确立为**对用户的指代方式**,写进 instructions 和工具描述
(现在只说「别说 id」,**没说「那该怎么指」**)。

- 成本:改几段文案,零代码。
- **解不掉的**:同一分钟内捕捉的两块时间戳一样;重复块本来就常常是同一批捕捉进来的。
  正好是最需要区分的场合失效。

### 1.3 正路(要动 schema)

`blocks` 加一列 `seq`:**每个项目内单调递增、永不复用**的整数。

- **必须落库,不能派生。** 「按时间排第几」这种算法,删掉一块后面全变——
  用户昨天记下的 `#12` 今天指向别的东西,比没有编号更糟。
- 分配规则:新块 `seq = (SELECT COALESCE(MAX(seq),0)+1 FROM blocks WHERE thread_id=?)`。
  删除不回收。
- 存量数据迁移:按 `created_at ASC, rowid ASC` 给每个项目的现有块编号(和 pack 的
  渲染顺序一致,所以老 pack 里第几块就是 `#几`)。

**露出面**:
- pack 每一块的头部:`#12 [2026-06-29 10:00 · from Claude] 正文…`
- `get_blocks` / `search_blocks` / `find_similar_blocks` 的每条返回加 `seq`
- App 块流里显示 `#12`(样式见 §1.4)
- **id 仍然不露**。`seq` 是给人的,`block_id` 还是工具参数。

**⚠️ 这会动 pack 渲染** → `assemble.ts` + `templates.ts` + 重生 golden + `mcp.rs` 同步
(硬规则 5)。

### 1.4 App 里长什么样(第 2 题)

| | 样式 | 好处 | 坏处 |
|---|---|---|---|
| a | 块左上角灰色小字 `#12`(建议) | 一眼能对上 AI 说的号;不抢戏 | 每块多一个视觉元素 |
| b | 只在鼠标悬停时出现 | 最安静 | AI 说「第 12 块」时,用户得挨个划过去找 |
| c | 不显示,但支持搜索框里输 `#12` 跳转 | 界面零变化 | 用户得先知道有这个功能 |

我建议 **a**,并且**点一下这个号就滚动+高亮那一块**(Ocean 原话里的「点击高亮显示」)。

## 2. H-3:存进来的 PDF 里的字能被搜到

**现状**(实测):`blocks_fts` 只索引 `content` + `annotation`。附件抽取出来的正文
完全在索引外面——讲义里明明有那句话,`search_blocks` 返回 `total: 0`。

**改法**:`blocks_fts` 加一列 `extracted`,由附件表的 `extracted_text` 聚合而来。

要考虑的三件事:

1. **一块可以挂多个附件** → 聚合成一个字段(用换行拼)。
2. **触发器**:附件的增/删/改都要更新对应块的 FTS 行。现在的触发器只挂在 `blocks` 上,
   要再加一组挂在 `attachments` 上。
3. **命中之后要看得出「这句话在附件里,不在正文里」** → `search_blocks` 的命中要标出
   `matched_in: "attachment"`,并给出是哪个附件。否则用户会以为块的正文里有这句话,
   点进去却找不到。

**建索引的成本**:迁移时要把现有所有附件正文重新灌进 FTS。真库里有多少附件、多大,
迁移前先量一遍。

## 3. 一次迁移,做完这两件事

```
schema v8 → v9:
  1. ALTER TABLE blocks ADD COLUMN seq INTEGER;
  2. 回填 seq(按项目、按 created_at ASC, rowid ASC)
  3. 重建 blocks_fts,加 extracted 列
  4. 灌入现有附件正文
  5. 新增 attachments 上的三个触发器
```

**双侧锁步**:`src/lib/db/client.ts` 的迁移注册表 + `mcp.rs` 的
`EXPECTED_SCHEMA_VERSION`(现在是 8)必须同一次改。MCP 端遇到不认识的 schema 版本
会拒绝写入——这是 2026-05-29 那次清库之后立的规矩,别绕过它。

## 4. 做完之后顺带能做的(不在本轮,但要记着)

- **D-1 add_block 硬拒绝裸 id**:可见编号落地后,AI 再也没有理由写裸 id,
  硬拒绝就没有代价了。**必须排在 H-1 之后。**

## 5. 我建议的顺序

1. 先量真库:多少块、多少附件、附件正文总共多大。(半小时,决定迁移要不要分批)
2. 备份真库。
3. 一次迁移写完 `seq` + FTS。
4. 露出面分两批:先 MCP 侧(pack + 三个工具),再 App 侧(块流显示 + 点击跳转)。
5. 最后才动 D-1(硬拒绝)。
