## 0. 一句话定位

**MCP 是回答者,不是维护者。它的写入是从"回答"那一端伸回库里的手,
只能伸回库里自己产不出来的东西。**

推论,也是本稿全部设计的来源:
- **维护是回答的副产品,不是一份独立的工作。** 不做"专门跑一趟整理你的库"这种通道。
- **写入必须让库变成更好的输入。** 否则它就该被砍掉 —— 见 §1 那个反问。

## 1. 先回答那个反问:写入权限凭什么存在

Ocean 问得比他自己以为的更狠:**如果 MCP 只是省去 compact 那一步,写入权限有什么用?**

答:**没用。** 而且这不是修辞 —— `get_pack` 的定位本来就是"用户原样粘给任何 AI",
官网白纸黑字写着「没配 MCP 也全功能」。**纯回答这件事,剪贴板已经覆盖了。**

所以:**写入权限唯一不可被剪贴板替代的价值,是改变库的状态。**
一次写入如果没让下一次的输入变好,它就是在给剪贴板做无用功。
这条是下面那道闸门的全部依据。

## 2. 那道闸门:可推导性

> **能从库里已有的东西推出来的,只进答案,不进库。**

**能推出来 → 别写。** 两处害:
1. **噪音放大。** 写一份"机器学习课整体总结"存回去,下次读 pack 时它躺在那儿,
   而 pack 的授权规则把它标成 🧩 Synthesis —— "只当框架,不当事实"。
   等于喂自己一份降级过的自己的输出。信息量没增加,长度增加了。
2. **权威洗白。** AI 的一句推测,下一次以"库里躺着的材料"的身份出现,
   看着和用户亲手存的东西一样正当。这比噪音更坏。
3. **会过期,而且看不出来。** 再来五块新的,那份总结就是错的,
   但它结构上完全合法,`check_library` 查不出来。

**推不出来 → 写。** 用户的困惑 + AI 的推理 = 那个结论,库里原先只有困惑。
这时候库是真的变厚了,不是变啰嗦了。

### 2.1 三种场景照这条闸门判

| 场景 | 判 | 为什么 |
|---|---|---|
| **结论回填** —— 用户问、AI 答、用户说"存回去" | ✅ 写 | 那句话原先不在库里,来自推理不是压缩。golden fixture 里就是这个样子:`#1` 用户块带批注「一直没懂为什么要除 sqrt(d_k)」,`#6` 是 MCP 署名结论 + `↩ cites:` 指回 `#1` |
| **分流归位** —— 用户贴一大段,横跨三个项目,AI 拆开分派 | ✅ 写 | AI 干的是**判断**不是生成。这是最有价值的一种,也是唯一需要新界面的一种(§4) |
| **总结全文** | ❌ 别写 | 可推导。**除非**推导很贵且结论很稳(两百块的项目、花了大力气才得的结论)—— 那是 `distill` 的定位,不是"总结全文" |

### 2.2 顺带说清:MCP 块和用户块的价值不同币种

不等同,但都是硬通货:
- **用户块**:第一手、带体温。💭 Personal 信号最强就是这个意思。
- **MCP 块**:补上库里缺的那一环。

所以不需要"给 AI 块单独划一块区域"。**块流按时间排,来源标签负责区分权威**,
这套四类授权规则已经在跑了,再加一层物理分区是重复造闸。

## 3. 为什么否掉 merge conflict 那套

Ocean 的方案:给 MCP 完整写入权限(含修改),用户逐块审批,并自动维护一份用户原始数据。

**三条否的理由,由轻到重:**

### 3.1 git 那个比喻在这儿没有活干

git 要三方合并,是因为**代码是被维护的对象**,两个人改同一行。
块是 append-only 的,**没有人改块**。没有同一行、没有共同祖先、没有冲突可解。
merge conflict 那整套机器搬过来是空转。

### 3.2 「自动维护一份用户原始数据」已经免费拿到了

用户的块从来不被修改 —— 所以原始版本**永远在那儿**,不需要额外存快照。
Ocean 想造的那个安全属性,是现在这个数据模型的**结构性后果**,不是要加的功能。
(⚠️ 这一条别当成"不用管数据安全",而是"这一处的安全已经由 append-only 承担,
再加一层快照是把已经硬的东西又软一遍"。)

### 3.3 最重的一条:审批疲劳,它换掉的机制比它自己强

「完整写入权限 + 用户点头」逻辑上自洽:用户批的就是用户自己的编辑,AI 只是手。
反对的理由不是逻辑,是人:

**审批闸防的是"写错的东西",防不了"用户点得太快"。** 第五十次弹窗的时候,
人一定是连看都不看就过。

而 append-only 那条承诺防的**恰恰是这个** —— 它不依赖用户每一次都清醒。
那是它作为**信任特性**的全部价值,也是「允许 AI 写入」这个开关敢让人打开的原因。
**用一个会疲劳的机制,去换一个不会疲劳的机制,不划算。**

**所以:提案永远是追加式的。** 分流可以提"这段该拆成三块进三个项目",
不能提"把你那块改一下"。

## 4. 保留下来的那一半:分流审批队列

Ocean 方案里真正有价值的是**审批队列**,但它该小得多、也只服务一个场景。

### 4.1 为什么只有分流需要界面

| | 单条结论回填 | 分流一大段 |
|---|---|---|
| 一次几块 | 1 | 三到十几 |
| 出错的后果 | 一块内容不对,看得见 | **进错抽屉** —— 块本身没错,位置错了,而位置就是 Spool 的全部结构 |
| 判断是谁做的 | AI 生成内容,用户判断内容 | AI 判断归属,用户**只能判断归属** |
| 在聊天窗里逐条念 | 可行,一句话的事 | 不可行,十几块念完用户已经不看了 |

结论:**分流是唯一"高量 + 高风险 + 机械"的场景**,而这三条正好是需要独立界面的三条。
单条结论回填继续走 `dry_run`,同步、轻量,不动。

### 4.2 时间形状:异步,不是 git 那种同步

这是最硬的一处工程约束,得先定。

git 解冲突时人在键盘前,合并停住等他。**MCP 写入不是** —— AI 调工具,几秒内必须拿到返回,
而用户可能在睡觉、在别的 app 里、四十分钟后才点。所以不能卡住等。

**`propose_blocks` 立刻返回「已提交 N 条待审」**,不等用户。三条随之而来的规矩:

1. **AI 必须把"已提交待审"和"已存进库"说成两件事。** 工具描述里写死,
   否则 AI 会对用户说"存好了",而用户的库里什么都没有。
   (⚠️ 这是本设计最可能出的事故,`human_headline` 的措辞要盯 —— 硬规则 13。)
2. **提案不进块流、不进 pack、不进 digest、不进 search。** 待审就是待审,
   `get_pack` 读不到它。否则 AI 会读到自己没落地的提案,拿它当材料。
3. **提案有保质期**(建议 7 天),过期自动作废并在审批面留一行"已过期"。
   不设期限,队列会变成第二个待办清单 —— §3.2 第 4 条那条"从 08-01 拖到今天"的教训。

### 4.3 界面:一屏,批量为默认动作

不做逐块弹窗(那正是 §3.3 说的疲劳源)。做**一个待审面**:

- 入口:主窗一个角标(「AI 提了 8 条待你过目」),**不弹窗、不打断**
  (`capture-note-first` 那条铁律:主窗永不跳前)。
- 一屏列完,每条显示:**正文预览 + 要进哪个项目 + 原文的哪一段**(见 §4.4)。
- 默认动作是**全批**和**全驳**两个大按钮;逐条勾选是次要路径。
  理由:分流的判断颗粒是"这次拆得对不对",不是"第三块对不对"。
  拆错了通常是整体拆错,一条一条改的成本比重来一次高。
- 驳回不需要理由,也不留痕(留痕会让队列变成垃圾场)。
- **驳回一条待审项 = 撤回**。所以交接 §4 第 10 条那件事**不用单独设计了**,
  也不再需要回答"时间窗多长""算不算 AI 自己写的"那一堆边界 —— 那些问题在
  "东西还没落地"的世界里不存在。

### 4.4 溯源:拆出来的块必须指得回原文

这是现在还空着的一处,也是分流跟普通 `add_block` 唯一的数据差别。

一段话拆成三块,三块各自都是原文的**片段**。如果不记原文,用户三周后看到其中一块,
没法判断它是不是被拆得断章取义了 —— 而断章取义正是分流唯一会犯的错。

✅ **Ocean 2026-08-05 拍板:走 A 案,用现成的 `ref_block_id`。** B 案封存,别动 schema。

- **A(已批,M1 照这条做)**:分流时先把**整段原文**存成一块(用户署名的那种,
  因为它是用户给的),再把拆出来的每一块用现成的 `ref_block_id` 指回它。
  零 schema 改动,`↩ cites:` 那一行渲染现成,pack 里读起来就是
  「这块出自那段原文」。代价:原文那一块会占一个项目的位置 —— 建议进用户指定的
  某一个项目,或者一个"收件箱"项目。
- **B(封存,别做)**:新增一个 `excerpt_of` 字段。更干净,但要动 schema(第 10 版),
  两侧锁步常量 + 真库迁移 + golden 重生,一整套。真需要时再升级 ——
  `ref_block_id` 到 `excerpt_of` 是加字段不是改语义,两者不互斥,今天走 A 不堵死 B。

⚠️ **A 案落地时的一处前提**:原文块和拆出来的块**可能不在同一个项目**
(原文进"收件箱",拆出来的进三个正主项目)。所以 `↩ cites:` 那一行**必须标出被引块
在哪个项目** —— 否则用户看到"出自那段原文"却在本项目里找不到它。
这正好是 §3.1 第 3 条那笔旧账(`↩ cites:` 不标项目名),**它现在是 A 案的前置依赖,
不再是可有可无的润色。**

## 5. 工具描述要加的话(那道闸门的确切措辞)

闸门写在文档里没用,得写进 AI 读得到的地方。三处:

**5.1 `add_block` 的描述,开头加一句:**

> Write only what the library cannot already produce. A conclusion that took real
> reasoning to reach, or the user's own words they asked you to keep — yes. A summary
> of blocks that are already here — no: you would be feeding yourself back a
> downgraded copy of your own output (packs mark AI-written text as 🧩 Synthesis =
> framing, not fact), and it silently goes stale as new blocks arrive.

中文那一半照 `t!` / `ts!` 的规矩一起写(硬规则 12)。

**5.2 server instructions 里,写入那一段改成角色声明:**

> You are the one who answers, not a librarian. Writing back is for what this
> conversation produced and the library lacks — not for tidying it up.

**5.3 `propose_blocks`(新)的描述里,把 §4.2 第 1 条写死:**

> This does NOT save anything. It queues proposals for the user to approve in Spool.
> Tell the user they have N items waiting for review — never that you saved them.

- **自动维护用户原始数据的快照** —— §3.2,append-only 已经免费给了。
- **"专门整理一趟"的通道** —— §0,维护是副产品。
  ⚠️ 这条和 `thread_health` 不矛盾:`thread_health` **只报不改**,它的产出是给用户看的
  发现,不是写回去的块。
- **提案进 pack / digest / search** —— §4.2 第 2 条。
