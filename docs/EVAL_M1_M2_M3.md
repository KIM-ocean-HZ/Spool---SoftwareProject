## 1. 我认为最可能错的三条(按严重程度)

### 1.1 🔴 `source_text` 是一条权威洗白通路

**事实**:§4.4 A 案要求原文块「以用户署名存」,我照做了 —— `source = NULL`。
而 pack 的授权规则把无来源块判成 **💭 Personal = 用户自己的意图,信号最高**。

**推论**:AI 在 `source_text` 里写什么,批准之后就会以**库里权威最高的身份**躺在那儿。
稿子 §2 花了整节论证「权威洗白比噪音更坏」,而 A 案在分流这条路上把它开了个口子。

**为什么我还是照做了**:这是 Ocean 08-05 明示拍板的(§7 第 4 条),而且防线是真的存在 ——
用户在待审面上看得见整段原文,我把它渲染成**不折叠、不截断**的一整块,并且写明
「会以你自己的名义存进〈X〉」。

**为什么我仍然不放心**:§4.3 让「都存进去」当默认动作。默认动作 + 一大段原文 =
用户很可能不读那一段就点了。**这不是实现 bug,是设计里一个真实的权衡,得让 Ocean 看见。**

**探针 P1**:调 `propose_blocks`,`source_text` 塞一段**不是用户说过的话**
(比如「我已经决定放弃这门课」),批准,然后 `get_pack` 看它落在哪一类。
预期:落进 💭。**如果落进 💭,这条就该上报给 Ocean 定,而不是我自己改设计。**

### 🔴 探针结果:**成立,原样发生**

`source_text` 传「我已经决定放弃这门机器学习课了,不打算再交作业」,工具**零阻力接收**;
按批准路径落库之后,`get_pack` 里它渲染成 `#3 [2026-08-05 14:13] 我已经决定放弃…`
—— **没有来源标注**,而 pack 开头的授权规则写着「💭 Personal…the user's own hypotheses
and notes…Blocks with no `source` field」。**AI 提供的一段话拿到了库里权威最高的身份。**

**这不是 bug,是 §4.4 A 案的直接后果,所以我没有擅自改。** 交 Ocean 的一句话是:
> 分流时那段「原文」以你自己的名义存进库(pack 里算 💭,权威最高)。防线只有一条 ——
> 你在待审面上会看见整段全文。但默认按钮是「都存进去」,你可能不读就点了。要不要
> (a) 给它一个来源标签、(b) 让它单独勾一次、(c) 只在很长的时候单独确认?

**我在不推翻决定的前提下做了的**(见 1.2b):把那一屏和那句话里所有**数不对的地方**改对了 ——
用户至少不会在「我以为只有 2 条」的情况下让 3 块落进 3 个项目。

**如果要收口,三个候选(都没做,等拍板)**:
- (a) 原文块给一个来源标签(例如 `Claude · MCP — 用户原文`),代价:它不再是 💭,
  §4.4 A「因为它是用户给的」这条理由就落空了;
- (b) 待审面上原文那一段单独一个勾选框,默认**不勾**;
- (c) 只在 `source_text` 超过某个长度时强制单独确认。

### 1.1b 🔴(探针跑出来的新一条)数不对:说 2 条,落库 3 块

P1 顺手撞出来的:`propose_blocks` 返回 `queued: 2`,headline 让 AI 跟用户说
「Spool 里有 2 条待你过目」;待审面的大按钮写「都存进去(2 条)」。
**但批准会写 3 块** —— 多出来的那一块是原文,而且落进一个**前面哪句话都没提到的项目**。

这和 §4.2-1 要防的是同一类事故(「说成已经存好了」),只是晚一步发生:
错的是数量和落点,不是时态。**✅ 已修并重验:**

- payload 加 `blocks_on_approval`;headline 在有原文时补一句
  「那整段原文会以用户自己的名义存进〈X〉…所以他点头之后落库的是 3 块」,没有原文时不出现
- 待审面按钮从「条」改成**「块」**,并把原文算进去;原文那一栏补一句「这段本身也算一块」
- Rust 测试把两种情况都钉住了(有原文断言 `blocks_on_approval=4` + 项目名出现在 headline
  里;没原文断言「原文」二字不出现)

### 1.2 🟠 批准写到一半失败 = 可能重复写

**事实**:`approveBatch` 是逐块 `createBlock`,最后才删批次。中间任何一块抛错,
异常直接抛出去 —— **已经写进去的块留着,批次还在**。用户再点一次「都存进去」,
前面那几块**会被写第二遍**。

**为什么它是真的会发生**:`idx_blocks_thread_seq` 是唯一索引,GUI 和 MCP 子进程
同时往一个项目里写就可能撞号(`insertBlocks` 的注释里已经承认过这个竞态)。
一批 8 条正好撞上一次 MCP 写入,就进这条路。

**探针 P2**:在 `approveBatch` 的循环里人为让第 2 条抛错(或者用一个 thread_id
在写到一半时被删),看重试后库里有几块。

### ✅ 探针结果:属实,已修并验过「去掉修复就会红」

用一个 `BEFORE INSERT ... RAISE(ABORT)` 触发器只让**第二条**的插入失败,重试后:
修复前 —— 原文和第一条**各写了两遍**;修复后 —— 各一遍,而且补上的那一条**仍然引用**
第一趟就写好的原文块。

**修法(已落地)**:每写成一块就 `DELETE` 掉那一行提案;原文一写完就把它的 id
`UPDATE` 进剩下所有提案的 `ref_block_id`,并把批次上的 `source_text` 置空。
重试因此只写没写成的那些,而且引用不丢。不需要事务
(`tauri-plugin-sql` 的连接池本来就撑不住跨语句事务 —— threads.ts:141 那条老账)。

### 1.3 🟠 「AI 归档了 N 块」的 N 数错了会当场翻车

**事实**:我数的是**全库块总数**跑前跑后的差。理由写在代码里:周回顾会写进别的项目,
只数本脉络会漏。

**漏洞**:跑的这几分钟里用户自己双击 ⌥ 捕捉了两条,就会被算进「AI 归档了 N 块」。
这是**当场就能被用户抓到的假话**,而这个功能的全部资本就是「你看得见 AI 干了什么」。

**探针 P3**:起一个跑得久的动作,跑到一半手动捕捉一条,看 toast 报几块。

### ✅ 已修(没有取舍,就是我数错了)

`countBlocks()` → `countMcpBlocks()`,只数带 MCP 来源标签的行:
`source = 'MCP' OR source LIKE 'MCP — %' OR instr(source, ' · MCP') > 0`。

⚠️ 这条规则现在有**两处实现**(这段 SQL,和渲染面用的 `isMcpSource()`),
两处写同一条规则一定会漂 —— 所以 `blocks.test.ts` 新增一条**平价测试**:
九种来源标签同时喂给两边,断言数出来的一样(5 个)。
