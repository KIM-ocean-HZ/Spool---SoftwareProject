# 捕捉重构:双击 ⌥ 之后直接写批注(note-first)+ 砍掉收集面板

2026-07-31。Ocean 提出、授权「审查通过即动手」;本文是审查结论 + 实现记录,
供 Ocean 复核。**如对结论有异议,回滚点是本批次的提交。**

## 0. Ocean 的原始想法

1. Spool 专注的是**用户的个人思考**,但双击 ⌥ 只把剪贴板搬进去,想留一句自己的话
   (note)还要再点两下——不利于养成「任何信息都留 note」的习惯。
   想要:双击 ⌥ 弹出 toast 后**自动进入 note 输入框**,直接打字零摩擦,
   点击外部 = 不留 note。
2. 如果快捷 note 成立,**收集面板(长按 ⌥)是不是可以整个不要了**?
   它不够简洁,而且能被「连续双击」替代。
3. 顺带:收集面板里单击 ⌥ 的行为不稳定——有时放大缩小,有时直接加块。

## 1. 审查结论:两条都通过,附三个修正

### 1.1 note-first 成立,而且大半机制已存在

现在的 toast **本来就有批注编辑器**(双击 toast 正文展开、自动聚焦、失焦保存、
Esc 取消、各条 dismiss 路径都会 flush 草稿)。改动本质只有两件:

- toast 出现时**默认就展开批注框**,并且**捕捉浮窗主动拿键盘焦点**
  (今天是刻意不拿——`focus:false` + 弹出后把焦点还给来源 app);
- 所有关闭路径把焦点**还给来源 app**(还焦点的机制 `reactivate_app_async`
  已存在,只是今天在弹出时用,现在挪到关闭时用)。

**代价要说清楚**:双击 ⌥ 之后紧接着的键盘输入会进 note 框,而不是用户原来的
编辑器。这正是 note-first 的本意(邀请你写一句想法),但对「双击完继续在原 app
打字」的肌肉记忆是个行为变化。缓解:

| 用户想干什么 | 动作 | 结果 |
|---|---|---|
| 留一句话 | 直接打字 → **Enter** | 存为该块批注,toast 关,焦点回到原 app |
| 换行(长 note) | Shift+Enter | 正常换行,「完成」/Enter 提交 |
| 不留 note | 点外部任意处 / Esc | toast 关、无 note、焦点回原 app |
| 连续摘录 | 回原文选下一段(这一下点击本身就是「点外部」) | 上一条自动收尾,毫无额外成本 |
| 什么都不做 | 置之不理 | 8 秒后自动关(框里没字才会自动关),焦点归还 |

### 1.2 修正一:点外部时**框里有字就保存**,空才是「无笔记」

Ocean 说「点击外部即代表无笔记」——按字面实现会把已敲的字扔掉。
捕捉工具丢用户打过的字比多存一条批注严重得多(且撤销/改批注都容易)。
所以:**点外部 = 空框不存、非空保存**。「无笔记」的含义落在「不打字直接走」上。

### 1.3 修正二:收集面板砍掉,判定为**结构性缺陷**而非 bug

单击 ⌥ 行为不稳的根因(读 double_tap.rs 状态机可证):

- 单击「结算窗」300ms < 双击判定窗 500ms。两次间隔 300–500ms 的「单击」,
  第一击先触发了缩放,第二击又和第一击配成了「双击」→ 直接加块。
- 双击加块还受 copy-gate 约束(10 秒内有过 ⌘C 才算捕捉),收集时通常刚复制过,
  所以「有时加块、有时缩放」随打字节奏和复制时机漂移。

这不是实现错误,是**三种手势(单击/双击/长按)挤在同一个键上、时间窗又互相
重叠**的必然歧义。任何修法都是在窗与窗之间挪毫秒,换一批新歧义。

而它的独特价值——「批量摘录后合成一块」——在 note-first 下有完整替代:
连续双击捕捉(见上表「连续摘录」行,零额外成本),回主窗多选合并
(MergeToolbar 已有);且每段还能带各自的 note,来源比合成一大块更清楚。

**结论:整个收集面板(长按 ⌥ + 单击 ⌥ 缩放 + 暂存合并)删除。**
双击 ⌥ 成为唯一手势,一个手势一个结果。官网从未宣传过收集面板,无对外文案孤儿。

### 1.4 修正三:自动消失的判定改为「框里没字才自动关」

现在「展开批注 = 暂停自动消失」;note-first 下 toast 永远是展开态,照旧就永远
不自动关。改为:**框里空且无悬停 → 8 秒自动关;打了字 → 不自动关**(Enter/点外部收尾)。

### 🚨 阻断级发现(2026-07-31 晚):从别的 app 捕捉时,「直接打字」在 macOS 上做不到

**这是本设计的前提被推翻,必须 Ocean 拍板。**

实测(隔离构建 + 可绑定捕捉快捷键,来源 app = TextEdit):

| 步骤 | 结果 |
|---|---|
| 在 TextEdit 里按捕捉键 | 浮窗正常弹出,批注框和 placeholder 都在 ✅ |
| 紧接着打字 | **字全进了 TextEdit**,批注是 NULL ❌ |
| 触发前后的前台 app | 始终是 TextEdit —— Spool 从未被激活 |

根因是 macOS 的两条硬约束,叠在一起:
1. **键盘事件只发给「活跃应用」**。浮窗即使是自己 app 内的 key window,只要 Spool 不是
   活跃应用,键盘就不会来。
2. **后台 app 不能自行抢占激活**。`win.set_focus()` 无效;显式调
   `[NSApp activateIgnoringOtherApps:YES]` 同样无效(现代 macOS 的协作式激活)。

试过的路也记下来,别重走:把浮窗运行时改类成 **非激活 NSPanel**(子类覆写
`canBecomeKeyWindow`)确实拿到了 `isKeyWindow=true` 且不抢激活,**但键盘照样不来** ——
印证了约束 1。该实验已回退,只留结论。

**目前实际能做到的是「点一下再打字」**:点批注框 → Spool 被激活(用户点击是合法的激活来源)
→ 光标进框 → 打字、Enter 保存,全部正常(已实测,来源 app 内容未被污染)。

**Ocean 2026-07-31 拍板:走 C,实在不行再回 A。**(B 不考虑)

- **C. 继续攻(已选)**,两条路,先试不花钱的那条:

    异步,轮到激活时授权窗口早过期。要试就得在**收到热键/tap 的那一刻、在 Rust 侧同步**
    激活,再让后续流程走原路;双击 ⌥ 同理(`double_tap.rs` 回调里)。

### 3.5 闪窗 bug 定案(2026-08-01):**两个独立成因,ecd71a9 一个都没打中**

Ocean 反馈 `ecd71a9` 没修好(点 ✕ 和 Esc 都还闪)。这次不靠推理了 —— 用
`CGWindowListCopyWindowInfo`(前→后顺序)每 20ms 采一次 z-order,配可绑定捕捉快捷键
从 TextEdit 触发,把两个成因分别拍死。**测法本身值得留着**:z-order 是客观事实,
比「看着像闪了一下」可靠得多,探针源码在会话 scratchpad,十几行 C。

**成因一:`set_focus()` 埋下的「延迟激活」** —— 这才是主因,而且比闪窗更严重。

| 时刻 | 实测 |
|---|---|
| t=0 | TextEdit 在前,Spool 主窗在它后面一层 |
| t=+1.1s 浮窗弹出 | **前台仍是 TextEdit**,主窗没动 —— 说明 `activateIgnoringOtherApps` 当场没生效 |
| t=+9.2s 浮窗消失 | **同一帧**里主窗窜到最前,`frontmost=spool`,而且**再也不还回去** |

`win.set_focus()` = `makeKeyAndOrderFront` + `activateIgnoringOtherApps:YES`。后半句从后台
app 调用时,现代 macOS 不是「忽略」而是**挂起**:等 Spool 下次有一个够格当 key 的窗口时
再兑现 —— 那一刻正好是浮窗被 `orderOut` 的瞬间。所以主窗是在**关闭时**窜上来的,
`ecd71a9` 调整「先激活来源 app 再隐藏」的顺序,最多改变它掉回去的快慢,不可能拦住。

而**没人碰的那次捕捉(8 秒自动消失)根本走不到归还分支**,于是 Spool 就这么把前台端走了 ——
用户过一会儿回来打字,字进的是 Spool。这条比闪窗更值得修。

**修法**:删掉 `set_focus()`。`win.show()` 本身就是 `makeKeyAndOrderFront`(tao 的
`set_visible(true)`),Spool 已在前台时该做的事一件不少;`set_focus()` 多出来的只有那句
有害的激活请求。**不求激活,就没有挂起的激活。**

**成因二:点浮窗 = 激活 Spool,而 macOS 按 app 分层** —— 这条才是 Ocean 说的「点 ✕ 会闪」。

浮窗是后台 app 的普通窗口,点它(✕ / 图钉 / 批注框)必然激活 Spool;macOS 一激活就把该 app
**所有可见窗口**整体抬到别人上面,主窗因此在**点击那一刻**窜前,直到关闭时归还来源 app 才掉回去。
实测 z-order 就在点击那一帧翻转。

**修法**:浮窗在的整段时间,把主窗压到 `BelowNormalWindowLevel`(比普通层低一级)。
低一级的窗口在窗口服务器眼里永远盖不住任何 app 的普通窗口,于是激活也好、key 窗口提升也好,
都抬不动它。用 Tauri 现成的 `set_always_on_bottom`,**不引依赖、不写 objc**。
只在「有来源 app 可归还」时压(等价于「用户人在别的 app」);人在 Spool 里时压了会把
他正在看的窗口塞到最底下。恢复必须**等来源 app 激活之后**再做 —— `setLevel` 会在新层里
重排一次,Spool 还占着前台时重排就等于抬起来。

**顺带修的第三个坑:归还焦点基本没生效过。** `useCapture` 只给前台 app 查询
`FRONTMOST_HOT_PATH_MS = 80ms`,而这查询要跑一趟 osascript,几乎必然超时 →
`prev_source_app` 为 null → 栈空 → 什么都不还。现在 Rust 侧兜底读
`FRONTMOST_CACHE`(2s 内的结果,不新起 osascript,热路径零成本)。
另外 `had_focus` 这个闸门也删了:note-first 之后浮窗从别的 app 弹出时**从来就不是 key**,
这个闸门等于把归还整条路封死。改用「点外部消失时清栈」来表达同一个意图 ——
那一下点击是用户自己选了新的前台 app,不该把他拽回去。

**验证矩阵(隔离构建 `com.oceanjin.spool.verify`,来源 app = TextEdit,已拆干净)**

| 场景 | 修前 | 修后 |
|---|---|---|
| 弹出后不碰,8 秒自动消失 | 主窗窜前 + **前台被 Spool 端走不还** | ✅ 主窗不动,前台始终 TextEdit |
| 点 ✕ 关闭 | 点击那刻主窗窜前 | ✅ 全程主窗压在 -1 层,关闭后回原位,前台回 TextEdit |
| 主窗层级 | 恒 0 | 浮窗在时 -1,消失后恢复 0 |

⚠️ **隔离构建验不了的一条**:新 identifier 没有 System Events 的自动化授权,
`get_foreground_app()` 恒返回 None(捕捉的 `source` 列也全是 NULL),所以「有来源 app」
那条分支是用临时环境变量喂进去验的,归还用的 osascript 本身实测 exit 0。
正式版有授权,这条路径天然可用。

⚠️ **另一条本次没能证实的**:Spool **已在前台**时批注框到底有没有拿到光标。合成键入
(`CGEventKeyboardSetUnicodeString`)打完 + Enter,批注仍是 NULL —— 但**删 `set_focus()`
前后一模一样**(用环境变量 A/B 过),所以不是本次改动引入的。
截图看批注框也没有 focus 描边。§4.3 记的「双击后光标在批注框(Spool 已在前台时)✅」
这条**值得 Ocean 用真手指复核一次**;若确实没光标,note-first 的前提比 §3 记的还要弱。

### 3.6 「直接打字」定案(2026-08-01):AppKit 那条路是死的,辅助功能那条是活的

**Ocean 2026-08-01 实测把两条不确定都结了:**

1. §3.5 存疑的那条 —— **Spool 已在前台时批注框确实拿到光标**,不点也能打字。
   §4.3(HANDOFF)记的 ✅ 是准的,上一版验不出来只是因为 HID tap 看不见合成键入。
   → **note-first 的前提没有比 §3 记的更弱。**
2. 闪窗三条手测(不碰它 / 点 ✕ / 写字后 Esc·Enter)**全部通过**,`a696d4a` 结案。

于是问题收敛成**唯一一条**:Spool 不在前台时,键盘不进浮窗。

**为什么不走 C-1 原样(热键回调里同步 `NSApp.activate`)。**
§3.5 测出激活请求不是「过期作废」而是**挂起**,所以「授权窗口过期」本来就不是失败原因,
把调用提前到 Rust 侧同步执行改变不了结果 —— 只会把闪窗成因一原样请回来。
更何况真正的触发路径是双击 ⌥,走的是 CGEventTap **观测**,事件根本没投递给 Spool,
「刚收到用户按键的 app」这个赌注在这条路径上最站不住。**所以不求激活。**

**改走辅助功能(`a3cfba2`)。** 给应用元素设 `AXFrontmost`,即
`System Events` 的 `set frontmost of process` 底下那个调用:**立即生效、不排队**,
而且对任何 pid 都能用,所以同一个调用负责两个方向 —— 弹出时把前台拿过来,
关闭时按 pid 还回去。授权不用新加(抑制型 tap 本来就要辅助功能),依赖不用新加
(externs 直接声明在已链接的 ApplicationServices 上,和 `AXIsProcessTrusted` 一样)。

落地要点:

- **激活在 `win.show()` 之后**。先激活的话,前台落到 Spool 那一刻拿到 key 的是主窗。
- **只在「用户人在别的 app」时激活** —— 与压低主窗同一个判据(`ax_source_app_pid()`
  返回 None 表示要么没授权、要么 Spool 本来就在前台)。Spool 已在前台的那条路径
  **一行都没变**,Ocean 已验过它是好的。
- **按 pid 归还比按名字稳**:`AXTitle` 与 LaunchServices 名字可能不一致(VS Code 的
  AXTitle 是 `Code`),而且不再有 `tell application "Spool"` 拉起第二个实例的风险。
  按名字那条路留着,只在没有辅助功能授权时走。
- 归还是**同步**的,所以来源 app 先活过来、浮窗后 `orderOut` —— 这正是 §3.5 成因二
  要求的顺序,而且不再依赖 osascript 起子进程。

**⚠️ 行为变化,需要 Ocean 在验收时对表:**浮窗存续的那几秒(最长 8 秒)**前台是 Spool**,
关闭后才还回去。这跟 Ocean 2026-08-01 那轮「前台该一直是你原来那个 app」的判据是
**相反**的 —— 那轮测的是不激活的版本。**要零摩擦打字就必须拿前台**,这是 C 路线的定义,
不是回归。真正的验收线改成:**关闭之后前台必须回到来源 app**(四条关闭路径都要回)。

### 3.7 实机验收(Ocean 2026-08-01 真手指,装机版 `a3cfba2`)

**`AXFrontmost` 设在自己 pid 上不会被拒 —— 结案。** 七次 TRIGGER,stderr 零条
`AXFrontmost refused`。**自激活这条路在 macOS 上是通的**,note-first 的最后一块补齐了。

| 测的 | 结果 |
|---|---|
| 弹出后**不点鼠标直接打字** | **✅ 字进批注框** —— 本设计的目的达成 |
| 主窗有没有跳到最前 | **✅ 四条路径一次都没有** |
| Enter / Esc / 点 ✕ / 8 秒自走,关掉后前台 | **✅ 四条都回到来源 app** |

**❗新暴露的现象:浮窗存续期间主窗沉到最底下。**
Ocean 的窗口栈是(后→前)`vscode - spool - texteditor`,双击 ⌥ 之后变成
`spool - vscode - texteditor`,关掉浮窗又变回来。

**这是 `a696d4a` 的 `park_main_window` 干的,不是本次改动引入的** —— 上一轮没看见,
是因为当时栈里只有 TextEdit 和 Spool,主窗本来就在最底下,沉了也看不出来;
栈里夹一个 VS Code 就现形了。

**这个沉底去不掉,除非放弃「主窗永不跳前」。** macOS 按 app 整体分层:Spool 一旦是活跃应用,
它所有可见窗口就整体抬到别人上面。唯一能让主窗不被抬起来的公开手段就是把它压到
**低于普通层**(`set_always_on_bottom`),而低于普通层 = 沉到所有普通窗口下面 ——
「压住不让它升」和「沉到最底」在 macOS 上是同一件事,没有「留在原位不动」这个档位。
(要真做到原位不动,只有把浮窗挪进一个**独立的辅助 app**,让被激活的是那个没有其他窗口的
进程 —— 那是另起一个 bundle 的工程量,不在本设计范围内。)

**⚠️ 关键推论:砍掉「直接打字」并不能消掉沉底。** 压低是为**点击**准备的 ——
用户点浮窗的 ✕ / 图钉 / 批注框,同样会激活 Spool、同样会把主窗抬起来(那正是 Ocean
最早报的「点 ✕ 会闪」)。所以只要浮窗还能点,压低就还得在,沉底就还在。
**反过来说:压低既然无论如何都要留,「直接打字」就是零额外代价的。**
