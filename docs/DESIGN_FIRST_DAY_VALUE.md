## 0. 一句话定位

## 2. 四件要做的

### 2.1 捕捉数统计,分出 MCP 那一份

**要显示的**:一共攒了多少条,其中**你自己捕的**多少、**AI 通过 MCP 写回的**多少。

**为什么要分**:这两件事在 Spool 里是两种不同的行为 —— 一个是用户在别处读到东西按了
双击 ⌥,一个是别的 AI 客户端替他写回来的。混成一个数,用户看不出自己到底在用哪一半;
而 MCP 那一半正好是「Spool 值不值」最难自己感知的部分。

⚠️ **「什么算一条捕捉」只有一处定义,别再写第二份**:`lib/db/blocks.ts` 的
`listCapturesSince` —— **有 source、不是 MCP、不是教程种子**。MCP 那一份用同一个文件里
现成的 `countMcpBlocks()`(它走 `MCP_SOURCE_PREDICATE`)。
这两个谓词各自只有一处出处,**在 SQL 里再抄一遍就是那两条注释警告的漂移**。

⚠️ **教程种子必须继续排除**。不排除的话新装用户第一眼看到的是「你已经攒了 6 条」——
而他一条都还没捕。教程过滤是在 TS 里做的(`TUTORIAL_SOURCES` 是双语的),不在 SQL 里。

### 2.2 个人 note 字数统计

**要显示的**:用户**自己写的字**一共多少字。

**为什么**:Ocean 明说了目的 —— **鼓励用户多写自己的 notes**。这是四件里唯一一件目的是
「改变行为」而不是「呈现事实」的。

⚠️ **「自己写的」要排除 AI 写的**。`blocks.annotation_by` 从 v14 起记着是 `'user'` 还是
`'ai'`,而且 **NULL 不等于用户** —— NULL 是「不知道」(v14 之前的行),要走
`annotationIsAi()` 那条回退,不能直接判 `!= 'ai'`。这条规矩在
`lib/blocks/annotationAuthor.ts` 和 schema.sql 的 `annotation_by` 注释里,两边都写着。

✅ **要不要把「用户手打的块正文」也算进去,2026-08-10 晚 Ocean 定了:走乙**(§4 第 1 条)。
下面这张取舍表留着 —— 它是当初为什么这么问的记录:

| 口径 | 数出来是什么 | 代价 |
|---|---|---|
| 甲:只算 annotation(批注) | 「我对读到的东西说了什么」 | 用户在 composer 里直接手写的块一个字都不算 |
| 乙:annotation + 无 source 的块正文 | 「我自己写的所有字」 | 无 source = 用户手打,这条推断在 §2.1 里已经用着了,一致 |
| 丙:全部块正文 + 批注 | 「库里一共多少字」 | 数的是别人的字,和「鼓励你多写」正好相反 |

✅ **他选了乙。** 丙明显违背他说的目的;甲和乙的差别他自己最清楚(他到底是在批注里写得多,
还是直接手打得多)—— **他选乙,意味着他手打的块也要算进「我写的字」。**
⚠️ **落地时「无 source = 用户手打」这条推断要和 §2.1 用同一处判断,别各写一份。**

### 2.3 ⭐ 线轴小组件(这一稿的主件)

**形态**:一个线轴(spool)的图形。**累积捕捉数**从 0 涨到 **100**,线轴从**空**到
**被线缠满**;满 100 时提醒用户「已经攒满一轴」,然后**清空,重新开始缠**。
**中间状态要多做几个**,不能只有空 / 满两档。

这是产品名字第一次变成界面上会动的东西 —— `spool` 本来就是「线轴」。

**要定的事(建议,待 Ocean 拍板)**:

- ✅ **几档中间状态:9 档已拍板**(空 + 8 档,每 12.5 条进一格),这样平均每捕两三条就
  看得见一次变化。档太少(比如 4 档)时用户捕了十几条画面纹丝不动,那正是这个组件要治的病。
  ⚠️⚠️ **2026-08-10 装机后 Ocean 改成 20 档**(原话「线轴的状态增加,变成 20 个」)——
  一格 = **5 条**。**这一改把画法也换掉了**,见 §7。
- **怎么画**:建议 **inline SVG,不用图片** —— 三个窗口入口共用一套 CSS token,
  暗色模式要跟着变,而且线轴要能在侧边栏那个尺寸下看清。⚠️ 位图在 Retina 上还要出两套。
- **动画**:进一格时线绕上去一小段。⚠️ **别做常驻动画** —— 侧边栏是常显区域,
  一个一直在动的东西会持续偷注意力,这跟 §2.5 的安静原则是硬冲突。
- ✅ **满轴那一下的提醒:就地一行 + 线轴闪一下,两个都要**(2026-08-10 拍板)。
  ⚠️ **不弹窗**。这一版所有「提醒」都是就地挂一行(日期提醒条、捕捉满三条的提示都是这么做的),
  弹窗会是全 app 唯一的一个。
  ⚠️ **闪那一下是一次性的,不是常驻动画** —— 和上面那条不冲突,别把它做成循环。

⚠️ **「累积捕捉数」是全库历史总数,不是今天的数** —— 和 §2.1 的第一个数字是同一个口径,
**但现在没有便宜的算法**:`countCaptures()` 是 `listCapturesSince(0).length`,
**它会把全库每一行捕捉都读成对象再数长度**。那是给「捕捉满三条」那个一次性提示写的
(注释里明说了「库小到只有一把行」)。**线轴是常显的,必须换成一条真正的
`SELECT COUNT(*)`**,谓词仍然复用 §2.1 那一处定义。

### 2.4 总线轴数

**要显示的**:一共缠满过几轴。

**为什么**:Ocean 说的是**成就感** —— 线轴清空之后,那 100 条不能就这么消失,
否则每满一次都是「回到原点」,和「攒东西」正好相反。

⚠️ **这个数不该存**,应该**从累积捕捉数算出来**:`满轴数 = floor(累积捕捉 / 100)`、
`当前进度 = 累积捕捉 % 100`。存一个「已满轴数」的计数器意味着**多一处可以和真实块数
对不上的状态**,而且用户删块之后它就成了假的。算出来的永远对得上。

### 7.1 ⭐⭐ 20 档逼着换了画法(这一条最值得记)

**原来一格 = 线缠粗一点**(绕线半径从 4.5px 长到 14px)。**分成 20 格之后,一格是
9.5 ÷ 20 ≈ 0.5 个 CSS 像素** —— 在 2 倍屏上就是 1 个物理像素,**等于看不见**。
「加档位」本来是为了让用户更常看见变化,照原画法加满 20 档反而**每一格都看不见**。

**换成:一格 = 一整圈线。** 轴上 20 个绕线位,每 5 条捕捉多一道线,**新增的那一圈从轴里
长出来**(`scaleY` 0 → 1)。一格一整圈,肉眼绝不会漏。

⚠️ **顺带的好处**:20 圈线**需要横向的地方** —— 40px 的方块里 20 圈只能隔 2px,
所以「排版不平衡」和「20 档」这两条**是同一个解**:线轴占满整张卡的宽度。

### 7.2 排版长什么样

```
▐║║║║║║░░░░░░░░░░░░░░░░▌   ← 线轴,占满卡宽,20 格
还差 66 条缠满              ← 满轴时变成「这一轴缠满了」+ 线轴闪一下
你攒了 34 条    我写了 2,973 字
AI 写回 32 条   已缠满 0 轴
────────────────────────
今天读了 N 条        打个包试试 →
```

⚠️ **四个格子永远都在,0 也显示** —— 谁是 0 谁就塌一块下去的话,就又变成他说的

## 9. ✅ 第三轮:满轴画成一排小线轴 + 文案按他的话改(2026-08-10 深夜)

**问他「面板还能加点什么有趣但有点用的」,他挑了一件,顺手把文案全部改了。**

### 9.1 先摆事实(问之前先量了他的库)

| | |
|---|---|
| 库建了 **11 天**,91 块 | **只有 2 天**真的在捕东西 |
| 91 块里 **43 条有他写的批注** | 剩下 48 条一个字都没有 |
| 超过 30 天的块 | **0 条** |

⭐ **这组数字本身就是答案的一半**:用法是爆发式的(11 天里 2 天),
**而当时那个面板只有捕东西的那天才会变** —— 剩下 9 天打开 app,它和昨天一模一样。
所以筛选标准是:**在什么都没干的那天,它有没有话说。**

**给了三个选项**(翻一条旧块出来 / 这周有几天在攒 / 满轴画成小线轴),
**他选了小线轴**,另外三条不做。⚠️ **「翻一条旧块」那条他没选,别自己补上。**

### 9.2 他同时提的文案要求(原话)

> 今天读了 XXX(写在面板里面,去掉打包的快捷键),你攒的替换成你捕捉了,AI 写回变成 AI 写入,
> 我写的变成:我一共写了;然后文字和数字放一起,不能拆分到距离这么远。

| 改成 | |
|---|---|
| `你攒的 … 34 条` | **`你捕捉了 34 条`** |
| `AI 写回 … 32 条` | **`AI 写入 32 条`** |
| `我写的 … 2,973 字` | **`我一共写了 2,973 字`** |
| 「今天读了 N 条」在卡底下自成一段(带分隔线 + 「打个包试试 →」) | **进面板里,和别的数字并排;打包那个按钮删掉** |
| 标签贴左、数字贴右 | **贴在一起,当成一句话** |

### 9.3 ⭐⭐ 三轮排版,三条互相打架的要求,最后怎么同时满足的

| 第几轮 | 他说什么 | 我做了什么 |
|---|---|---|
| 一 | 「右边什么都没有,而左边很紧凑」 | 以为要更多地方 → 线轴占满一整行 ❌ |
| 二 | 「太大个了,回到上一版本」 | 小线轴 + **标签贴左、数字贴右** ❌ |
| 三 | 「文字和数字放一起,不能拆分到距离这么远」 | ✅ **一串完整短语,自动折行** |

**答案是「短语流」**:每个短语自己是完整的(`你捕捉了 34 条`),
它们**并排排到放不下为止,放不下的整条掉到下一行** ——
**既不会把标签和数字拆开,也不会让右边空着,而且侧边栏拖窄时是换行不是截字。**
⚠️ **别再改成固定几列的 grid** —— 固定列宽正是「拖窄了就截字」的来源。

### 9.4 小线轴那一排

- **满几轴画几个**(`FilledSpools`,16×12,和大线轴同一套零件:两块端板 + 缠满的线)。
- ⚠️ **超过 5 个就画一个 + `× N`** —— 再多这排比线轴本身还长,面板就不是面板了。
  ⚠️⚠️ **这个 5 已经作废,以 §10.3 为准**:2026-08-11 这排挪到了「还差 N 条缠满」后面,
  上限变成**量出来的 4**(那一行必须保持一行)。
- ⚠️ **0 轴时整个不画**:空货架是个洞,不是一条信息(和别的「数了个 0」不一样,
  那些是数字,这个是图)。

### 9.5 ⚠️ 量的时候踩到的两个坑(下次别再踩)

1. **`zoom:3` 会把 SVG 里 `transform: translateY(18px)` 那个补偿也乘 3** ——
   线轴的线整段跑到轴下面去了,**看起来像个真 bug,其实是量法的 bug**。
   ⭐ **要放大看细节,就把 viewBox 的尺寸调大,别用 CSS `zoom`。**
2. **预览页是手抄的 markup,它自己会有 bug** —— 这次 python 里一处字符串拼接写错,
   小线轴少画了两个,**差点当成组件的 bug 去改组件**。
   ⭐ **预览页和组件不一致时,先怀疑预览页。**
