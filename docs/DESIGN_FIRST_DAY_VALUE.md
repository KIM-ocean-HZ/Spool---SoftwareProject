## 0. 一句话定位

**一期那张卡答的是「今天读了什么」—— Ocean 看完的判断是:内容本身没价值。
二期把它从「列出你读的东西」改成「显示你攒了多少」:三个计数 + 一个线轴。**

差别不是显示什么,是**它替用户回答哪个问题**:

| | 一期(已落地) | 二期(本稿) |
|---|---|---|
| 卡在答 | 我今天读了哪三条? | 我到现在攒了多少? |
| 内容 | 前三条捕捉的正文预览 | 数字 + 一个会变的线轴 |
| 用户看完想干嘛 | (点进去重读一遍自己刚读过的东西) | 再捕一条 / 多写两句自己的 |

⚠️ **一期那三条正文预览要撤掉**,不是在旁边加东西。Ocean 原话第一句就是
「不添加具体内容」。

## 1. Ocean 的原话(2026-08-10)

> 首日价值面板内容没什么价值,不添加具体内容,添加一下信息:
> 1. 捕捉数统,包括 MCP 数量统计;
> 2. 个人 take note 字数统计(鼓励用户多写个人的 notes);
> 3. 加一个 spool 线轴的小组件,记录用户的累积捕捉数量,线轴从空到被线缠满做一个动态变化,
>    积累 100 条捕捉线轴被缠满,然后提醒用户已经累积 100 条,再清空,中间状态多做几个。
> 4. 加一个总线轴数统计,让用户有记录的成就感。

## 2. 四件要做的

### 2.1 捕捉数统计,分出 MCP 那一份

**要显示的**:一共攒了多少条,其中**你自己捕的**多少、**AI 通过 MCP 写回的**多少。

**为什么要分**:这两件事在 Spool 里是两种不同的行为 —— 一个是用户在别处读到东西按了
双击 ⌥,一个是别的 AI 客户端替他写回来的。混成一个数,用户看不出自己到底在用哪一半;
而 MCP 那一半正好是「Spool 值不值」最难自己感知的部分。

⚠️ **「什么算一条捕捉」只有一处定义,别再写第二份**:`lib/db/blocks.ts` 的
`listCapturesSince` —— **有 source、不是 MCP、不是教程种子**。MCP 那一份用同一个文件里
现成的 `countMcpBlocks()`(它走 `MCP_SOURCE_PREDICATE`)。
这两个谓词各自只有一处出处,**在 SQL 里再抄一遍就是那两条注释警告的漂移**。

⚠️ **教程种子必须继续排除**。不排除的话新装用户第一眼看到的是「你已经攒了 6 条」——
而他一条都还没捕。教程过滤是在 TS 里做的(`TUTORIAL_SOURCES` 是双语的),不在 SQL 里。

### 2.2 个人 note 字数统计

**要显示的**:用户**自己写的字**一共多少字。

**为什么**:Ocean 明说了目的 —— **鼓励用户多写自己的 notes**。这是四件里唯一一件目的是
「改变行为」而不是「呈现事实」的。

⚠️ **「自己写的」要排除 AI 写的**。`blocks.annotation_by` 从 v14 起记着是 `'user'` 还是
`'ai'`,而且 **NULL 不等于用户** —— NULL 是「不知道」(v14 之前的行),要走
`annotationIsAi()` 那条回退,不能直接判 `!= 'ai'`。这条规矩在
`lib/blocks/annotationAuthor.ts` 和 schema.sql 的 `annotation_by` 注释里,两边都写着。

✅ **要不要把「用户手打的块正文」也算进去,2026-08-10 晚 Ocean 定了:走乙**(§4 第 1 条)。
下面这张取舍表留着 —— 它是当初为什么这么问的记录:

| 口径 | 数出来是什么 | 代价 |
|---|---|---|
| 甲:只算 annotation(批注) | 「我对读到的东西说了什么」 | 用户在 composer 里直接手写的块一个字都不算 |
| 乙:annotation + 无 source 的块正文 | 「我自己写的所有字」 | 无 source = 用户手打,这条推断在 §2.1 里已经用着了,一致 |
| 丙:全部块正文 + 批注 | 「库里一共多少字」 | 数的是别人的字,和「鼓励你多写」正好相反 |

✅ **他选了乙。** 丙明显违背他说的目的;甲和乙的差别他自己最清楚(他到底是在批注里写得多,
还是直接手打得多)—— **他选乙,意味着他手打的块也要算进「我写的字」。**
⚠️ **落地时「无 source = 用户手打」这条推断要和 §2.1 用同一处判断,别各写一份。**

### 2.3 ⭐ 线轴小组件(这一稿的主件)

**形态**:一个线轴(spool)的图形。**累积捕捉数**从 0 涨到 **100**,线轴从**空**到
**被线缠满**;满 100 时提醒用户「已经攒满一轴」,然后**清空,重新开始缠**。
**中间状态要多做几个**,不能只有空 / 满两档。

这是产品名字第一次变成界面上会动的东西 —— `spool` 本来就是「线轴」。

**要定的事(建议,待 Ocean 拍板)**:

- ✅ **几档中间状态:9 档已拍板**(空 + 8 档,每 12.5 条进一格),这样平均每捕两三条就
  看得见一次变化。档太少(比如 4 档)时用户捕了十几条画面纹丝不动,那正是这个组件要治的病。
- **怎么画**:建议 **inline SVG,不用图片** —— 三个窗口入口共用一套 CSS token,
  暗色模式要跟着变,而且线轴要能在侧边栏那个尺寸下看清。⚠️ 位图在 Retina 上还要出两套。
- **动画**:进一格时线绕上去一小段。⚠️ **别做常驻动画** —— 侧边栏是常显区域,
  一个一直在动的东西会持续偷注意力,这跟 §2.5 的安静原则是硬冲突。
- ✅ **满轴那一下的提醒:就地一行 + 线轴闪一下,两个都要**(2026-08-10 拍板)。
  ⚠️ **不弹窗**。这一版所有「提醒」都是就地挂一行(日期提醒条、捕捉满三条的提示都是这么做的),
  弹窗会是全 app 唯一的一个。
  ⚠️ **闪那一下是一次性的,不是常驻动画** —— 和上面那条不冲突,别把它做成循环。

⚠️ **「累积捕捉数」是全库历史总数,不是今天的数** —— 和 §2.1 的第一个数字是同一个口径,
**但现在没有便宜的算法**:`countCaptures()` 是 `listCapturesSince(0).length`,
**它会把全库每一行捕捉都读成对象再数长度**。那是给「捕捉满三条」那个一次性提示写的
(注释里明说了「库小到只有一把行」)。**线轴是常显的,必须换成一条真正的
`SELECT COUNT(*)`**,谓词仍然复用 §2.1 那一处定义。

### 2.4 总线轴数

**要显示的**:一共缠满过几轴。

**为什么**:Ocean 说的是**成就感** —— 线轴清空之后,那 100 条不能就这么消失,
否则每满一次都是「回到原点」,和「攒东西」正好相反。

⚠️ **这个数不该存**,应该**从累积捕捉数算出来**:`满轴数 = floor(累积捕捉 / 100)`、
`当前进度 = 累积捕捉 % 100`。存一个「已满轴数」的计数器意味着**多一处可以和真实块数
对不上的状态**,而且用户删块之后它就成了假的。算出来的永远对得上。

## 3. 摆在哪、什么时候出现

⚠️ **一期那张卡「只在当天有捕捉时才出现」**(没捕捉整个不渲染)。二期这条规矩**得重想**:

- 「今天读了 N 条」当天没捕就该消失,这是对的。
- **但线轴不该消失** —— 一个只在你刚干过活时才出现的进度条,恰好在你需要被推一把的
  那天不见了。

✅ **2026-08-10 晚 Ocean 拍板:常显** —— 当天没捕捉时不显示「今天」那一行,
线轴和累计数照常在。
⚠️ **他是在读到代价之后选的**:这会改变每一个用户每一天的侧边栏长相,
而一期刚刚才把「大多数日子侧边栏和以前一模一样」当成设计的一部分。**这条是明确推翻它,
不是没注意到。** 落地时不要再折中回「攒够几条才出现」。

⚠️ **第 3 条落地时的具体形状**(他选的是「常显」,这两句是它的推论):
- **「今天读了 N 条」那一行**:当天没捕捉就不渲染 —— 这一半和一期一样。
- **线轴 + 累计数 + 满轴数**:**永远在**,库是空的也在(那时线轴是空轴)。
  ⚠️ **新装用户第一眼就会看到一个空线轴** —— 那正是它该在的时候,别给它加「攒够几条才出现」
  的门槛,加了就又变回一期那个「需要被推一把的那天它不见了」的毛病。

## 5. 落地时的硬提醒(踩过的坑,别重踩)

1. ⚠️ **纯读,零写。** 一期定的规矩是「日卡只是界面,不写库」(Ocean 拍板,代价是卡明天
   就没了)。二期的四个数**全部是查询结果**,同样一个字都不存 —— §2.4 那条「满轴数算出来
   不存下来」是同一条规矩的延伸。
2. ⚠️ **跨午夜**:一期靠 `window focus` 重查、`startOfToday()` 每次现算。二期加进来的三个
   数是全库累计,不受午夜影响,**但「今天」那一行仍然受**,那段逻辑别删。
3. ⚠️ **本地时区 vs UTC 别混**:「今天」是**用户的本地日**(`startOfToday()`);
   块的 `retrieved_at` / `recheck_after` 是 **UTC 日**。HANDOFF §6.3-13。
4. ⚠️ **文案双侧**:界面文案走 `t!`/`ts!`,中文那一半在前(硬规则 12)。
   跑 `node scripts/i18n-check.mjs`。
5. ⚠️ **截图**:侧边栏这一屏 HANDOFF §5.1 已经标了「拍之前先当场捕两三条」。
   二期做完之后**这条要改** —— 线轴常显的话就不用先捕了,但**线轴上有多少线是会入镜的**,
   拍之前想清楚要拍哪个状态。
6. ⚠️ **schema 不用动。** 四个数全部从现有列查得出来(`source`、`annotation`、
   `annotation_by`、`created_at`)。**如果你发现自己想加列了,先回来看 §2.4。**
