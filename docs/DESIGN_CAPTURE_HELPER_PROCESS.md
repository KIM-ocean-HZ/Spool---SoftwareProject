# 设计稿:把捕捉浮窗挪进独立进程(待 Ocean 批,尚未动手)

> 前置:`docs/DESIGN_CAPTURE_NOTE_FIRST.md` §3.6 / §3.7。
> 本文只解决一件事:**捕捉浮窗弹出时,Spool 主窗一动不动。**

---

## 1. 为什么要做

Ocean 2026-08-01 定的优先级:**主窗永远不跳到最前面 > note-first 直接打字**。

现在两条都做到了,但代价是**主窗在浮窗存续期间沉到最底下**(Ocean 实测:窗口栈
`vscode - spool - texteditor` 变成 `spool - vscode - texteditor`,关掉浮窗才回原位)。

这个沉底在**当前架构下去不掉**。macOS 按 app 整体分层:Spool 一旦是活跃应用,它所有可见
窗口就一起抬到别人上面。唯一能拦住的公开手段是把主窗压到低于普通层
(`set_always_on_bottom`),而「低于普通层」= 低于所有普通窗口。
**「不让它升」和「沉到最底」是同一个动作,系统没给「留在原位」这一档。**

而且**砍掉直接打字也消不掉沉底** —— 压低是为**点击**准备的:点浮窗的 ✕ / 图钉 / 批注框
一样会激活 Spool、一样会抬主窗(那就是最早报的「点 ✕ 会闪」)。只要浮窗能点,压低就得留。

**Ocean 2026-08-01 选:上独立辅助 app。**

---

## 2. 承重假设:已验,成立

**假设**:激活是按**进程**算,不是按 **app bundle** 算。若按 bundle 算,方案当场作废。

**验法**(可复现,探针源码见 §7):起三个 TextEdit 进程,让 VS Code 的窗口夹在中间,
激活其中一个,用 `CGWindowListCopyWindowInfo` 读 z-order。

```
 1  pid=92441  TextEdit   ← 被激活的进程,升到最前
 4  pid=20447  Code       ← 没被挤下去
 5  pid=91656  TextEdit   ← 同 bundle 的另外两个进程,纹丝不动
 7  pid=73440  TextEdit
```

**结论:按进程算。** 让浮窗住在另一个进程里,主窗就不会被连坐。

---

## 3. 方案

### 3.1 进程形态:同一个二进制的第二个进程(**推荐 A1**)

| | **A1 `spool --overlay` 子进程** | A2 内嵌独立 `.app` bundle |
|---|---|---|
| 新 bundle id | 不用 | 要 |
| 打包 / 签名 / 公证 | 不变 | 每项多一条 |
| TCC 身份 | 不新增 | 可能新增一个 |
| 已有先例 | **有** —— `--mcp` 就是这么跑的 | 无 |
| 激活效果 | 一样(按进程算) | 一样 |

**A2 没有任何额外收益**,只多出对外风险面(多一个要签名公证的可执行体)。**选 A1。**

辅助进程由主进程在**启动时拉起并常驻** —— 不能等捕捉时才 fork,否则热路径上要付一次
webview 冷启动,`<200ms keypress → toast` 的 SLO 直接破。

### 3.2 谁来激活辅助进程

**主进程。** 它已经有辅助功能授权,`AXFrontmost` 对任何 pid 都能用
(§DESIGN_CAPTURE_NOTE_FIRST 3.6 已实现并验过)。所以:

- 弹出:主进程让辅助进程显示浮窗 → 主进程 `ax_set_frontmost(helper_pid)`。
- 关闭:主进程 `ax_set_frontmost(source_pid)`(已有代码,不用改)。

**辅助进程自己不需要任何 TCC 授权。** 这是 A1 相比 A2 的另一个好处。

### 3.3 🚨 红线:辅助进程绝不开 SQLite

`src/lib/db/client.ts` 的 `getDb()` 会跑 `migrateSchema` + `seedDefaults` ——
**那正是 2026-05-29 抹库事故的代码路径**。两个进程各自开库、各自跑迁移,是把那个事故的
前提原样重建一遍。

浮窗现在直接调了 5 处 DB:

| 调用 | 干什么 |
|---|---|
| `updateBlockAnnotation` | 保存批注 |
| `deleteBlock` | 丢弃 / undo |
| `togglePin` | 图钉 |
| `createBlock` | redo |
| `listWorkspaces` + `listAllThreads` | 「改投」下拉列表 |

**全部改成走 IPC 回主进程执行。** 辅助进程只管画和收键盘,一行 SQL 都不碰。

### 3.4 IPC

沿用 `--mcp` 已有的形态(stdin/stdout,一行一个 JSON),不引新依赖、不开网络端口。

- 主 → 辅:`show` / `notice` / `undo` / `source-update` / `dismiss`
- 辅 → 主:`hide` / `resize` / `disarm-dismiss` / 上面那 5 个 DB 操作

### 3.5 可以顺手删掉的

- `park_main_window` / `unpark_main_window` / `MAIN_WINDOW_PARKED` —— **整套压低机制作废**
- `tauri.conf.json` 里的 `overlay` 窗口声明
- 主进程里所有 `emit_to(OVERLAY_LABEL, …)`

**不动的**:双击 ⌥ 的 HID tap、点外部消失的 click watch、全局 ⌘Z —— 都留在主进程,
它们本来就只跟坐标和事件打交道,跨进程没影响。

## 4. 风险

| 风险 | 处置 |
|---|---|
| **双进程开库**(5/29 红线) | §3.3:辅助进程零 SQL。**这条是验收必查项。** |
| 辅助进程崩了 | 主进程监控并重启;重启期间捕捉降级成「只写库不弹窗」,不能静默丢内容 |
| 主进程崩了留下孤儿进程 | 辅助进程盯父进程存活,父死自退 |
| 内存 | 见 §4.1 实测,**净增约 +40~80MB**。A1/A2 都躲不掉,Ocean 要认 |
| 热路径变慢 | 常驻 + 一次 IPC,理论上不比现在慢;**但必须实测,不能靠推理** |
| 首次启动多一个进程 | 用户在活动监视器里会看到两个 Spool。可接受(Claude Desktop 也是一堆) |

### 4.1 内存代价:实测底数(2026-08-01,Ocean 本机)

| 进程 | 常驻 |
|---|---|
| Spool 主进程 | 120 MB |
| 主窗的 WebKit 内容进程 | 84 MB |
| **浮窗的 WebKit 内容进程** | **62 MB** |
| `spool --mcp`(同一个二进制,无 GUI) | 9.4 MB |

**关键**:浮窗的 webview **本来就跑在一个独立的 WebKit 进程里**(62MB),
挪进辅助进程只是换个宿主,这 62MB 不是新增的。
**真正新增的只有一个宿主进程** —— 带 AppKit 和一个窗口,比 `--mcp` 的 9.4MB 重、
比主进程的 120MB 轻,**粗估 +40~80MB**。动手前第一期就能量到准数。

## 5. 分期(每期独立提交、独立可验)

1. **辅助进程骨架**:`--overlay` 模式能起来、能显示一个空浮窗、父死自退。
   → 验:主进程杀掉,辅助进程 5 秒内消失。
2. **IPC 通路 + 显示浮窗**:主进程能让它显示真实捕捉内容,能激活它。
   → 验:z-order 探针确认主窗**一格没动**。
3. **DB 全部改走 IPC**:5 处调用改完,辅助进程零 SQL。
   → 验:`lsof` 确认只有主进程持有 `spool.db`。
4. **删掉压低机制 + 旧 overlay 窗口**,回归全套捕捉行为。
   → 验:note-first 五条 + 四条关闭路径,全部真手指重跑一遍。

粗估 **2~4 个工作窗口**。第 3 期是最容易出事的一期(碰库)。

## 7. z-order 探针(留用)

`CGWindowListCopyWindowInfo` 每次采样打印「普通层、在屏」窗口的前→后顺序,
只取 owner 名和 pid(不取窗口标题,所以**不需要屏幕录制授权**)。
源码存在 `scripts/zorder.c`,二十行 C:
`clang -o zorder scripts/zorder.c -framework ApplicationServices`。
**z-order 是客观事实,比「看着像闪了一下」可靠得多** —— 2026-07-31 那次判错成因,
就是因为只能靠肉眼和合成点击。本设计每一期的验收都用它。
