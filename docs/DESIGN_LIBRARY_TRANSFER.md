# 设计稿 — 库的导出与导入（2026-08-17 拍板）

> 来源：`archive/BACKLOG-2026-08-15.md` §1.1、交接 `archive/HANDOFF-2026-08-15.md` §11.8 第 1 条。
> **缺的从来不是迁移能力**（同一台机器上原地升级早就会自动迁移，取证在 backlog §1.1），
> 缺的是**换机器时用户可见的入口** —— 现在只有终端命令（`DB_BACKUP_AND_RECOVERY.md` §3）。
>
> ⚠️ **别和「打包整个工作区」混成一件事**（`DESIGN_WORKSPACE_PACK.md`）：
> 打包是**给 AI 读的快照**，是有损的（不是全部项目），但一个字都不改；
> 导出/导入是**换机器**，要的是能原样装回来。**一个丢了元数据无所谓，另一个丢了就是事故。**

---

## 0. ⭐⭐ 这一条压着整份设计：导入是**合并**，不是替换

我推荐的是「整个换掉」（导入前备份现在这份，然后原样顶掉）。**Ocean 否了**，原话：

> 「我选择合并，还有一个原因是：未来软件继续发展，如果想做出生态系统，
> 可以做打包文件互传到对方 spool 的操作，所以合并可以留后路。」

⭐ **他是对的，而且理由比我给的强**。两条：

1. **合并是替换的超集。** 换机器时新机器上的库是空的（只有播种的收件箱和教程），
   合并进一个空库，结果就是原样装回来 —— 「换机器」这个用例合并自己就覆盖了。
   反过来不成立：替换永远只能是替换。
2. **替换是不可逆的形状。** 它把「这台机器上现在的东西」放在一次操作的刀口上，
   而这个库正是 2026-05-29 丢过一次的那个东西。合并**只做加法**，
   和迁移那条红线（`DESIGN_FOLLOW_UP.md` §8.7：只做加法，绝不重建表）是同一个方向。

⚠️ **代价我当场说了，他知道**：两个库里各自独立建的同名项目，合并之后是**两个**项目
（它们本来就是两个 —— 见 §3.1 为什么这不是 bug）。

**本窗只做合并本身。库之间互传是他给未来留的路，不在这一版里。**

---

## 1. 导出：一个文件，`VACUUM INTO` 写出来

**导出的是整个库**：全部工作区 / 项目 / 信息块 / 跟进条目 / 附件记录，
包括软删除的行（`deleted_at` 不为空的）—— 换机器要的是原样，不是清理过的样子。

**做法不用发明**：`client.ts` 的 `backupDbBeforeMigration()` 早就在用 `VACUUM INTO`
写迁移前快照。它**通过 SQL 引擎复制**，所以 WAL 开着也是一致的，
而且**不需要任何 fs 权限**（写盘发生在 SQLite 里）。导出就是同一句话，换个目的地。

⚠️ **不要用文件拷贝代替它**：直接 copy `spool.db` 会漏掉还在 `-wal` 里没落盘的那部分。

**格式不需要自己发明版本兼容**：导出的就是一个当前 schema 版本的库文件，
导入端负责把它升上来（§2.2）—— 这条是 backlog §1.1 就写好的思路。

## 2. 导入：暂存 → 升级 → 合并

三步，**每一步都不碰用户选的那个文件**。

### 2.1 暂存（Rust 落盘，前端不摸字节）

`stage_import_db(source)` 把用户选的文件**拷进数据目录**成 `spool.import-staging.db`。

⭐ **为什么要先拷一份**：第 2 步会往这个库里写（跑迁移）。
**用户拿来的文件是他自己的东西，导入不该改它** —— 万一中途失败，他手上那份还得是好的。

分工照抄打包那条（`src-tauri/src/pack.rs` 的注释）：**Rust 只管落盘，判断和组装都在前端。**

### 2.2 升级：**复用 `migrateSchema`，不写第二套兼容代码**

暂存库用 `Database.load('sqlite:spool.import-staging.db')` 单独打开，
直接把现成的 `migrateSchema()` 喂给它 —— 它接受的就是一个 db 句柄。

于是三种来库自动各就各位：

| 来库的 `user_version` | 会发生什么 |
|---|---|
| 比当前构建**旧** | 沿 `MIGRATIONS` 注册表一步步升上来，和启动时走的是同一条路 |
| **一样** | 什么都不做 |
| 比当前构建**新** | ⚠️ **拒绝**，且**一个字都不合并** —— 降级防线（`client.ts` 那条 `refusing to rebuild`）在这里同样成立 |

⚠️ 最后一行的文案要说清楚**这不是导入失败，是这台机器上的 Spool 太旧了**，
否则用户会以为文件坏了（backlog §1.1 早就点了这条）。

### 2.3 合并（见 §3），完事删掉暂存库

## 3. 合并规则

### 3.1 撞 id 就跳过，**永不覆盖本机已有的行**

id 是 21 位随机串，两个库各自建的东西**不可能撞**。所以撞上只有一种情况：
**同一份库被导入了两次**。那时候正确的动作是跳过 —— 于是重复导入天然是安全的。

`INSERT OR IGNORE` 一句话就是这个语义。⚠️ **不要写成覆盖**：
覆盖等于让一个外来文件改写本机的行，那是替换从后门爬回来。

⭐ 顺带解释了 §0 那条代价：两个库里各自建的「Flux」是**两个不同的 id**，
所以合并之后是两个项目。**这是对的** —— 它们本来就是两段互不相干的历史，
按标题合成一个才是在替用户猜。

### 3.2 哪些表跟着走

| 表 | 跟不跟 | 为什么 |
|---|---|---|
| `workspaces` / `threads` / `blocks` | ✅ | 用户的东西本体 |
| `follow_up_items` | ✅ | 跟进清单是项目的一部分（v22 起一行一条） |
| `attachments` | ✅ | 记录跟着走，⚠️ 但文件本身不会（§3.4） |
| `proposal_batches` / `proposals` | ✅ | 待审的东西是「还没处理完」，不是「已经过去」 |
| `engine_runs` | ❌ | 运行卡按设计就是**来了又走的**（交接 §9.8），是一次运行的痕迹不是数据 |
| `date_dismissals` | ❌ | 「今天不提醒」，跨机器无意义 |
| `file_access_requests` | ❌ | ⚠️ **授权状态，绝不搬** —— 那些文件在这台机器上根本不存在 |
| `*_fts` | ❌ | 外部内容索引，**由触发器自己长出来**。照搬会索引两遍 |

⭐ 最后一行是免费的：合并走的是**逐行 INSERT**，`blocks_ai` / `attachments_ai`
那几个触发器照常开火，全文检索不用管。

### 3.3 ⚠️ 合并会撞坏一条全局唯一性：`is_capture_target`

schema 上写着**「exactly one row globally may be 1」** —— 捕捉目标全局只能有一个项目。
两个库各有一个，合并之后就是**两个**。

**规矩**：本机已经有捕捉目标 → 带进来的项目一律落成 `0`；
本机一个都没有（新装的机器）→ 保留来库的那一个。

⚠️⚠️ **只有活着的行有资格争这个标记** —— 这一条是**在真库快照上演练时才发现的**，
不是读代码读出来的：

> 真库里**有两行**带着 `is_capture_target = 1`：活着的「UIUC MSC」，
> 外加一条**已删除的无标题项目**。**删项目并不会清掉这个标记。**

我最初的规则是「数所有行」，于是**表里谁排在前面谁就赢** —— 很可能是那条已删除的赢，
把用户真正在往里捕捉的项目顶掉。换机器之后捕捉悄悄落到一个删掉的项目上，**不会有任何报错**。
现在两侧都只看 `deleted_at IS NULL` 的行，带进来的已删除行一律落 `0`。

⚠️ **那条遗留标记本身不去动它**（既存的产品小毛病，不在这一件的范围里）——
只是合并不再被它骗。

⭐ 通则：**一条「全局只有一个」的规矩，要连着问「删掉的那些还算不算数」。**
软删除让不变量多了一个没人想过的维度。

⭐ 这条是那类**「把两个容器并起来，容器级别的不变量就没人管了」**的问题
（和交接 §10.4 第 2 条同源：平列表改成树之后，所有「按容器算」的行为都要重看一遍）。
**合并两个库之前，先把「全局只能有一个」的东西数出来。**

### 3.4 附件：记录跟着走，文件不会 —— **导入完成时直说**

`attachments.target` 存的是**绝对路径**（schema 注释：只从系统文件选择器来）。
换到新机器，那些路径指向的是旧机器上的位置。

**Ocean 定的**：导入完成时直说 —— 「有 N 个文件在这台机器上找不到了」，
并说清楚**块里的文字都还在**（`extracted_text` 在库里，AI 照样读得到），
只是点「打开」会失败。

⚠️ 他否掉的两条：什么都不提（用户哪天点开才发现，那时候已经不知道是导入造成的）、
做一个逐个重新指路的界面（明显更重，等真有人要再说）。

## 4. 已知代价（都是明说的，不是漏掉的）

1. **两个收件箱。** 新装的机器会播种一个收件箱 + 教程项目，导入再带进来一个收件箱。
   用户看到两个同名文件夹，拖一下、删一个就好（拖放 2026-08-17 刚修好）。
   ⚠️ 不做「按标题自动合并」—— 那是替用户猜，和 §3.1 一个道理。
2. **附件打不开**（§3.4），已明说。
3. **运行记录不跟**（§3.2），跟进清单本身是跟的。
4. **合并没有撤销键。** 但它只做加法，撤销 = 把带进来的项目删掉；
   而且导入前会像迁移那样先写一份自动备份。

## 4-bis. 验到哪一步了（2026-08-17）—— 说准

**跑过并且过了**：Vitest 全套、tsc、cargo、i18n。合并本身 13 条单测。

⭐ **在真库快照的副本上真跑了一遍**（照交接 §8.3 那条规程，快照是只读 `VACUUM INTO` 出来的，
**真库一个字节都没写过**）。把整份真库合并进一个空库：

| 项 | 结果 |
|---|---|
| 12 工作区 / 39 项目 / 186 块 / 2 附件 / 10 条跟进 | **一条不差全部落地**，`skipped = 0` |
| 全文检索 | 186 条索引**自己长出来了**（触发器，没抄索引） |
| 嵌套工作区 | **7 个子工作区的 `parent_id` 原样保留** |
| 软删除的 12 个项目 | **照样带过去**（换机器要原样，不是清理过的样子） |
| 再导入一次同一份 | 新增 0，跳过 249 —— **重复导入是安全的** |

✅ **已装机，Ocean 当天真跑过一遍**：导出一次 → 把导出的文件再导入 → 报「已经都有了 / 跳过」。
**重复导入不会变成两份，这条是他亲手验的。**

### ⚠️⚠️ 装机第一次就炸了一个：`db.close()` 把整个 app 的库关了

他的报错：**「数据库初始化失败 / attempted to acquire a connection on a closed pool」**。

`tauri-plugin-sql` 的 `close` 收一个**可选**的库名，**不传就是关掉每一个池** ——
文档原话「Otherwise, all database pools will be in scope」。它挂在 `Database` 实例上，
我读成了「关我这一个」。于是导入一收尾，`sqlite:spool.db`（真库那个池）也被关了，
**之后每一次查询都失败**，下次载入就报「数据库初始化失败」。

改成 `staged.close(staged.path)` —— `path` 正是 `execute` / `select` 自己用的那个 key。

⭐ 通则：**一个可选参数，默认值是「全部」，就是个陷阱。**
它长得像作用于这个实例，实际上是全局操作。**读到 `f(x?)` 时先问一句「不传是什么意思」。**

⚠️⚠️ **仍然没验过的，别当验过**：

1. **「带进来 N 个」那条路没人看过。** 本机导入自己的库永远是「已经都有了」（id 都一样），
   要真的另一台机器才看得见。
2. **导出的两条拒绝路径没走到过**：「导出到数据目录里」的拒绝、替换已有文件。
3. **没有真的跨机器走过一遍。** 附件路径找不到的那个计数，本机上凑不出真实场景。
4. **一个大库的耗时没量过。** 真库 186 块是瞬间的事，几万块的库没数据。

## 5. 不做的

- **同步 / 双向合并**：两台机器都改过同一个项目，谁赢？这一版不回答这个问题
  （id 撞了就跳过 = 本机赢，仅此而已）。
- **按标题去重、冲突解决界面**：见 §3.1。
- **把库导出做成「打包」的一种**：见开头那条警告。
