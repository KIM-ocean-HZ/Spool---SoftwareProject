## 1. 本轮定下的结论

### 1.1 核心判断

| 结论 | 依据 |
|---|---|
| **事件层 = `follow_up_items` + 一个可空 `due_at`** | 该表已有 `standing`、`status`(`proposed`/`open`/`answered`)、`fingerprint` 去重、`proposed_by`、`answer_block_id`、`outcome`；MCP 已有 `get_follow_up_brief` / `suggest_follow_up_item` / `close_follow_up_item` |
| **"项目管理 / 周回顾 / 日程"不是三个东西，是同一张表的三种排序** | 按项目分组 = 项目管理；按周期回顾 = 周回顾；按日期排序 = 日程 |
| **拒绝清单里「Kanban / calendar / table views」那一行不需要推翻** | 那一行拒的是"日历作为一等新视图，每个视图都是永久维护"。改造已有的项目板不产生新的维护面 |
| **项目摘要功能已存在，不要重造** | `threads` 有 `summary` + `summary_source`(`user`/`mcp`/null) + `summary_at` + `auto_maintain`；`set_thread_summary` 在 `summary_source='user'` 时**拒绝**执行（§6.3：这是列级强制，不是约定） |
| **音视频的四带归属由触发方式决定** | 用户自己的语音输入 → 💭 Personal（等价于打字）；视频 / 会议音频转录 → 与网上捕获同级，必须带 source 标签 |

### 1.2 本轮收回的两个说法

- **"一旦可以手输就变成待办 app"** —— 过于绝对，收回。判据不是"能不能手输"，是
  **用户为了让日程保持准确，需不需要定期回来维护它**。替代红线见 §1.3。
- **"抓字幕就能覆盖视频"** —— B 站没有可选中的转录文本，这条路对主力场景不成立，收回。

### 1.3 新增红线（建议写进 §13）

> **Spool 永远不因为事件过期而要求用户做维护动作。**
> 过期事件自动沉默：变灰、退出提醒、不再占据视觉焦点，绝不弹出"此事件已过期，请更新"。

这条是"日程不会把 Spool 变成待办 app"的可执行判据，取代了原来那句绝对化的表述。

## 2. 数据模型改动（全部改动只有这一处）

```
follow_up_items
  + due_at        TIMESTAMP NULL     -- 有值 = 事件；无值 = 原来的"要盯的事"
```

- **必须带 down-migration。** §6.2 的规矩：每个 schema 步骤都要能迁回去，否则下一步的迁移
  往返测试没有起点。
- 不新建 `events` 表。事件和 follow-up 行是同一种东西，区别只在有没有日期。
- `fingerprint` 去重逻辑要把 `due_at` 纳入，否则同一件事被抽出两个不同日期会去重成一条。

## 3. 工作项（按落地顺序）

### W1 · 修连续专注判据 —— 最先做，因为现有行为是错的

**问题**：现判据是「Spool 必须是**前台窗口** 且五分钟内被触碰」。但 Spool 的设计前提就是
你在别的软件里工作（全局捕获、浏览器标签标题捕获），所以这条判据和产品前提直接矛盾。

**不采用**"关闭软件才算中断"：那会把问题从**漏报**翻成**谎报**。原设计特意防了伪造
（"a sleeping laptop cannot manufacture a streak"），而这是个健康干预——剂量来自
BJSM 论文（DOI `10.1136/bjsports-2025-111221`），会真的锁窗口五分钟。

**新判据**：

```
工作中 = 系统未空闲
         AND (Spool 在前台 OR 最近 N 分钟内有过捕获)
```

- 系统空闲查询：macOS `CGEventSourceSecondsSinceLastEventType` / Windows `GetLastInputInfo`。
  只返回时长、不读事件内容。**Spool 为全局捕获本来就持有 Input Monitoring 权限，
  这条不引入任何新权限。**
- `N = 15`（原为 5）。有了系统空闲这道闸，放宽到 15 是安全的；30 也不会造假，但收益递减。
- 仍然按 tick 计入，不改。

**验收**：
1. 在别的应用连续工作 60 分钟、期间有捕获 → 触发休息提醒 ✅
2. 挂机 60 分钟（Spool 在前台不动） → **不**触发 ✅
3. Spool 前台阅读长块 14 分钟不动手 → 计时不中断 ✅

**兜底**：如果并集判据仍然不准，按 §2.6 第五问，正确动作是**下架这个功能**，不是把它
重定义成永远为真。本项目已有两次上线后回滚的先例（进度条、`next_step`）。

### W2 · 查清已有的项目摘要为什么不可见 —— 调查，不是开发

不要重造。先查三件事，产出一句话结论：

1. UI 上在哪里能看到和编辑 `threads.summary`？如果没有入口，那就是全部问题所在。
2. MCP 写回之后，`set_thread_summary` 是否真的被调用？还是只是工具存在、routing text 没提它？
   （§8.4：新工具必须同时出现在 `OPENERS` 或 `INSTRUCTION_BODY`，否则第三方客户端永远不会调用它。）
3. `auto_maintain` 默认值是什么？谁在读它？

**结论只有两种**：要么"没接线"，要么"接了但没入口"。两种的修法完全不同，先分清再动手。

**顺带**：用户提的"方便 MCP 读取相关的项目"，更好的解法不是摘要而是**确定性字段**——
项目列表工具返回 块数 / 最近更新时间 / `deadline` / `status`。全部可从数据推导，零腐烂，
且不会产生"AI 写的摘要被下一个 AI 当成 Reference"的权威污染（摘要没有 source 标签，
坐在块之上，四带模型防的正是这个）。

### W3 · `follow_up_items` 加 `due_at`

- 迁移 + down-migration + 往返测试（见 §2）。
- 过期事件行为：变灰、退出提醒、不再要求任何用户动作（新红线 §1.3）。
- MCP 同步：
  - `get_follow_up_brief` 返回 `due_at`
  - `suggest_follow_up_item` 支持带日期的提案，**仍然落 `proposed`，永不直接生效**
  - `close_follow_up_item` 对 `standing` 行的拒绝逻辑不变
- **routing text 必须同步更新**，否则 AI 不知道可以提日期（§8.4）。

**验收**：AI 通过 MCP 提一条带日期的事件 → 落进 review queue → 用户点一下才生效。

### W4 · 日期抽取 → 事件提案

- 复用已有的「分析文本日期」功能 + 已有的 review queue（该队列已承载 split writes /
  corrections / follow-up lines，这只是第四种提案类型）。
- **只从已捕获内容推导。** 手输允许存在，但**不能是主路径**——主路径必须是"你捕获的东西里
  藏着哪些日期"，而不是"请输入一个日程"。这是 Spool 和待办 app 的分界线。
- 抽出的事件挂在**来源块所在的项目**下，并记录 `answer_block_id` 指向那个块（该字段已存在）。

**验收**：捕获一段含日期的文本 → review queue 出现一条待批准事件 → 批准后出现在右侧栏。

### W5 · 右侧栏事件面板 —— **右栏只归当前项目**

**复用已有的 `RightRail`**（Follow up 的运行已经在那里，事件落在同一个面上是一致的）。

**已定：右侧栏不做嵌套，范围严格等于当前项目。** 跨工作区的事件全览交给 W6 的日程板。

理由（四条，任何一条单独都成立）：

1. **职责不重叠。** 右栏 = "我现在在这个项目里"；日程板 = "我接下来要处理什么"。
   如果右栏也能全览，两个界面在做同一件事，那就是自己跟自己重复——正是拒绝清单
   「每个视图都是永久维护」要防的成本，只不过换了个形式。
2. **右栏窄，装不下树。** 工作区已经可以无限嵌套（见下），在窄容器里渲染深树很快就不可读。
   日程板是主区域，有宽度承载跨项目视图。
3. **它给了项目板活下去的唯一理由。** W6 挂了 kill criterion。如果右栏也能全览，
   日程板就再一次没有独占价值，那条 criterion 基本注定触发。让"跨项目看时间"只有一个地方，
   日程板才有存在意义。
4. **和已有模式一致。** 跨范围的聚合在侧边栏（cross-workspace focus）就已经不放在右栏了。

**唯一的补偿设计**：右栏事件列表底部放一行 **「本工作区还有 N 个事件 →」**，
点击跳转到日程板并预筛到该工作区。零嵌套、零重复视图、一次点击到位。

> ✅ **已澄清（2026-08-20）**：`SPOOL_OVERVIEW.md` 关于层级的描述**已过期**。
> 左侧边栏现在**本来就支持工作区无限嵌套**，「Exactly two tiers」那条拒绝早已被实现推翻，
> 只是文档没跟上。见 W9。

**由无限嵌套带出的一个必须定的语义**：日程板按选中工作区聚合事件时，是只算直属子项目，
还是**递归所有后代**？建议**递归**（规划视角要的是全部），并在每条事件上显示
**所属项目名 + 至少最近一级工作区**，否则深树里"这个事件属于哪儿"会读不出来。

### W6 · 项目板改造成日程板

**现状**：作者本人在使用中从来不打开项目板。它是一个死界面——因为它复制了侧边栏的信息
却没有增加任何新维度（`deadline` 虽然在，但没有时间轴）。

**改造**：把项目板变成**按 `due_at` 排序的事件 + 项目 `deadline` 的时间轴视图**。

- 这是**改造已有视图**，不是新增视图 → 拒绝清单那一行彻底不用推翻
- 顺带清掉一个死表面，净维护成本可能是负的

**硬性 kill criterion（必须提前写下来）**：
> 改造后一个月内，如果作者本人仍然不主动打开这个板，**删掉整个项目板**。

一个自己都不用的界面，加了时间轴就一定会用吗？这是个假设，不是结论。本项目的文化是
用测量推翻假设，这里不要破例。

## 4. 音视频：本轮定下的规则 + 待调研清单

### 4.1 四带归属规则（已定）

| 触发方式 | 写入时的 source | 落进哪一带 |
|---|---|---|
| 用户对着麦克风说话（语音输入） | **无 source 标签** | 💭 Personal —— 等价于打字 |
| 视频 / 会议音频转录 | **必须带 source**（如 `Bilibili · 音频转录`） | 与网上捕获同级，按来源判定 |

**触发方式决定来源标签。** 这条和现有设计一致（无 source = 用户自己输入的）。

**两处连带改动**：

1. **pack header 的措辞要改。** 现在写的是"no label means the user **typed** it themselves"和
   "these are **typed** by the user directly into Spool"。语音输入进来之后 typed 不再准确，
   要改成能涵盖口述的说法。
2. **口述块建议带一个"来自语音"的标记**（不是 source 标签，是一个 flag）。原因：
   Personal 那一带的规则是"如果有事实错误，直接指出，不要照顾用户感受"。
   转录噪声会被当成用户的主张，导致 AI 去纠正用户根本没说过的话。

### 4.2 待调研（先查清再设计，不要先写代码）

1. **macOS 捕获系统音频到底要什么权限？** ScreenCaptureKit 的音频流 vs Core Audio
   process tap（macOS 14.4+）分别对应哪个 TCC 项？**用户看到的弹窗文案是什么？**
   —— 这条最关键：如果弹窗仍然写"Spool 想要录制你的屏幕"，那"只录声音不录屏"的隐私叙事
   在第一个弹窗处就崩了。
2. **Windows 上的系统音频回环（WASAPI loopback）要什么权限？** 预期不需要特殊授权。
   如果属实，**Windows 反而可以先行**，这会是少见的"Windows 体验优于 macOS"的功能。
3. **本地 ASR 的体积代价**：whisper.cpp 各模型档位的二进制 + 权重体积，以及中文准确率。
   对照当前安装包体积，判断是否可接受。
4. **云 ASR 能否塞进 sidecar**（`SPOOL-STRATEGY-2026-08-19.md` §5 的形态 C），
   且**只接受本地文件、不接受 URL** —— 这样注入面不变，红线只用到已经反转过的那一条。
5. **B 站是否有可程序化获取的字幕**（部分视频有 AI 字幕），作为零成本的补充路径。

### 4.3 顺序与依赖

- **麦克风先，系统音频后。** 麦克风的权限语义干净，且直接对应"语音输入"和"会议捕捉"两个场景。
- **依赖 sidecar（形态 C）先落地。** ASR 无论走云 API 还是本地二进制，形状都是 sidecar。
  这不是并行的新工程，是同一条路的第二步。**sidecar 没做完之前不要开工。**

## 5. 明确否决（附理由，防止重提）

| 否决项 | 理由 |
|---|---|
| 颜色映射项目优先级 | 优先级是需要维护的主观数字，与已回滚的进度条同类；且「Colour-coded blocks by source」已因违反"quiet"被拒 |
| 项目"预估完成时间" | 估计值会腐烂（项目永远延期），假日期比没日期糟。不腐烂的是**外部给定的真实日期**。且 `threads.deadline` 已存在 |
| 目标列表推导项目完成 | 由完成度推导状态 = 需要维护的派生状态 = 进度条被回滚的原因。已有 `status` 由人一次性设置 |
| ~~文件夹作为第三层容器~~ | **此条作废**：工作区已支持无限嵌套，文件夹早就有了。剩下的是堆积问题，见 W7 |
| 右侧栏做工作区级事件嵌套 | 与日程板重复；右栏窄装不下深树；且会让日程板失去唯一存在理由（见 W5） |
| "关闭软件才算中断" | 把漏报翻成谎报；在伪造信号上执行有论文依据的健康干预，比不干预更糟 |
| 链接直接转视频 | 联网抓取撞零出网；且是 Follow-up 注入面的放大版——一个 URL 决定进入项目的内容 |
| 双击 ⌥ 录屏 | 撞「Fully automatic capture」；且是首次运行信任冲突的加强版 |

- **§4.4 / §4.5** —— 事件层、右侧栏面板、项目板改造
- **pack header** —— §4.1 的 typed 措辞
- **`CASE_STUDY_LEDGER.md`** —— 本轮有一个值得记的数据点：作者本人 dogfood 产出的 pack
  里**零 pin、零 `↩` 引用**，而其中一块明确推翻了另一块。这是 provenance graph
  "已在数据里、几乎没有被呈现"的直接证据

## 7. 一条从本轮讨论带出来的方向修正

`SPOOL-STRATEGY-2026-08-19.md` §4.1 把 provenance graph 列为第一优先，理由是它已经在数据里
却几乎没有被呈现。**本轮给出了更准的诊断**：不是概念没用，是**建立引用的动作不存在或太贵**——
作者本人在真实使用中都没有伸手去用 `supersedes`。

所以顺序要调：**先做"怎么建立引用"**（时间线上把一个块拖到另一个块上，或写块时提示
"这是在推翻上面哪一条吗"），**再做展示**。展示一张空图没有意义。
