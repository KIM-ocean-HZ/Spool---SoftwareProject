### 5.1 ✅ LICENSE:不加(2026-08-08 Ocean 明确答复)

⚠️ **这一件已经结了,别再问,也别在任何时候顺手加 `LICENSE` 文件。**
memory `no-license-file` 的红线继续有效,而且现在有了明确的"不"作后盾。

**为什么当初要单独要一次明确答复**:给一个已经公开的仓库加开源许可,是一扇单向门 ——
MIT 一旦推上去,那个版本的代码就永久地授出去了,之后改成别的许可只对**之后**的版本有效,
**已经放出去的那一版任何人都可以继续用、改、卖,撤不回来。** 他选了不迈这扇门。

**后果要写进 case-study 台账,别掩着**:公开仓库没有 LICENSE,
**法律上等于「保留所有权利」** —— 读的人不能复制、修改、分发。
对 case-study 场景这不一定是坏事(展示 ≠ 授权别人拿走),
**但它是一个会被问到的问题,应当在页面上主动答一句**,而不是等人来问。

→ **建议的一句话措辞(英文,进 §4 的第三期正文)**:
> Source-available for review; all rights reserved. Not licensed for reuse.
⚠️ **加的时候顺手确认署名写谁**(真名 / KIM-ocean-HZ / 别的)。

### 6.2 ⭐ 写的时候定下来的一条口径(以后照它维护)

**每条失败都必须回答「结构上变了什么」,不能只写「修了什么」。**

理由:招生官读一条 bug 修复不会有任何印象;读到「这一天之后,数据层多了六条守卫,
其中一条是『任何在启动时碰项目表的东西都按这个 bug 的形状对待』」——那是**判断力的证据**,
而 bug 本身只是背景。**§3.1(真库被清空)是照这个口径写的样板,以后加条目对着它写。**

⚠️ **顺带一条**:三条失败(§3.4 提示词规则失效 / §3.5 effort 用不了 / §3.6 免费档撞墙)
指向的是**同一个教训**,台账里让它们互相引用,而不是各写一遍。
那个教训本身(「子进程和外部客户端的事,只有真跑能验」)现在是台账里最反复出现的一句。

### 6.3 ⚠️ 三条维护规矩(下次动这份台账之前读)

1. **只增不改。** 数字变了就**新加一行带日期**,旧的留着 —— 趋势本身是证据。
   这跟交接的规矩正好相反(交接每窗重写),别拿交接的习惯改台账。
2. **脱敏是硬的**:能公开的只有「形状和数量」。任何一条**不引用库里内容就说不清**的,
   就不该进台账。§2.3 那条 ChatGPT 写入测试**明写着「发布前需脱敏」** ——
   11 块正文是真实申请材料。
3. ⚠️ **公证回执是唯一一个「过后补不回来」的数字**(§6 待办第三条)。

### 7.3 ⭐ 「目标用户」这一栏是怎么写的(以后改它之前先读这条)

   开发者 / 单干的人)信息量很低,**「每开一个新对话都要从零解释一遍」才是真正的定义**。
2. **写清「不是给谁用的」** —— Notion 替代品 / 团队工具 / 写文档的地方,三条都否掉。
   §2.6 那张否决表是现成的,而**主动说不做什么比列功能更可信**。
3. ⚠️⚠️ **主动交代「没做过用户研究」。** §2.4 明写着 v1 期间不做用户研究、
   开发者本人就是精确样本。**藏起来会被问,主动说反而是强项** ——
   页面里紧接着给了证据:**几个决定正是靠自用把设计推翻的**(§2.1 那笔账最典型)。
   **这一条是本篇的判断:招生场景里，「知道自己方法的边界」比「装作没有边界」值钱。**
