### 3.2 ⭐ 本窗新学到的三条

1. **`None` 和「没事可做」是同一个值。**
   `ax_focused_app_pid()` 返回 `None` 时，调用方把它当「没有来源 app，不用抢焦点」，
   于是一个**查询失败**静默变成了一个**看起来正确的 no-op**，两周 dogfood 都没抓出来。
   写这种查询时，「查不到」和「不需要」要能分开。

2. **推理定位敌不过埋日志。**
   我在设计稿里断言「按代码，从任何非 Spool 的 app 捕捉都该抢到焦点」，
   并把 Ocean「只有 word 会抢占」的观察记成待验证。**他是对的，我是错的。**
   装机埋一行 `eprintln!` 就看清了。这台机器上合成事件驱动不了 Spool
   （HID tap 看不见注入事件、合成点击驱动不了 webview），
   **所以「让 Ocean 真手指跑 + 埋日志」是唯一可行的验证路径，不是偷懒。**

3. **原子量跨线程读会骗人。**
   helper 回的 `"shown"` 在 stdout 读取线程上处理，主线程稍后再读同一个原子量时
   它可能已经被改回去了。要跨越 send 的判断，用**局部变量**。

### 3.3 换装 `/Applications/Spool.app` 的规程（本窗走了四遍，零事故）

```
① 核 identifier（仓库的 + target/release/bundle 里躺着的，防 verify 产物）
② codesign -dvv /Applications/Spool.app | grep Authority  ← 看到什么就用什么
   本机现在是 "Spool Dev" 自签 → 直接 npm run tauri build -- --bundles app，不加发布证书
③ 核 SCHEMA_VERSION（src/lib/db/client.ts）== 真库 PRAGMA user_version，否则别装
④ 手动 VACUUM INTO 备份真库（自动那份是迁移代码自己写的，它坏了就没有它）
⑤ 按 pid kill 主进程和 --overlay ——⚠️ 绝不模糊 pkill，别的 AI 客户端的 --mcp 子进程一直在跑
⑥ ditto 新版 → open --stdout/--stderr 抓日志
⑦ 起来后核：真库行数/user_version 未变、CPU 0.0%（白屏会烧 CPU）、
   启动日志是 installed at HID/active（= 两个 TCC 授权都还在）
```

⚠️ zsh 下 `kill $(...)` 会把多个 pid 拼成一个参数报 `illegal pid`，**显式写 pid**。

### 11.2 ⭐⭐ 拖项目进工作区一直是坏的 —— 原因不在我们的代码里

**Ocean 的原话**：「拖移项目到工作区……无论是单个项目还是多选项目拖移都无法做到，
拖移它会出现**绿色的加号**，但是工作区并没有任何变化」。

**⭐ 那个绿色的加号就是决定性证据，而且它不可能来自我们的代码** —— 我们的 `dragover`
写的是 `dropEffect = 'move'`，macOS 上 move **不画角标**。绿色 ＋ = `NSDragOperationCopy`。

取证到底之后的结论：**这个 app 里 HTML5 拖放从来就不可能工作。**
Tauri 给 WKWebView 装了一个原生拖放处理器（窗口配置 `dragDropEnabled`，**默认开**），
wry 的 macOS 实现（`wkwebview/drag_drop.rs`）覆盖了 `draggingEntered:` /
`draggingUpdated:` / `performDragOperation:`，而且**一旦监听器认领了事件就不再调 super**
—— `tauri-runtime-wry` 的监听器**无条件 `return true`**。于是任何一次拖动：

- `draggingEntered` 直接回 `NSDragOperation::Copy` → **绿色 ＋**；
- `performDragOperation` 回 YES 就结束 → **网页永远收不到 `dragover` / `drop`**。

行上的 `dragstart` 照常触发（那是 WebKit 的**发起**侧，不经过这个处理器），
所以拖起来看着是活的、松手什么也没有。⚠️ Tauri 自己的文档只说「**Windows** 上要关掉它
才能用 HTML5 拖放」，**macOS 上同样会挡**，文档没写。

⚠️⚠️ **不能靠关掉 `dragDropEnabled` 解决**：那个原生处理器正是 Finder 拖文件进来时
`useThreadDropTarget` 拿到**真实路径**的唯一通路。HTML5 的文件拖放只给一个没有路径的
`File`，而项目文件功能存的就是路径。**两个功能抢同一个开关，只能让我们这半让路。**

**改法**：左栏自己驱动一次指针拖动（`lib/sidebar/railDrag.ts`）——
`pointerdown` 只是**上膛**，走过 4px 才算拖；跟手的小卡片（`RailDragGhost`，
`pointer-events-none`，否则它自己会挡住命中测试）；命中测试用
`elementFromPoint(...).closest('[data-drop-workspace]')`；靠近上下边缘自动滚动左栏；
Esc 取消；松手后**吃掉紧随的那一次 click**（否则拖回原地会顺手把项目打开）。

⭐ **顺带把 §10.4 第 2 条那个「嵌套 → 事件冒泡 → 后跑的赢」问题一起消掉了**：
`elementFromPoint` 返回的就是**最里面**那个元素，子工作区天然赢过父工作区，
两个 handler 都不用再 `stopPropagation`。

⭐ **这一窗最值钱的方法论**：**先问「屏幕上那个现象只可能由谁画出来」，再去读代码。**
绿色 ＋ 在整个技术栈里只有一个出处。我如果从「React 的 onDrop 为什么没跑」开始查，
会在自己的代码里绕很久 —— 而那里一行错都没有。
⚠️ 同时说准：**这条诊断没有靠日志证实过**（合成事件驱动不了 Spool），
证据链是「代码里读出来的机制 + 只此一家的角标」。**但改法不依赖诊断对不对** ——
指针拖动本来就不走 HTML5 那条路，诊断即使错了它也照样能用。这是故意选的。
