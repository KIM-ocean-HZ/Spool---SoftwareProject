## 1. 专业可量化的用户下载量看板

**Ocean 原话**：「我需要专业可量化的用户下载量看板，用来得到用户反馈，和下载量情况」。

**里面其实是两件事**，做法完全不同，别混在一个东西里：

| | 下载量 | 用户反馈 |
|---|---|---|
| 数据在哪 | **GitHub Releases 的资产下载计数**（每个资产一个数） | 现在**一条都没有**，没有任何回流渠道 |
| 要不要动 app | **不用**（数在 GitHub 那边） | 看选哪条路 |
| 撞不撞零出网红线 | **不撞** | ⚠️ **很可能撞**，见 §5 |

### 1.1 先要他定的口径（不定就没法做「可量化」）

1. **看板给谁看？** 只有他自己看（本地一个页面/脚本就够），还是要能给别人看（要挂公网）？
2. **多久一个点？** 下载计数是**累计值**，GitHub 不给历史曲线 —— 想要「每天新增多少」
   **必须从某一天开始自己按天存快照**，越早开始越好。**这件事越晚做，丢的历史越多。**
3. **口径怎么算才叫「一个下载」？** ⚠️ 这次发布有**四个资产**：
   `Spool_0.6.1_aarch64.dmg` / `Spool_0.6.1_x64-setup.exe` 加两个固定名
   `Spool-macOS-arm64.dmg` / `Spool-windows-x64-setup.exe`。
   **同一个文件有两个名字，官网下载按钮走的是固定名那两个。**
   直接把四个数相加会**双算**；只看带版本号的那两个会**漏掉官网来的绝大部分**。
   这个口径他得先认一个。
4. **反馈要哪一种**：邮件？官网表单？GitHub Issues？app 里一个入口？
   ⚠️ 最后一种要动 app，先看 §5 第 2 条。

### 1.2 已知的起点（只是线索，不是方案）

- 下载计数可以直接问 GitHub，不需要 app 配合，也不需要用户同意 ——
  **这是唯一一条完全不碰零出网红线的路**。
- 官网已经有一个邮箱订阅/反馈位（`email-collection-website-only` 那条决策：
  **只放官网，app 内零出网叙事不动**）。**扩反馈渠道优先从这里长，别从 app 里长。**

## 2. 订阅制 vs 买断制 + 给朋友的兑换码

**Ocean 原话**：「我需要考虑 app 的订阅制和买断制，并设计一个给朋友的兑换码」。

### 2.1 ⚠️ 这件事必须他先拍板，代做不了

定价模式是产品所有者的决定，不是技术选型。**下一窗可以把两种模式的代价摊开给他看，
但不许替他选。**

### 2.2 他一定要先回答的问题

1. **卖的是什么？** 整个 app？还是某些功能（比如 MCP 那一侧、跟进、周回顾）？
   现在**全部功能都是免费全开的**，没有任何门。
2. **老用户怎么办？** v0.6.1 之前下载过的人（下载量是多少见 §1），加不加门？
3. **兑换码要免费到什么程度？** 永久全功能？一段时间？给几个人？
   —— 这决定它是「一次性发几个码」还是「要一套发码/校验系统」。
4. **能不能离线校验？** ⚠️ 这条最关键，见下。

### 2.3 会撞上的既有红线（都是硬的，见 §5 全表）

- ⚠️⚠️ **不上 Mac App Store 是 2026-07-06 就定了的**（沙盒与 CGEventTap / 私有 API /
  浏览器 AppleScript 硬冲突）。**所以 App Store 那套现成的订阅和兑换码（Offer Code）用不了。**
  订阅制意味着**要么自己架收单和校验服务，要么用第三方发牌服务** ——
  两条都会给这个「本体零出网」的 app 引入一条出网通路。**这是最大的那个矛盾。**
- ⚠️ **买断制 + 离线校验的签名许可证**是唯一和现有红线不冲突的形态（本体仍可零出网），
  但它天生防不住分享。**这个取舍要他自己认。**
- ⚠️ **Windows 版没有代码签名**（2026-08-15 决策，且他说「这条不要再问」）。
  收费软件在 Windows 上弹 SmartScreen 警告是个真问题，**要收钱可能得回头重新决定这件事** ——
  但**别再主动问他**，等他自己提。
- ⚠️ **仓库里没有 LICENSE，而且是明确不要的**（问过三次都是否）。
  要卖东西，许可条款迟早要有个说法。**这件事只能他开口，别擅自加文件。**
