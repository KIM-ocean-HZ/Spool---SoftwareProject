# M4 定时跟进调查（2026-08-13）

> ⛔ **2026-08-15 Ocean 拍板：M4 定时调度不做，换方式。本报告转为「为什么不做定时调度」的论证留档。**
>
> **§7 那十二个问题不再需要回答。** 新方案不是后台定时任务，而是 **MCP 会话内的主动提议 + 待审写入**：
>
> 1. 用 MCP 对话后会留下**还没明确的问题**或**还没发生的事情**，MCP 要**能主动提出**把它们放进跟进面板；
> 2. 等捕捉更新、进入新一轮对话，MCP **发现这些跟进问题就主动搜索并汇报**，有结论就写入，
>    并**修正或删除**对应的跟进条目；
> 3. **手动联网搜索保留**，作为用户主动的开关。
>
> Ocean 的判断是：**跟进「内容是什么」才是最重要的，不是定时。**
> 新方案复用现有的待审闸和署名写回机制，**不需要 scheduler、预算、静默条件那一整套**。
> 落点是 `DESIGN_FOLLOW_UP.md`；当前任务面见 `docs/BACKLOG-2026-08-15.md` §2.1。

> 结论：**当前是 NO-GO，不应进入 scheduler / schema / UI 实现。**
>
> 两道既有闸门都没有关闭：
>
> 1. **M3 的长期用户价值未被证明。** 手动 M2 有真实有用产出，M3 也有真实 CLI 产出验证过技术闸；但没有 Ocean 连续使用 M3 一段时间、确认它稳定带回有用新东西的记录。
> 2. **“往外拿”闸门未被一个无歧义的产品动作关闭。** 当前有删除、标记不作数、合并重复、Pack/周回顾等动作，但没有一个动作能把“仍然有效、非重复、已经完成阶段使命”的内容安全地移出活跃上下文。后期交接把官网/截图/case-study 进度写成这道闸“快满足了”，与最初 14 周撞满上下文预算的定义不一致，需要 Ocean 重新定口径。
>
> 在两道闸门关闭前，建议只做 **3–4 周手动 dogfood 取证**，不要让一个尚未证明值得的钱包与进货口自动运行。

## 2. 两道闸门

### 2.1 闸门一：M3 是否已有真实价值证据？

**结论：未通过。准确说法是“有潜在价值证据 + 有技术有效性证据，但没有长期用户价值证据”。**

#### 【仓库已知事实】已有的证据

1. **手动 M2 曾产生真实有用结果。** 2026-08-06 在 Ocean 的 Flux 项目副本上跑出 4 条待审提案；仓库记录称最有价值的是发现两处材料出入：MIT 日期与项目名问题、CMU 日期问题。后续真库盘点又记录了 3 条同主题 MCP 块（Cornell / MIT / CMU）。这两份记录共同支持“至少部分结果进入了真实使用”的推论，但仓库没有保留 run→proposal→approved block 的关联，不能把它写成可逐条复算的批准记录。证据见提交 `67777dc` 对 `docs/HANDOFF.md` 的记录，以及 `docs/DESIGN_CONTEXT_HYGIENE.md` §9.1–§9.3。
2. **M3 两次真实 CLI 跑验证了技术闸。** `docs/DESIGN_FOLLOW_UP.md` §4.2 记录：
   - 第一次：haiku，9 轮，$0.19，3 条提案；暴露 3 条中 2 条正文没有 URL 的真 bug。
   - 第二次：haiku，16 轮，$0.25，5 条提案；5 条都有 URL，硬闸把 5 条筛成 3 条，拦住 1 条历史 URL 重复和 1 条批内同页重复。
   - 真跑还暴露并修复了软/硬两侧 TTL 不一致、中文全角标点进入 URL 的问题。
3. **当前测试覆盖了 M3 的核心纯逻辑和数据库支撑。** 本次审计实际运行：
   - Vitest：`followUp.test.ts`、`proposals.test.ts`、`threads.test.ts`、`fileAccess.test.ts`、`engineRuns.test.ts`、`assemble.test.ts`，**6 文件 / 98 项全过**。
   - Rust：follow-up brief/硬规则、`list_threads.following_up` + `due_for_recheck`、brief 建议不得自行生效，**3 项定向测试全过**。

#### 【仓库已知事实】仍缺的证据

1. `docs/HANDOFF.md` 明确写着：M3 自 08-07 完成后，**“从来没有人真用它跑过一段日子”**；只有 Ocean 能通过多次实际跟进判断它是否持续有用。
2. 没有一组按周重复运行的数据能回答：
   - 幸存提案中有多少真的更新了决定或行动；
   - 有多少只是换一种说法的旧闻；
   - 有多少重要变化被静默条件误吞；
   - 用户是否愿意承担待审负担和订阅额度。
3. 当前数据模型不能回算“某次 follow-up 的提案最终批准/驳回/过期”：提案批准或驳回后原行会删除，`engine_runs` 与 proposal batch / 最终 block 之间没有 durable lineage。这是有意的“不留驳回垃圾”设计，不是查询漏写；也意味着不能拿现有库自动算出 M3 价值率。

#### 【推论】为什么不能把已有证据写成“闸门已过”

- M2 的三条有用块证明“手动联网跟进可能有价值”，不证明“每周自动跑仍然有价值”。
- M3 的 5→3 证明硬去重闸有必要且能拦住两类明确重复，不证明剩下 3 条值得用户看。
- 一次发现规则 bug、一次证明修法生效，是工程有效性，不是长期产品价值。

#### 【建议】关闭闸门一的最低取证

在实现 M4 前，Ocean 手动使用现有“联网搜索”至少 **3 周、6 次、覆盖至少 2 个真实项目**，每次只记四项：

1. 本次是否带回至少一条“会改变决定/行动/材料”的信息；
2. 待审条数、批准条数；
3. 是否出现旧闻、无源、跑偏或漏掉已知变化；
4. 运行耗时与 CLI 报出的成本（未报告就记“未知”，不能当 $0）。

建议的开工门槛不是单纯批准率，而是：**至少 3 次运行被 Ocean 明确标成有用；零无源提案；没有发生会让 Ocean 想关掉跟进的重复/跑偏；并且他明确愿意把同样行为改成自动。**

### 2.2 闸门二：自动往里写前，是否已有“往外拿”动作？

**结论：按原始上下文预算定义，未通过；仓库里另有一条口径矛盾，需要 Ocean 定义。**

#### 【仓库已知事实】原始闸门是什么

`docs/DESIGN_CONTEXT_HYGIENE.md` §9.5 的原始论证是容量与产品信任：定时跟进会周期性向项目送提案，批准后有效块线性增长；按当时 Flux 数据，每周约 1,700 字，约 14 周触到 50,000 字 Pack 预算，而那时可能没有重复可清，去重帮不上忙。因此原文要求：**M4 上线前先有一个“往外拿”的动作。**

#### 【仓库已知事实】今天已有但不完全符合的动作

| 现有动作 | 能减少活跃上下文吗 | 为什么没有无歧义地关闭闸门 |
|---|---:|---|
| 删除块 / 删除项目 | 是 | 破坏性强，不是正常处理“仍然有效但阶段已结束”的知识出口 |
| “这条不作数了” (`stale_at`) | 是，退出 Pack 但保留在库中 | 语义是“结论不再成立”；拿它清理仍然有效内容会撒谎 |
| 合并/处理重复 | 是 | 只解决重复；原始 14 周推演明确假设没有重复可清 |
| `corrects` | 否 | 治疗错误，不减少旧块体积 |
| Pack、MCP 读取、周回顾 | 否 | 把内容拿出去使用，但没有降低项目的后续 Pack 存量 |
| 完成项目 | 未形成通用容量出口 | 项目状态改变，但项目内容仍在；不是把一阶段知识安全地移出活跃上下文的动作 |

#### 【仓库已知事实】交接中的矛盾

`docs/HANDOFF.md` 2026-08-11 的 C1 又写过：“往外拿动作——A0 做完，A1/A2/A3 还欠着，这条快满足了”。当时 A0/A1/A2/A3 指官网、截图/视频、case-study 等对外发布工作。它们能证明 Spool 的材料最终被用于产出，但**不会降低任何项目的 Pack 存量**，与 §9.5 的 14 周容量论证不是同一件事。

#### 【推论】当前最稳妥的判断

- 若“往外拿”意为“有真实对外交付使用了 Spool 的材料”，官网/case-study 可能接近满足。
- 若“往外拿”意为“给持续增长的活跃上下文一个安全出口”，当前没有满足。
- M4 的风险来自后一个定义；因此在 Ocean 明确改口径前，不应拿官网进度替代容量出口。

#### 【建议】什么动作才足以关闭这道闸

需要一个用户可理解、可撤回、不会谎称事实失效的动作，例如：

> “把这批已完成阶段使命的材料收进归档层；默认 Pack 不再带，搜索和显式历史读取仍能找到；随时恢复。”

它与 `stale_at` 的差别是“仍然有效，只是不再属于活跃工作集”。在这项能力落地并真实用过以前，M4 仍不应自动扩大入口。

## 3. 当前 M3 与调度输入审计

### 3.1 M3 的现状

#### 【仓库已知事实】可复用的地基

- `follow_up_state` 是现有 `threads` 列，JSON v1：`{v, lastRunAt, seen:[{u,f,at}]}`。
- 历史最多 200 项，90 天 TTL；给提示词的 URL 最多 40 条、由新到旧。
- 软闸在 Rust prompt 组装前提供历史 URL，目的是少抓、少花钱。
- 硬闸在 CLI 结束后、刷新待审角标前运行；按 URL 或结论指纹去重，并做批内去重。
- 提案在用户批准前不是 block；驳回与 7 天过期都不留痕。
- 引擎队列严格串行；Rust 还有第二层单运行保护。follow-up 上限 24 turns；默认超时 300 秒，Rust 硬上限 600 秒。
- `engine_runs` 已记录动作、项目、成功/失败/取消、结果、提案数、成本/token（CLI 未报告时为 NULL）、起止时间。

#### 【仓库已知事实】M4 前必须处理的技术缺口

1. **`lastRunAt` 不是“上次成功”。** `siftFollowUp()` 在没有提案时会更新它，并且失败/取消的 follow-up 也会跑 sift；因此失败、取消、空结果都可能推进该时钟。直接拿它排下一次会把失败当成功冷却。
2. **候选批次按全库时间窗取，不按 run/thread 做 durable 关联。** `listBatchesCreatedSince(runStartedAt)` 会取窗口内所有 batch，再统一送进当前项目的 state。引擎自身串行不等于外部 MCP 客户端不能同时提案；无人值守运行会扩大这类并发窗口。
3. **硬闸失败现在是 fail-open。** `siftFollowUp` 抛错后只 `console.warn`，流程继续刷新待审面并把 CLI outcome 记为成功；窗口内未筛提案可能露给用户，`queued` 却仍是 0。
4. **“同 URL 真的变了”在 90 天内仍会被硬闸吞掉。** Prompt 允许同一页面真正变化后再提，但 `siftProposals` 只要 URL 撞历史就直接判重复，内容是否变化不参与豁免。测试还明确锁定了“同页不同句也删除”。这与 `recheck_after` 最重要的政策页/截止页场景冲突。
5. **“正文必须有 URL”不是硬约束。** 当前硬闸把 `content + annotation` 一起扫描；无 URL 提案仍可按指纹记入 state，并不会被删。URL 只在 prompt 中被强制。
6. **follow-up 的 5 条上限不是硬约束。** follow-up prompt 写 5；通用 `propose_blocks` 服务端硬上限是 24；M3 没有再截成 5。无人值守入口不应只靠模型记住这个数字。
7. **自动空跑会留下噪音。** 当前每次 follow-up 都写 `engine_runs.reviewed_at = NULL`，右栏会显示未处理运行卡；成功空跑也会 toast。手动动作可以这样，定时“没有新东西”不能每周制造一张要手动消失的卡。

#### 【建议】M4 的硬前置修正

- 定时到期使用 `engine_runs` 中该项目最后一次 `action='follow_up' AND outcome='ok'` 的 `finished_at`，不要用 `lastRunAt` 代表成功。
- 候选必须至少按目标 `thread_id` 过滤；更稳的是为内部 run 与 proposal batch 建立不可由模型伪造的关联。在没有关联前，M4 不应无人值守。
- 定时路径的后处理必须 fail-closed：去重/校验/状态写回任一失败，本次候选不得显示，运行不得记成功，也不得推进成功时钟。
- follow-up 专属后处理硬校验：正文至少一个完整 `https://` URL、最多 5 条；不满足的丢弃并把运行标成“规则未满足”，不能只靠 prompt。
- 重新定义同 URL：至少要能区分“同页旧结论”与“同页已变化”。`recheck_after` 到期的来源不能被 90 天 URL 闸无条件吞掉。

### 3.2 `recheck_after`

#### 【仓库已知事实】

- `blocks.recheck_after` / `proposals.recheck_after` 已存在，存 UTC 零点日期。
- AI 写入/提案可携带该字段；批准提案后字段保留。
- 过期块不会自动隐藏或作废。Pack 标“可能已经过时”；`get_project_overview.needs_attention.due_for_recheck` 只数 `stale_at IS NULL` 且已到期的块。
- 当前 GUI 不显示 `recheck_after` 到期提醒；交接明确说该 UI 兑现口被推迟。
- `list_threads` 没有 due 数；跨全库选择到期项目需要 app 侧新增读查询或逐项目读 overview。这里说的是新查询，不要求新 schema。

#### 【推论】

- `recheck_after` 比固定周频更有理由花钱：它是某个事实自己声明的复查日。
- 但它不是完整搜索指令。没有 brief 的项目仅凭一个日期，M4 不知道用户希望查到什么程度；自动起草或自动打开 brief 会越过既有过目闸。
- 一个到期块触发整份 3–5 行 brief 全跑，可能比复查该事实昂贵；现有 follow-up 动作没有“只复查这一块”的范围参数。

#### 【建议】

- 把 `recheck_after` 作为**优先级触发器**，不是绕过 brief 的第二套指令。
- 只有项目已明确同意自动跟进且 brief 非空时，due block 才可让该项目提前进入候选。
- 项目没有 brief：只进入“需要复查”的用户提醒，不自动联网、不自动生成 brief。
- 运行 prompt 应明确列出已到期块、旧 `source_url` 与旧结论；接受的新块必须给新的 `retrieved_at` / `recheck_after`，若推翻旧结论则走 `corrects`。仍然不得自动写 `stale_at`。

### 3.3 `list_threads.following_up`

#### 【仓库已知事实】

- 值等于 `follow_up_brief` 非空；空/空白为 false。
- 它是廉价布尔旗标，不包含 brief 正文；正文由 `get_follow_up_brief` / overview 读取。
- 它表示“这个项目有联网跟进 brief”，不表示“用户同意自动跑”、不表示何时到期，也不区分 active / parked / done。

#### 【建议】

- M4 候选可以复用同一 NULL/非空语义，但不能把 `following_up=true` 当自动化同意。
- app 内调度直接读本地 DB/Thread 状态，不应为了调度调用 MCP `list_threads`；该字段的价值是保证外部客户端也能便宜看见用户在盯什么。

### 3.4 `applyBriefSuggestion.updated_at`

#### 【仓库已知事实】

- 用户批准 MCP 的 brief 建议时，`applyBriefSuggestion` 会在同一条 SQL 中写入 brief、清空建议，并推进 `threads.updated_at`；已有测试断言该时钟前进。
- 用户在 FollowUpPanel 直接保存、编辑或关掉 brief 走 `setFollowUpBrief`，该函数**不更新 `updated_at`**；`threads.test.ts` 还明确断言 title/status/updated_at 原样不动。
- `updated_at` 也会被摘要等其它变化推进；它不是 brief 专属时钟。

#### 【推论】

`updated_at` 既漏掉用户直接编辑，又混入无关变化，不能可靠表示“brief 何时变化”，也不能作为 M4 due clock。它只能说明“某些项目事实发生过变化”。

#### 【建议】

- M4 第一版不要依赖 `updated_at` 计算到期。
- 若 Ocean 希望“用户一改 brief 就尽快跑一次”，需要一个所有 brief 写路径一致维护的专属语义；在没有该语义前，仍由用户手动按“联网搜索”完成立即运行。
- 不要因为 M4 顺手改变 `setFollowUpBrief` 的既有时钟契约；那是独立决策与测试迁移。

## 4. 推荐的 M4 形状（两道闸门通过以后）

### 4.1 调度模型

#### 【建议】机会型、单队列，不承诺精确钟点

复用 `useAutoMaintain` 的 app 内检查形状，但不要照搬它的失败重试：

1. Spool 仍在托盘运行时，在启动稳定期后、系统唤醒/窗口重新聚焦时、以及每 30 分钟做一次廉价 due 检查。
2. 完全退出 Spool 时不运行；产品文案应明确“Spool 开着时自动跟进”，不要冒充系统级 cron。
3. 每次只把 **1 个项目**送进现有串行引擎队列；先处理最早到期的 `recheck_after`，再处理距上次成功最久的固定周期候选。
4. 不在 mount 瞬间把所有从未跑过的 brief 一次性补跑。每个项目应先手动成功并由用户单独同意自动化，或明确选择“从今天开始自动”。

推荐的候选条件：

```text
专用“自动跟进”总开关开启
AND 项目明确选择自动（不能只看 brief 存在）
AND status = active
AND brief 非空
AND 没有待用户处理的 brief 建议
AND 该项目没有待审提案
AND 选中引擎存在且 supports_web
AND 未超过全局运行预算
AND (有到期 recheck_after OR 距上次成功 follow-up 达到周期)
```

`threads.auto_maintain` 虽仍在 schema 和 Thread 类型中，但它保存过旧的“自动维护项目”语义。**不建议静默复用为自动联网同意**：旧值 `1` 不是对自动出网的新授权。若要复用，必须让所有用户重新明确选择，不能继承旧值。

### 4.2 预算

#### 【仓库已知事实】可执行的现有边界

- 单 run：默认 300 秒，硬上限 600 秒；Claude follow-up 最多 24 turns。
- 已测两次 haiku run 为 $0.19 / $0.25；这只是样本，不是价格承诺。
- Claude 可报告成本；Codex 当前记录可能为 NULL。`spendSince` 只能统计实际报告的成本，不能把 NULL 当免费，也看不到剩余额度。

#### 【建议】M4 dogfood 初始硬预算

- 默认关闭，和“每周自动回顾”分成两个开关。
- 每项目最短成功间隔：**7 天**；有到期 `recheck_after` 可提前，但同一项目 24 小时内最多一次。
- 全库自动 follow-up：**每天最多 1 次、滚动 7 天最多 3 次**。手动运行不占自动次数，但仍进统一串行队列。
- 每次最多 **5 条幸存提案**，由 app 硬截；超出直接丢，不留到下次。
- 某项目已有任何待审 batch 时跳过；全库待审总数达到 **10** 时暂停所有自动 follow-up，先让人处理入口。
- 成本字段可用时显示近 7 天实付；无论是否有成本字段，run-count 上限始终生效。
- 不自动在不同引擎间 fallback。无人值守时，用户选的引擎不可用就暂停并给一次可处理提示，避免订阅/成本边界悄悄变化。

这些数字是保守 pilot 建议，不是仓库既有拍板；正式值需要 Ocean 回答 §7。

### 4.3 静默条件

#### 【建议】真正的静默

以下情况不产生提案、不亮角标、不 toast、不留一张待手动关闭的右栏卡：

- 没到期；
- 项目 paused/done、没有 brief、未同意自动；
- 有未处理 brief 建议或待审 batch；
- 超过自动预算；
- 成功运行后没有任何候选；
- 所有候选都被 M3/硬规则判为重复或无效。

成功空跑仍可保留一条 `engine_runs` 审计记录，但自动将其视为 reviewed；历史/花费页可查，日常界面占 0 像素。

#### 【建议】不能静默的暂停

这些情况要合并成一次明确、可处理的状态，而不是每 30 分钟重复报错：

- 引擎未登录、额度/订阅不足、引擎不支持 web；
- 连续失败达到阈值；
- M3 hard gate、DB 或 state 写回失败；
- `follow_up_state` 损坏；
- 规则违例（无 URL、超过硬上限、提错项目）。

### 4.4 用户控制

#### 【建议】

- 专用总开关，默认 off；不能让现有 `aiAutoMaintain` 的“每周自动回顾”顺带开启联网跟进。
- 每项目至少三态：`手动` / `每周自动` / `暂停`；清空 brief 仍是完全关闭跟进。
- 开启总开关时先列出会自动运行的项目数、频率和全局上限；不能把所有现有 brief 默认为已授权自动。
- 项目状态改为 parked/done 时自动暂停；重新 active 后不立刻补跑，等用户恢复自动或下一个周期。
- 提供“立即跑一次”“跳过本次”“暂停 30 天”“关掉自动但保留 brief”。
- 用户改 brief 或批准建议时，若已有自动任务排队，应取消旧任务并要求重新按新 brief 计算；已经开始的任务不应让旧 brief 的结果悄悄进入待审面。
- 取消自动 run 不得让 scheduler 下一 tick 立刻重排；把“用户取消”当明确暂停信号。

### 4.5 失败恢复

| 失败 | 【建议】处理 |
|---|---|
| 网络短断 / 进程异常 / timeout | 不推进成功时钟；6 小时后最多重试 1 次，再失败暂停到次日 |
| 登录、额度、权限、CLI 不存在 | 不自动重试；提示一次，等设置/手动重试发生变化 |
| 用户取消 | 保留已发生的审计；定时路径丢弃未完整校验的部分提案，暂停该项目本周期 |
| 去重/URL 校验/DB 写回失败 | fail-closed；候选不显示，run 标失败，不推进成功时钟 |
| `follow_up_state` JSON 损坏 | 不按当前“退化为空历史”自动跑；暂停该项目并要求一次手动恢复/重建，避免无人值守重复灌入 |
| app 睡眠/完全退出错过时间 | 下次恢复只跑最优先 1 个，不追补 N 次历史周期 |
| brief 在排队后变化 | 丢弃旧任务；以新 brief 重新计算，不让旧指令继续出网 |

现有 weekly review 的失败不会算成功，因此每 10 分钟 tick 都可能再次尝试。这个策略不能复制到联网 follow-up；它会把额度错误变成自动重试风暴。

## 5. 监测与验收方案

### 5.1 先验收手动 M3（关闭闸门一）

用 §2.1 的 3 周 / 6 次 dogfood 表。由于现有库无法可靠关联 run→proposal→approved block，价值判断应由 Ocean 当次记一行，不新增隐形遥测，也不为了统计保存驳回内容。

至少记录：

- 项目 / 日期 / brief 版本；
- 成功、失败、取消；
- CLI / model / turns / duration / reported cost；
- 模型提案数、硬闸删除数、最终待审数；
- 批准数；
- Ocean 的“有用/无用”与一句理由；
- 无源、旧闻、跑偏、误吞已知变化。

### 5.2 M4 实现前的自动测试矩阵

#### 【建议】纯调度/数据库测试

- master off、项目 manual、active/parked/done、空 brief、pending suggestion、pending proposal；
- last success 与失败/取消/空跑的区别；
- UTC `recheck_after` 的到期边界；
- due block 已 stale 时不触发；无 brief 时只提醒不出网；
- 全局 1/day、3/week、每项目 24h/7d；排序稳定且每次只取一个；
- 连续失败退避，重启后仍能由 `engine_runs` 推导；
- app 睡眠跨过多个周期只补一次；
- 手动与自动同时到期、第二窗口同时 enqueue；
- brief 排队后被编辑/关闭；
- 选中 Gemini / 引擎消失 / 不允许 fallback。

#### 【建议】M3/M4 联合测试

- 外部 MCP 客户端在 run 窗口内向别的项目/同一项目提案，不能被本次 sift 读取或删除；
- hard gate 抛错时，零提案可见、outcome 非 ok、成功时钟不动；
- content 无 URL、URL 只在 annotation、6 条、24 条均按 follow-up 专属规则处理；
- 同 URL 同结论删除；同 URL 真变化在 `recheck_after` 到期时能通过；
- 批内重复、跨 run 同义改写、中文全角标点；
- 自动空跑没有 toast / badge / 未处理卡，但有审计与成本；
- 失败/取消留下的部分提案不进入无人值守待审面。

### 5.3 真实 CLI pilot 验收

在隔离库与真实 CLI 上至少覆盖：

1. 两个项目同日到期，只跑一个，另一个下次机会再跑；
2. 一个项目有过期 `recheck_after`，旧 URL 页面真的改变；
3. 没有新东西，完整静默；
4. 模型违反 URL/5 条规则，被 app 硬闸拦住；
5. 网络/额度失败，退避且不重试风暴；
6. 用户在运行中关掉自动或修改 brief；
7. 外部 MCP 客户端同时提案，互不污染。

### 5.4 建议的 M4 pilot 通过线

- 零自动直写 block；所有新内容仍先到待审面。
- 零无源幸存提案、零超过 5 条、零跨项目误删/误收。
- 没新闻的运行日常界面完全静默。
- 失败不会推进成功时钟，不会在一天内反复扣额度。
- 4 周内待审总数不超过设定上限，且用户没有因为积压关闭整个功能。
- Ocean 明确确认自动产出中至少 3 次对决定/行动有用，并接受实际花费与频率。
- “仍有效内容的出口”已经落地并被真实用过，或 Ocean 明确重定义并豁免这道闸。

## 6. 现阶段可以做与不该做的事

### 【建议】现在可以做

- 用现有手动“联网搜索”完成 3–4 周价值取证。
- 每次手工记录一行结果，不改 schema，不保存驳回正文。
- 让 Ocean 回答 §7 的产品决策。
- 若单独排修复窗，可先修 M3 与自动化无关也成立的硬闸缺口；但这不代表 M4 获准。

### 【建议】现在不该做

- 不实现 scheduler、schema、UI。
- 不用 `following_up=true` 自动打开所有项目。
- 不把 `lastRunAt` 或 `updated_at` 直接当成功/brief 变化时钟。
- 不复用 weekly review 的 10 分钟失败重试。
- 不因官网/case-study 已完成就默认容量出口已经存在。
- 不把隔离库 5→3 的技术成功写成“用户价值已证明”。

## 7. 需要 Ocean 回答的问题

1. **“往外拿”到底是哪一种？** 是“Spool 的材料被用于对外交付”，还是“仍有效内容能安全退出活跃 Pack”？若是前者，是否明确撤销 §9.5 的 14 周容量闸？
2. **M3 价值闸怎么判过？** 是否接受本报告建议的 3 周 / 6 次 / 2 项目、至少 3 次明确有用？
3. **自动同意粒度是什么？** 一个总开关覆盖所有已有 brief，还是每个项目单独同意？本报告建议后者。
4. **频率选哪种？** 固定每周、只按 `recheck_after`、还是二者混合？本报告建议混合，但 due 优先、每项目成功间隔默认 7 天。
5. **项目状态规则？** parked/done 是否一律暂停？重新 active 后是否需要再次确认？
6. **预算是否接受？** pilot 先每天 1 次、7 天 3 次、待审 10 条暂停、每次硬上限 5 条。
7. **引擎不可用时怎么办？** 暂停等待，还是允许自动 fallback 到另一订阅引擎？本报告建议不 fallback。
8. **同 URL 在 90 天内变了怎么办？** 是否同意 `recheck_after` 到期时允许带明确变化说明的新结论通过，而不是 URL 一撞就吞？
9. **没有 brief 但 `recheck_after` 到期怎么办？** 只提醒用户，还是允许临时联网？本报告建议只提醒。
10. **空跑是否完全静默？** 是否同意不 toast、不角标、不留未处理卡，只保留已 reviewed 的审计/成本记录？
11. **连续失败怎么通知？** 一次合并提示后暂停，还是每个项目各报？本报告建议合并并暂停。
12. **每项目自动状态存哪里？** 不应静默继承旧 `auto_maintain=1`；Ocean 是否接受以后为自动联网做一次明确的 per-project 数据决策（必要时才另排 schema）？

## 8. 最终判断

**【仓库已知事实】** M1/M2/M3 的手动链、待审闸、URL/指纹去重、运行审计、成本字段、`recheck_after` 和一个 app 内机会型 scheduler 先例都已经存在，M4 不需要从零发明后台系统。

**【推论】** 但当前基础只能支撑“继续手动验证”，还不能支撑“无人值守后仍然省钱、静默、不会误吞变化、不会污染别人的提案”。自动化会放大现有 M3 的 fail-open、时间窗归属、同 URL 变化、软约束 5 条/URL 等边界。

**【建议】** 保持 M4 为 NO-GO。先由 Ocean 用现有 M3 跑出一段真实价值证据，并明确“往外拿”的口径；两道闸都关闭后，再按“机会型单队列 + recheck 优先 + 硬预算 + fail-closed + 明确逐项目同意”的形状实施。
