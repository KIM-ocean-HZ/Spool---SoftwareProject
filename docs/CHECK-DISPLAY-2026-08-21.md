# 屏幕尺寸自查 —— 2026-08-21

> 起因：Ocean 把 Mac 从 **More Space（1800×1169）** 换回 **默认（1512×982）**，
> 问「前端是否标准」以及「app 有没有对不同尺寸的电脑做兼容」。
>
> ⚠️ **这一份是实测 + 读码，不是猜的。** 实测数据在 §1，⛔ 结论在 §2。
>
> ✅ **2026-08-21 当天已修复并实机验过 —— 修法和验证结果在 §7。**
> 一句话：`1600×1000 @ (100,51)`（右边掉 188 点）→ **`1512×879 @ (0,32)`，整窗在屏内**。

---

## 1. ⛔ 实测：主窗现在有一大块在屏幕外面

**当场量的**（Spool 正在跑，pid 9925，System Events 读的窗口几何）：

| 量到什么 | 值 |
|---|---|
| 屏幕（物理 / 逻辑） | 3024×1964 Retina → **逻辑 1512×982**（默认档，确认了） |
| Spool 主窗**尺寸** | **1600 × 1000** |
| Spool 主窗**位置** | x=100, y=51 |

**算一下右边和下边到哪了：**

```
横向：窗口 x 从 100 到 100+1600 = 1700，屏幕只到 1512
      → ⛔ 右边有 188 点在屏幕外

纵向：窗口 y 从  51 到  51+1000 = 1051，屏幕只到  982
      → ⛔ 下边有  69 点在屏幕外
```

⛔⛔ **右侧栏宽 340 点，它整个贴在窗口最右边 —— 188/340 = 它有 55% 看不见。**

**这不是偶发**：仓库里没有窗口状态持久化，每次启动都按配置开成 1600×1000
（`src-tauri/tauri.conf.json` 第 18–19 行）。**在这块屏幕上，每一次启动都是这样。**

## 2. ⭐ 原因找到了，而且修法已经写好了 —— 只是被关在 Windows 那边

`src-tauri/src/lib.rs:665` 有一个函数叫 `fit_main_window_to_work_area`：
它问系统要「这块屏幕真正能用的矩形」，量出标题栏和边框占了多少，
然后把窗口缩到装得下、再居中。**正是这次需要的东西。**

但它上面挂着一行：

```rust
#[cfg(target_os = "windows")]     // ← lib.rs:665，调用点 lib.rs:529 也有一行同样的
```

**它只在 Windows 上编译。** 函数自己的注释写着为什么：

> Ocean, 2026-08-17（2560×1600 laptop）:「打开之后底部一小部分被 windows 的程序坞挡住了」
> …… **Nothing on macOS reports this**, and the port's rule is that Mac behaviour does not
> move, so this is gated rather than shared.

⭐⭐ **「macOS 上没人报过这个问题」那句话，在写下它的那天是对的** ——
那天 Ocean 的 Mac 是 More Space（1800×1169），1600×1000 **装得下**。
**今天他换回默认档，这句话就过期了。而代码不知道它过期了。**

> ⚠️ 这和这一轮 §9.13 查的是**同一种毛病**：一条在它自己的范围里完全正确的结论，
> 被带到范围外面继续用。这次它长在代码里，不在文档里。

## 3. 这块屏幕装得下吗 —— 不止你这一台

配置里的 **1600×1000** 是逻辑点。常见 Mac 的默认档：

| 机器 | 默认逻辑分辨率 | 1600×1000 装得下吗 |
|---|---|---|
| MacBook Pro 14"（**你这台**） | 1512×982 | ⛔ **横竖都装不下** |
| MacBook Air 13" | 1470×956 | ⛔ **横竖都装不下** |
| MacBook Air 15" | 1710×1112 | ✅ 装得下 |
| MacBook Pro 16" | 1728×1117 | ✅ 装得下 |
| 外接 1080p | 1920×1080 | ⚠️ 横向可以，**纵向 1000 + 标题栏 + 菜单栏 + 程序坞 会顶到** |

⛔ **两款最常见的 Mac 笔记本，默认档都装不下。**
而现在真实外部用户是 0 —— 也就是说**第一个真人打开 Spool，很可能就看到一个跑到屏幕外的窗口。**
这是漏斗上的洞，不是使用习惯问题。

## 4. ⭐ 好消息：三栏布局本身是好的，它真的会跟着窗口缩

`src/lib/layout.ts` 那套是认真写的，**不是固定像素**：

- 左侧栏 = 窗口宽的 **1/6**，夹在 [260, 300] 之间（`SIDEBAR_SHARE`）
- 右侧栏用户可拖，夹在 [左侧栏+40, 480]
- 中间阅读区有下限 520，**不够的时候按「先挤右栏、再挤左栏」的顺序让位**（`resolveLayout`）

按这套算出来（右栏取默认 340）：

| 窗口宽 | 左栏 | 右栏 | 中间 | 两栏占比 | |
|---|---|---|---|---|---|
| 1800 | 300 | 340 | 1160 | 35.6% | |
| 1600 | 267 | 340 | 993 | 37.9% | |
| **1512** | **260** | **340** | **912** | **39.7%** | ⭐ 装得下的话，这个比例是健康的 |
| 1360 | 260 | 340 | 760 | 44.1% | |
| 1024 | 260 | 244 | 520 | 49.2% | ⚠️ 触发挤压 |
| 900 | 200 | 180 | 520 | 42.2% | ⚠️ 触发挤压 |
| 860（配置的最小值） | 200 | 180 | **480** | 44.2% | ⛔ **中间掉到 480，低于它自己写的 520 下限** |

⭐ **结论：只要窗口装得进屏幕，1512 这一档的版面是正常的**（中间 912 点，两栏 39.7%）。
**问题 100% 出在窗口比屏幕大，不出在版面。**

## 5. ⚠️ 顺带查出来的三条小问题（都不急）

| | 什么 | 说明 |
|---|---|---|
| **①** | **左侧栏那个「按比例缩放」在 Mac 笔记本上其实没生效** | `SIDEBAR_SHARE = 1/6` 是照着 1800 调的（1800/6 = 300，正好顶到上限）。但 **窗口宽度低于 1560 时，1/6 就掉到 260 以下、被下限夹住** —— 也就是说在 14"/13" 上它**恒等于 260**，是个常数，不是比例。⚠️ 不是 bug，但注释里「a hard-coded 1800 would be this laptop baked into the product」这个初衷，在小屏上没兑现 |
| **②** | **最小窗口 860 的时候，中间区违反自己的下限** | 见上表最后一行：480 < 520。`resolveLayout` 的注释承认了这种情况（「genuinely tiny window」），⚠️ 但 `minWidth` 定成 860 就等于**允许用户拖到一个版面已经破了的宽度**。要么把 `minWidth` 提到 900，要么承认 520 只是个「尽量」 |
| **③** | **全项目 0 个 `@media`、0 个 tailwind 响应式前缀** | 对桌面 app 来说**不算问题**（版面是 JS 算的，不是 CSS 断点），记一笔是为了以后别以为有 |

⭐ **对话框类都是对的**：宽度固定（480–640）但**高度一律用 `vh`**（`max-h-[72vh]`、`80vh`…），
在 982 高的屏上照样正常。⛔ **别顺手去改它们。**

## 6. 关于「在设置里加一个 display 切换」

⚠️ **这条办不到，而且不需要办。** app 改不了 macOS 的显示缩放 ——
那是「系统设置 → 显示器」里的东西，任何 app 都碰不到。

⭐ **而你实际做的那一步（把系统切回默认档，然后让我测）是对的**，它当场就逼出了 §1 那个 bug。
**要修的不是「让用户在 Spool 里切屏幕」，是「Spool 开在哪块屏幕上就装得进哪块屏幕」** —— 也就是 §7。

## 7. ✅ 已修复 —— 改了什么，实机验成什么样

### 7.1 改动（`src-tauri/src/lib.rs`，两行）

去掉 `fit_main_window_to_work_area` 的两道 `#[cfg(target_os = "windows")]`
（调用点一道、函数一道）。**函数体一个字没改** —— 它问系统要 work area、量标题栏、
缩到装得下、再摆回屏内的逻辑本来就是平台无关的。

⭐ 顺带确认了一件事：`work_area()` 在 macOS 上**是实现了的**，走
`NSScreen.visibleFrame`（`tauri-runtime-wry/src/monitor/macos.rs`），
**菜单栏和程序坞都已经排除掉**。所以不需要写任何 Mac 专用分支。

### 7.2 ⭐ 实机验证结果（隔离构建，⛔ 没碰真库）

按 `isolated-verify-workflow` 那套走：identifier 临时改成一个**没人认领**的
`com.oceanjin.spool.dispcheck` → `npx tauri build --bundles app` → `open` → 量窗口。
验完已 pkill、注销 LaunchServices、删 bundle、删隔离数据目录、还原 identifier。

| | 修之前 | 修之后 |
|---|---|---|
| 窗口 | `1600 × 1000` @ `(100, 51)` | ⭐ **`1512 × 879` @ `(0, 32)`** |
| 右边界 | 1700 → ⛔ **超出屏幕 188 点** | 1512 → ✅ **正好贴住屏幕右缘** |
| 下边界 | 1051 → ⛔ **超出屏幕 69 点** | 911 → ✅ **屏内，底下 71 点留给程序坞** |
| 右侧栏 | ⛔ **55% 在屏幕外** | ✅ **整条可见，折叠按钮也在屏内** |

**连开三次量了三次，`(0, 32) 1512×879` 一次不差。**

⭐⭐ **而且截图量出来的三栏宽度，和 §4 那张算出来的表对上了**：
左栏 ≈ 260、中间 ≈ 912、右栏 ≈ 340。**§4 不再是纸面推算，是验过的。**

> ⚠️ 参照：Ocean 手动把正式版窗口拉/缩到合适之后是 `1512 × 870 @ (0,32)` ——
> **修完之后自动落到的位置，和他手动调出来的几乎一模一样。**

### 7.3 ⚠️ 还有一条没验，需要你换回 More Space 时看一眼

**验收 ②「More Space（1800×1169）下窗口仍然是 1600×1000、一点没变」还没验** ——
我改不了你的显示设置，也不该替你改。

⭐ 但它走的是函数开头那句 `if inner <= max { return; }` 的**提前返回**，
装得下就一行都不执行。这条路径自 2026-08-17 起就在 Windows 上跑着。
**风险低，但你哪天切回 More Space 顺手看一眼窗口是不是还是老样子就行。**

### 7.4 ⚠️ 「居中」是什么意思 —— 你问的那个

我上一轮说「要不要顺带居中是个单独的决定」，**这句是我说错了，它不是可选项。**

原因：`set_size` 只改**大小**，不改**位置**。窗口原来在 x=100，
就算把宽度从 1600 缩到 1512，它还是从 x=100 开始 —— 右边照样掉出去 100 点。
**所以缩完必须挪，不挪等于没修。**

「居中」只是**挪到哪**的答案里最简单、且四条边一定都在屏内的那一个。
实测落点是 `(0, 32)`：横向正好占满、纵向贴在菜单栏底下。
⛔ **装得下的窗口不会被挪** —— 提前返回在前面就退出了，位置一动不动。

## 8. 一句话回答你那两个问题

> **「前端是否标准？」** —— **版面标准，窗口不标准。**
> 1512×982 下三栏比例是健康的（中间 912 点、两栏 39.7%），
> 但窗口开成 1600×1000，**右边 188 点、下边 69 点在屏幕外，右侧栏 55% 看不见。**
>
> **「有没有对不同尺寸做兼容？」** —— **布局一直有，窗口刚补上。**
> 三栏会跟着窗口缩、有下限、有挤压顺序，写得很好；
> 缺的是「窗口本身装得进屏幕」，那段代码其实早就有，只是被 `#[cfg(target_os = "windows")]` 关着。
> ✅ **2026-08-21 已把门去掉并实机验过（§7）。**
