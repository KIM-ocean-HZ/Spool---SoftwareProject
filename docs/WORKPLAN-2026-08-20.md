### 2.6 ✅ 表头第八条 —— 你说没看懂，这里重写一遍（2026-08-20 已批：做）

原文写得太术语了，是我的问题。用真的 pack 字节讲一遍。

**现在 pack 里，一个块长这样**（这是真的，出自 golden fixture）：

```
#5 [2025-06-15 15:06] 我的想法:先复现 baseline 再谈改进,别一上来就魔改
#6 [2025-06-15 15:16 · from Claude · MCP] 结论:除以 sqrt(d_k) 是为了控制点积方差
```

看出 #5 和 #6 的区别了吗？**#5 没有 `· from XXX` 那一截，#6 有。**

表头开头那一大段（「How to Read This Context」）教了 AI 一条规则：
**没有来源的 = 💭 Personal = 用户自己敲的，信号最强。**

所以 AI 读到 #5 的时候，要做这么一件事：

> 「唔，#5 这一行……我找找 `from`……没有 `from`……
>   我回想一下三千字之前那个表头是怎么说的来着……哦，没有来源的算 Personal。」

**这就是第八条要干掉的东西。** 三个毛病：

1. **它靠「找不到东西」来判断。** 「有 `from Claude`」是看见了才算数，
   「没有 from」是**看了一圈没看见**才算数。后者天然比前者弱。
2. **它靠记住表头。** 读到第 80 个块的时候，三千字之前那段规则的注意力已经掉下去了。
3. **它是唯一一个还要靠记忆的判定。** —— 这条最关键，见下。

**第八条要做的事，一句话：把 💭 直接印在那一行上。**

```
💭 #5 [2025-06-15 15:06] 我的想法:先复现 baseline 再谈改进,别一上来就魔改
   #6 [2025-06-15 15:16 · from Claude · MCP] 结论:除以 sqrt(d_k) 是为了控制点积方差
```

就这么多。**AI 不用回想表头了，也不用靠「没找到 from」推理了，字就写在眼前。**

**为什么只做两带、不做四带？**

四个带里，判定方式不一样：

| 带 | 怎么判的 | 渲染器能不能自己打？ |
|---|---|---|
| 💭 Personal | 没有 `source` 字段 | ✅ **能**，纯查字段 |
| 💭 Personal | 是 `note:` 那一行 | ✅ **能**，纯查字段 |
| 📖 Reference | 来源是不是机构/邮件/附件 | ❌ 要看内容，会判错 |
| 🧩 Synthesis / 🔄 Process | AI 来源，再看**内容形状**像文章还是像对话 | ❌ 要读内容，只有 AI 判得了 |

**下面两行是纯查字段，上面两行要读内容。** 能确定的那两行就别让 AI 猜——
四带里正好有两带是白送的。

**这条为什么值得做（真正的理由）：**

pack 里已经有一堆**印在行内**的记号：`📌` 置顶、`⚠️` 后面被纠正过、`↩` 引用了谁。
这些记号有个共同点：**它们出现在需要它的那个块上，所以就算表头已经被忘了，它们照样生效。**

而四带分类是**唯一一个**不这样、只写在表头里的东西。
也就是说，**它是整份 pack 里最先失效的那部分**。第八条把其中一半挪到行内，
让它和 `📌`、`⚠️` 一样抗遗忘。

## 4. 定位：不做工作版（已定，别再翻）

**结论：不做「工作版」，做「和办公软件并排装的项目记忆层」。**

一句话定位：**给 AI Agent 用的项目记忆层，装在你公司的办公软件旁边**——而不是「一款办公软件」。

**2026-08-18 企业微信 5.0.10 对所有企业开放 CLI 与 MCP**（11 类办公能力，取消人数门槛）。
这件事的三层含义：

1. **「给企业微信做中转」这个位置，腾讯自己占了。** 何况那条路本来就走不通——
   2022-06 起新建自建应用必须配可信 IP 白名单，动态 IP 上的本地桌面应用拿不到入场券。
2. **但腾讯放出来的是「动作能力」，不是「跨天记忆」。** wecom-cli 能读文档、建日程、拉纪要，
   它不回答「这个项目三周前为什么否掉了方案 A」。
3. **那一层是空的，而 Spool 正好是那个形状。**

### 4.1 一个应该前置的定位论据

**零出网在中国企业环境里不是包袱，是最强的过审论据。**
很多公司明令禁止内部数据外传，Spool 是唯一一个「装了也不会往外发一个字节」的东西。
配合「一次性买断 + 离线签名许可证」，恰好是采购最容易签字的组合。
反倒是工作版——要账号、要同步、要上传——最难过审。

> ⚠️ 这条论据与 §6 的 API 引擎有直接张力。选了形态 C，这句话要精确化，见 §6.3。

### 4.1.5 🆕 你问的：企业微信开放了 CLI 和 MCP，Spool 是不是能接进去？

**能。而且要做的工程量是零——今天就能用。**
但「让企业微信读取 Spool」这个说法要掰一下，因为方向反了，而**方向反了这件事恰好是好消息**。

**先看这两样东西各是什么角色：**

| | 是什么角色 | 谁主动 |
|---|---|---|
| **Spool** | MCP **服务端**（`spool --mcp`，等着被连） | 被动 |
| **企业微信** | MCP **服务端** + 一个 CLI（`@wecom/cli`） | 被动 |

**两个都是「被连的一方」，所以它们俩永远不会互相说话。**
「企业微信读取 Spool」这件事，字面上不会发生——企业微信不会主动伸手过来。

**真正发生的是这个：**

```
          你的 AI 客户端（Codex / DeepSeek Harness / Kimi Work…）
                        ↙                    ↘
              连 Spool（MCP）          连企业微信（MCP 或 CLI）
                   ↓                            ↓
            读你的项目记忆              读文档/纪要/日程/待办
                        ↘                    ↙
                    AI 在中间把两边搬来搬去
```

**搬运工是 AI，不是 Spool，也不是企业微信。**
所以「企业微信写进 Spool」的真实形态是：
**你对 Codex 说一句「把刚才那个会议纪要归到 Spool 的 X 项目里」，它就做了。**

**这为什么是好消息 —— 它绕开了 §4.2 第 1 条那个死结。**

§4.2 说读日程/云盘走不通，理由是**「自建应用必须配可信 IP 白名单，动态 IP 上的桌面应用拿不到入场券」**。
那条判断针对的是「**Spool 自己去做一个企业微信应用**」。

**而现在这条路上，Spool 根本不需要成为企业微信应用。**
凭证在 `wecom-cli` 手里（`wecom-cli auth init` 扫码登录，是用户自己的身份），
Spool 从头到尾不知道企业微信的存在。**没有应用，就没有可信 IP 这回事。**

> **一句话：那个死结锁的是「Spool 连企业微信」这条路，
> 而现在走的是「AI 同时连两边」这条路，锁根本不在这条路上。**

**要做什么？—— 一件事，而且是最便宜的那种：写字。**

Spool 的 routing text（`OPENERS` / `INSTRUCTION_BODY`）里加几句，让 AI 知道
「读完企业微信的东西之后，该归到哪个项目里去」。**一行代码逻辑都不用改。**
这正是 §4.2 第 7 条已经裁决过的做法（「降级为 routing text」），
只是当时没意识到它同时也解决了第 1 条和第 2 条。

⚠️ **两个必须提醒的现实：**

1. **企业里得管理员点头。** 企业微信那侧有「人员与 AI 操作权限独立配置、
   关键动作人工审批、AI 授权会过期、全程审计」。这是**好事**（正是 §4.1 说的过审论据），
   但意味着**你自己一个人试不出真实企业场景**——你没有一个真企业。
2. ⛔ **别把它做成一个功能去宣传。** 现在能说的是「Spool 和企业微信可以在同一个 AI 里并用」，
   **不能说「Spool 支持企业微信」**——后者暗示有对接、有维护、有保证，
   而实际上中间那一段完全不由你控制，企业微信改一次 API 你就变成撒谎的人。

📌 **一个顺带捡到的东西，比上面整段都值钱**：
企业微信自己的分发方式是 **`npx skills add WecomTeam/wecom-unified -y -g`**
—— **就是 §3.1 里那条 skills.sh 渠道。**
腾讯在用这条渠道发东西，说明这条渠道是活的、有人走的。
**§3.1 那个「发四带格式当 skill」的计划，因此从「猜测」变成了「有先例」。**

#### 6.4.1 压缩进 pack：你说得对，我原来那条建议是错的

**你的原话**：「如果压缩不进 pack，那它节省上下文就没有意义了。」

这句是对的，我原来那条「建议否」站不住：压缩的**唯一目的**就是让 pack 变小，
产物不进 pack，就等于花钱买了一份没人会读的副本。**采纳你的。**

**但「核对无误后直接替换原文本」这个动作，要换一种做法实现**，理由只有一条：

> **这个库里唯一不可再生的东西，是你当初粘进去的那段原文。**
> 模型可以再跑一次，网页可以再抓一次，唯独「2026 年 3 月你从招生页上复制的那一段」，
> 删了就没了。压缩必然丢信息——这是它的定义，不是它的 bug。
> 用一个必然有损的产物去覆盖一个不可再生的原件，只要错一次就找不回来。

**做法：把它接到你已经有的那套机制上，一行新概念都不用发明。**

库里本来就有 `supersedes` / `corrects` / `cites`（§2.5 说它们「已经在数据里」）。
压缩就是 `supersedes` 的一个新用例：

```
你点「压缩」
  → sidecar 跑，回来一份压缩稿
  → 界面并排放：左边原文，右边压缩稿，中间标出压掉了哪些句子
  → 你逐条核对（可以改字，可以整段驳回）
  → 你点「用这一份」
  → 压缩稿存成一个新块，标 supersedes 原块
  → 原块留在库里，从 pack 默认路径里退下来，pack 里印一行
     「↩ 这里原本是 #7，压缩后长这样，原文一键可取」
```

**这样四件事同时成立**，一件都不用牺牲：

| 你要的 | 怎么拿到 |
|---|---|
| pack 真的变小 | 默认路径里走的是压缩稿，体积立刻降下来 |
| 你核对过才生效 | 不点「用这一份」，库里什么都不变 |
| 原文没丢 | 原块还在，`supersedes` 指着它，一键展开 |
| **pack 还是确定性的** | 关键在这 —— 见下面那段 |

⚠️ **「pack 还是确定性的」这一条别当成细节，它是钱。**

区别在于**压缩发生在哪一步**：

- ❌ **压缩在 pack 的热路径上**（每次生成 pack 时现调 AI）：
  同一个项目每次吐的字节都不一样 → **前缀缓存永远命中不了** →
  §6.2 那个 30 倍、那一到三分钱，**全部作废**。而且你会失去「pack 可复现」这个卖点。
- ✅ **压缩在写入路径上**（你核对后存成块，pack 照旧纯字符串组装）：
  pack 仍然是「给定块集合 → 唯一确定的字节」。**AI 不在热路径上，缓存照常命中。**

**换句话说：你要的「压缩进 pack」，和我要的「pack 不许有 AI」，本来就不冲突——
冲突的是「压缩在读的时候发生」还是「在写的时候发生」。放在写入路径上，两边全要到。**

**你提的提示词调教也接在这里**：压缩比例做成一个显式档位
（比如「只删重复」/「保留结论和数字」/「压到最短」），
默认最保守那档。**这比在提示词里写「请少删一点」可靠得多**——
后者是求模型自觉，前者是给它一个能被核对的目标。
每一档都要在压缩稿顶部写清：原始 N 块 → 压缩后 M 块，删掉了哪几类东西。

**第一步动哪个文件**：`compress_pack` 一个动作先跑通形态 C，
产物先只做「并排核对」界面，**暂不接 `supersedes` 写入**——
先确认压缩质量你认可，再开写入那一段。质量不认可的话，后面那半段就不用做了。

#### ⛔ 08-20 第二次失败：一次超时**花了 ¥0.08 却一个字都没拿到**

26,615 字符那份 pack，180 秒还没写完就被掐了，而 DeepSeek 那边**已经计费 ¥0.08**。
界面报的是「可能不是一个 OpenAI 兼容的接口」——**和上一次同一种错法**：把超时说成了别的东西。

**根子不是超时设小了，是「不流式」。** 不流式意味着三件事同时成立：

1. 整个生成期间**一个字节都不到**，所以界面分不出「正在正常写」和「卡死了」；
2. 超时只能按**总时长**算，于是一次正常但慢的生成和一次真卡死长得一模一样；
3. 掐断之后，**已经付过的那部分全部作废**。

已改成**流式**，三件一起解决：现在界面上显示「模型在思考…已经想了 3,200 字」→
「正在写压缩稿…已经写了 8,100 字」，字数一直在涨就说明没卡住。
超时上限也从 180 秒提到 **600 秒**（可调到 30 分钟）——「一次几十秒的调用」这个前提本来就是错的。

⚠️ 顺带一条给对外说法的：**这个模型是先想完再动笔的。** 中途掐断不会拿到半份稿子，
只会拿到账单。这句话以后写进任何「成本很低」的宣传之前都要先说清楚。

**块没变、内容没变、提示词没变，只有表头那个日期变了**，缓存命中就从 **97% 掉到 16%**。

这把 §9.1 里那个悬着的问题测完了，而且两边都测到了：

- **同一天再压一次** → 97% 命中。pack 逐字相同，**确定性确实赢了**。
- **隔一天再压一次** → 16% 命中，只剩提示词那一截（512 token ≈ system 那段）。
  ⚠️ **`PACK_HEADER` 里那句 `Generated by Spool on <日期>` 就是断点**，和 §9.1 判断的一样。
  而且真实场景更偏向这一边：**你会去重复压缩，通常是因为过了一段时间、或者加了新块。**

#### ⛔ 但真正的结论是：命中还是不命中，**几乎不影响账单**

第 3 次和第 4 次输出量几乎一样（24,242 / 23,513），命中率差了 6 倍，
**账单差 ¥0.0006 —— 0.5%。**

> **缓存能不能命中，在这个调用形状下根本不重要。**
> 输入只占总花销 8%，无论怎么命中，天花板就是 8%。
> §6.2 拿「确定性 × 缓存」当护城河、并由它推出「一到三分钱」，**这条推理链整根断了**。
> ⚠️ 注意这不是「缓存做得不好」——**缓存做得非常好（97%），只是它省的那部分太小**。

#### 质量：四次里三次没打中自己的目标

「只删重复」这一档写的目标是压到原文的 **50–75%**。实测 90% / 73% / 84% / 85%，
**只有第 2 次达标**。同样的输入、同样的档位，结果在 73%–90% 之间晃。
⚠️ 显式档位本来是要把「请少删一点」换成一个能核对的目标，现在它只是**半数时候能达标**。

**建议下一次换「保留结论和数字」那一档**（目标 25–50%）看看，而不是继续在最保守档上取样。

#### 9.6.5 ✅ ④ 核对界面：按**块**核对，用**渲染后**的文本 —— **已做（2026-08-21）**，顺手查出七个毛病见 §9.7.2

**Ocean 的原话**：「删除内容划线的可视化我认可，但是前后文本一一对应仍然不够直觉性，
用户可能看不懂删了什么…转移到右侧面板后应该使用渲染后文本，但是仍然体现出 personal 等等这种文本地位。」

**病根**：现在比的是**两大坨 pack 纯文本的行**。而用户脑子里的单位**不是行，是块**。
一行一行对齐读，本来就读不出「第 3 块被合并进第 2 块了」这种事。

**改法：一块对一块。**

```
┌─ 💭 #2  [2026-08-20 13:50 · from 重新设计Spool宣传物料和视频 - Claude]
│  1,359 → 890 字符（剩 65%）
│  ┌── 原文（渲染后）──────────┬── 压缩稿（渲染后）────────┐
│  │ …划掉的地方是删掉的…        │ …黄底的是它自己写的…       │
│  └────────────────────────┴──────────────────────┘
└─ note: 这条是硬要求 ✅ 原样保留
```

**要点**：

| 要做的 | 为什么 |
|---|---|
| **按 `#N` 把两边切开配对** | `countPackEntries` 已经认得条目行（`(📌\|💭\|🗜)? #N [`），复用它 |
| ⚠️ **配不上要明说** | 模型漏了一块或者改了编号，必须显示「**第 3 块在压缩稿里找不到**」，⛔ 不许静默跳过 |
| **每块头上带四带记号**（💭 / 📖 / 🧩 / 🔄）和来源 | Ocean 点名要的「体现出 personal 这种文本地位」。⚠️ 记号从**原块**取，不从压缩稿猜 |
| **正文用渲染后的样子** | 和 `ThreadView` 里看到的一致；纯文本对比是在让用户读渲染器的中间产物 |
| **每块单独报字符数** | 「整份剩 72%」看不出是谁被压了；一块一块报才知道它动了哪儿 |
| **核对（`auditCompression`）也按块报** | 现在是整份报「少了 2 条批注」，按块之后能直接指到是哪一块少的 |

⚠️ **技术上的难点写在这儿，别到时候才发现**：压缩稿回来是**纯文本**，
要按块渲染就得**先把它解析回块**。靠 `#N [` 行切是可行的，但**模型可能不守规矩**——
所以解析失败必须是一个**可见的结果**（「这一份没法按块对照，退回整份文本对照」），
不是一个异常。

#### 9.6.6 ✅ ⑤ 项目压缩 / 单块压缩 —— **已做（2026-08-21）**

**Ocean 的原话**：「可以项目压缩也可以 block 压缩，思考交互逻辑应该如何设计。」

**两个入口，同一张核对桌子**（正好是 §9.6.5 那张）：

| 入口 | 在哪 | 送去的是什么 | 核对面上是几对 |
|---|---|---|---|
| **压缩这个项目** | 右侧栏 | 整份 pack | N 对 |
| **压缩这一块** | 块自己的菜单 | ⚠️ 见下 | 1 对 |

⚠️⚠️ **单块压缩是另一件事，不是"项目压缩缩小版"，这一条必须在界面上说清楚**：

> **压缩干的主要活是「合并重复」，而重复是跨块的。**
> 单独压一块，它只能把这一块自己的话说短，**看不见别的块，也就删不掉重复。**

所以：

- **「只删重复」这一档，单块压缩基本无事可做** —— 要么在单块模式下**不给这一档**，
  要么给了就明说「这一档需要整个项目一起压」。
- **「压到最短」在单块上是成立的**（它就是把一块自己的话说短）。
- ⭐ **推论**：单块压缩最适合的是**那种一块特别长的项目**（比如一整篇网页正文），
  而不是「一块一块把项目压完」——后者花的钱更多、效果更差。

**存哪儿**：两条路都通向 §6.4.1 那套 `supersedes` —— 压缩稿存成新块、指向原块、
原块退出默认路径但一键可取。⛔ **那一段仍然锁着**，条件没变：Ocean 说质量认可。

4. ⛔ **§9.5 那个「缓存论据塌了」，这一轮坐实了**：命中率中位 **99%**，
   而输入只占账单 **16%** —— 缓存能省的天花板就是这 16% 的一部分。
   **账单的大头是「思考」：它占输出的中位 57%（0–80%），而思考按输出价计费。**
5. ⚠️ **「压到最短」第一次有数据了：68–81%（10 次）**，目标写的是 10–25%。
   ⛔ **它并不比上一档更短**，但它**丢东西最多**（见 §9.9 第二条）。

### 9.9 ⛔ 压缩质量的评判 —— **我作为压缩后文本的使用者，判定：现在不能解锁写入**

> **Ocean 2026-08-21：「你 AI 作为压缩后文本的使用者，你来评判压缩质量更加权威。结合测试给出你的评判。」**
>
> 好。下面这一节是我的判断，不是转述实测。**结论：不认可，写入那一段不解锁。**
> 但理由不是「模型不够好」——是**这个功能现在问错了问题**。

#### 一句话

> **它压得动的时候会丢日期，它不丢日期的时候等于没压。**
> 而两种结果**长得一模一样**：都是一份完整、通顺、自洽的简报。

#### 一、压缩率根本不由档位决定，由「这个项目里有多少重复」决定

| 项目 | 里面有什么 | 同一组设置（保留结论和数字 · low）压完剩 |
|---|---|---|
| **Flux** | 同一份 README 在库里出现了**四遍**（两个块 + 两处附件提取） | **62%**（60–100） |
| **宣发** | 5 块，跨块复述较多 | **79%**（72–92） |
| **申请规划** | 22 块，每块是一次**不同的**决策记录，几乎没有重复 | **95%**（64–194） |

**同一组设置，换个项目差 33 个百分点。同一个项目同一组设置，十次之间差 130 个百分点。**
而三个档位在申请规划上的中位数是 **95% / 95% / 76%** —— ⛔ **统计上分不开**。

⭐ 这一条推翻的不是某个数字，是**「档位」这个设计本身的前提**：
档位假设「压多狠」是用户能选的，而实测说它是**输入的性质**。
一个用户选不动的旋钮，做成旋钮就是在骗他。

#### 二、⛔⛔ 它一旦真的开始压，就开始丢日期和数字 —— 而这一档就叫「保留结论和数字」

**45 次全部按新的核对跑了一遍，分成两堆看：**

| 这一堆 | n | 其中**丢了数字/日期**的 | 丢掉的个数（中位） |
|---|---|---|---|
| **真的压动了**（压完剩 ≤85%） | 21 | ⛔ **18 次（86%）** | **3 个** |
| **几乎没压**（86–105%） | 23 | 5 次（22%） | **0 个** |
| 比原文还长（194% 那次） | 1 | 0 | 0 |

**丢掉的是什么**（每一个都查过上下文，不是噪声）：

| 压完剩 | 丢掉的不同数字/日期 |
|---|---|
| **64%**（申请规划压得最狠那次） | `2026-11-25`（CMU SCS 建议的 GRE **最晚重考日**）、`12-15`（USC 奖学金截止）、`11-18`/`12-09`（CMU SCS 节点）、`320`（那句「GRE 目标**不再只是** 320+」里的旧目标） |
| **68–81%**（「压到最短」十次） | `2026-12-15`/`2027-01-15`（USC 两个截止）、`76.0`（第一学年成绩）、`11-18`/`12-09`、`23:50` |
| **60%**（Flux） | `5173`/`8000`（demo 的端口）、`2027-01-26` |
| 72–81%（宣发） | `3:4`/`16:9`（宣发尺寸）、`26,163 / 50,000`（他自己引用过的那次测量） |

⚠️ **「压到最短」这一档最坏**：十次里**十次**都丢了数字，而它并不比上一档更短（76–78% vs 76%）。
**花更多的钱，压一样多，丢更多。**

提示词第 5 条的原话是「**所有结论、日期、数字、金额、人名一字不改地保留**」。

⚠️⚠️ **而且没有一次承认。** 十次「它说删了」里，没有一条提过自己删掉了一个日期 ——
这正是当初那条「让被审查的一方报告自己的成绩单没有意义」，第三次被同一件事验证。

⭐ **还丢了一样更要命的东西**：Spool 自己打的那行
`[... 8945 more chars not shown ...]`。那是 pack 的**诚实性标记** ——
「这里被截断过，你知道就行」。压缩稿把它删了，于是**下一个 AI 会以为自己拿到的是全文**。

#### 三、结构性的连线比正文掉得更早

**45 次里 19 次**掉了 `↩ cites:` / `↩ replaces` 行 —— 而**真的压动了的那 21 次里占 12 次**。
第 4 次 14 条只剩 2 条，第 7 次一条不剩。
这些是「这一条引的是哪一条、替代了哪一条」——**pack 的价值有一半在这些连线上**，
而它们又短又长得像装饰。

#### 三点五、还有一次它**改写了 12 条批注**（第 27 次，「压到最短」）

核对同时报「少了 12 条批注」和「写了 11 条你没写过的批注」——同一批行，被重写了。
⚠️ 典型改法：「现有成绩需按 **Fall 2027** 开学日复核」→「需按开学日复核」，**日期没了**。
批注是 💭 那一带，pack 里权威最高的一带。

#### 四、罕见但致命：45 次里一次，它把整份 pack 原样输出了两遍（剩 **194%**）

这一种**看得出来**（块数 22 → 44），所以它不是最危险的。**最危险的是第二条。**

#### 五、公道话：它压得对的时候，压得是真好

第 6 次那份 64% 的稿子，我一块一块读下来，**是好文字**：
四段变一段、重复的三处并成一处、语气统一、事实一个没编。
Flux 那几次把出现四遍的 README 合成一份，**每一个事实都至少留了一次**。
⛔ 所以「模型不行」这句话是错的，别这么记。

#### 六、我作为使用者，拿到这三种稿子会怎么样

| 拿到哪一种 | 我会怎么样 |
|---|---|
| **95% 那份**（45 次里有 23 次是这种） | 和原文没有区别。用户花了 ¥0.12、等了 2.6 分钟，换来一份一样长的东西 |
| **194% 那份** | 一眼看穿，重跑 |
| **64% 那份**（压动了的 21 次里，18 次带着这个毛病） | ⛔ **我会用得很顺，而且在不知情的情况下漏掉三个截止日期。** 我不会发现——它完整、通顺、自洽 |

> **最坏的一种失败，是它不像坏掉。**

#### 七、所以：⛔ 不解锁 `supersedes` 写入

⚠️ 理由**不是**「质量差一点」。§6.4.1 那条保护（原块还在、一键可取）
**假设用户知道要去取**。而第二条说的正是：**用户不会知道。**
一份看起来完整、其实少了三个截止日期的上下文进了默认读取路径之后，
没有人会再去核对它——**包括我。**

#### 八、⭐ 怎么才能解锁 —— 三条，按性价比排

> ⚠️ **2026-08-21：这张表已被 §9.10 十 重排**（第三轮实测之后）。
> 三条本身都还成立，但**顺序变了**，而且中间插进了一条新的（作废检测）。
> ⛔ **照着做请看 §9.10 十，不要照这一张。**

| # | 做什么 | 为什么这条最值 |
|---|---|---|
| **1** | **把「数字一个不少」从提示词变成闸门。** 检查已经做好了（`missingNumbers`）。让它变成**硬条件**：丢了数字的压缩稿，**即使解锁之后也不许存进库**，只能重跑 | ⭐ **这条不需要模型配合**，是纯机械的。它把第二条那个「看不见的失败」变成一个看得见的拒绝 |
| **2** | **压之前先本地算一遍「这个项目有多少重复」**，算出来接近 0 就**别让他花这笔钱**。`find_similar_blocks` 已经在库里，本地、免费 | 直接解掉第一条：把用户选不动的旋钮，换成一句他能用的判断 |

### 9.10 🆕 第三轮实测：**作废检测**，25 次跑完了（2026-08-21，真实 ¥1.78）

> **Ocean 2026-08-21：「压缩程度是由发送的决定的……库里大部分文本是 MCP 写入的或者是 AI 回答，
> 语义上本身就不好压缩，真的压缩应该需要理解上下文意思之后把一些已经推翻了的结论、放弃的数据〔去掉〕。
> 我在想是否可以变为 deepseek 首先使强思考用好的模型去理解上下文，给出项目内容前后矛盾、
> 想法偏移的地方，提问用户是否需要压缩，然后再使用 low、限制数字等等条件进行压缩。」**
>
> **全部原始数据在 `docs/Deepseek-API-compress-test.md` §5。** ⛔ 一次失败都没有。
> ⚠️ 这一轮在**高峰**跑（第二轮是闲时），所以并排比用的是 token 和闲时折算价，理由见 §5.1。

#### 一句话

> **你的诊断是对的，而且这条路比压缩便宜、比压缩安全、比压缩多省一倍的字。
> 但你方案里的「强思考」那一半，实测是反的 —— `high` 是这一轮最差的一格。**

#### 一、⭐ 先把两件事分开：这不是压缩的加强版，是**另一个功能**

| | 压缩（已实测两轮） | 作废检测（这一轮） |
|---|---|---|
| 输出 | 一份**重写过的文本** | 一组**指针**：第 X 块被第 Y 块取代 + 理由 + 两处原文摘引 |
| 改动原文 | 全篇 | **一个字都不改** |
| 失败长什么样 | 完整、通顺、自洽，但少三个截止日期 —— **看不出来** | 指错一条，用户一眼看见，点「不」 |
| 现在能不能解锁写入 | ⛔ 不能（§9.9 七） | ⭐ **能** —— 理由见第五条 |

#### 二、⛔ 你那条「先用强思考理解上下文」，被测反了

| 思考 | 出过提议 | 严格过闸 | 找全两条 | 秒 | ¥闲时 |
|---|---|---|---|---|---|
| `low` | 2/5 | 3/3 | 1 次 | 37 | 0.0222 |
| ⭐ **`medium`** | **4/5** | **5/5** | 1 次 | 88 | **0.0478** |
| `high` | 3/5 | ⚠️ 2/3 | **0 次** | 100 | 0.0617 |

`high` 比 `medium` **贵 29%、慢 14%、提议更少、过闸率更低、一次都没找全**；
探针那次它烧了 **15,377 个思考 token** 得出一个 `[]`。
**要用的是 `medium`，不是「越强越好」。**

⭐ 而这和压缩那边**正好相反**（§9.8 第 2 条：压缩上 `medium` 是纯亏）。
**结论：「思考力度」不能跨功能照搬，每个功能自己测。**

#### 三、⛔ 假阳性 = 0，而且两个「什么都没找到」是**对的**

25 次一共 11 条提议，**全部**落在申请规划上、**全部**指向 `#21`。
宣发和 Flux 十次全部 `[]` —— 这两个 `[]` 我逐块核过：

- **宣发**：确实有过时的东西（#2 的「六拍」分镜被 #4 的「八拍」取代），
  但那是**块内几句**，同一块的字体/色板/文案红线仍然成立 —— 提示词写着「只提议整条作废」，
  **不提议才是守规矩**。
- **Flux**：它的冗余是同一份 README 出现四遍，**字面重复**，那是压缩的活（实测 62%）。

⭐ **这一条把分工测出来了**：Flux 走压缩，申请规划走作废检测，宣发两个都不是干净的赢。
**这正是 §9.9 第一条那个「压缩率是输入的性质」的正面用法 —— 它决定该派哪个功能上场。**

#### 四、⚠️ 弱点是**召回**，不是精度

正确答案两条（`#2←#21`、`#3←#21`），十五次里**只有 2 次两条都找到**；
11 条提议里 8 条指 `#2`，只有 2 条指 `#3`。
**它几乎不指错，但经常只指一半。**

⚠️ **「多跑两次」不够** —— 拿归档免费算过（⛔ 没花钱）：

| 思考 | 单次找全 | 任取 2 次求并 | 任取 3 次求并 | 五次全并 |
|---|---|---|---|---|
| `low` | 1/5 | 4/10 | 6/10 | ✅ 找全（多带一条边界提议） |
| `medium` | 1/5 | 4/10 | 6/10 | ⭐ ✅ **正好是真值两条，并集里也没有假阳性** |
| `high` | 0/5 | 0/10 | 0/10 | ⛔ **全并仍然不全** |

**跑三次也只有 6/10 的把握找全**，所以召回要从**提示词**上改（§9.11 阶段 3），不能靠重复跑。⭐ 顺带又一条 `high` 的罪证：并了五次仍然不全。

#### 五、⭐⭐ 机械闸门当场抓到一次 —— 而且抓的是一个**结论正确**的提议

第 13 次（`high`）提议 `#2←#21`，结论对，但引文逐字对不上：
**全角 `；`/`，` 被打成半角 `;`/`,`** —— **它不是在复制，是在重打**。

这是 `compress.ts::normLoose` 记过的同一个毛病的**第三个变种**
（第二轮第 6 次把 `“…”` 打成 `"…"`，害核对误报「编造了 4 条批注」）。

⚠️ **修法照抄那条已有的纪律，两面都要**：比对时折叠全角/半角标点（折叠后 11/11 全过闸），
但「引文是重打的」**单独报一个数**；⛔ **只折叠标点，绝不折叠数字和日期。**

#### 六、成本：省的是正文，⛔ **思考一分钱没省**

同一份 pack、同样的输入 token：

| | 压缩（第二轮 `balanced`·`low`） | 作废检测（第三轮 `medium`） |
|---|---|---|
| 输出 token（中位） | **26,924** | **10,446** |
| 　其中正文 | 16,986 | **33** |
| 　其中思考 | 9,938 | **10,413** |
| 耗时（中位） | 158 秒 | **88 秒** |
| ¥闲时（中位） | 0.1219 | **0.0478** |

⭐ **思考量几乎一模一样 —— 它跟着输入走，不跟着输出走。**
省下的全部是「不用把整份简报重写一遍」那 16,986 个正文 token。**总账是 39%，耗时是 56%。**

#### 七、⭐ 收益：**它省的字比压缩多一倍**

| | 省下多少 | 代价 | 丢东西吗 |

| **退掉 `#2` + `#3`** | ~~**9.0%**（2,390 / 26,615 字符）~~ ⛔ **改为 8.4%（净）** | ¥0.0478 / 88 秒（一次检测） | ⭐ **零** —— 原块原样留在库里 |

> 「有 2 块已被标为不再有效」。**对外报 8.4%。** 详见 `Deepseek-API-compress-test.md` §6.7。

**一次作废检测省下的字，是压缩中位表现的一倍多，花的钱是它的四成。**

#### 八、⚠️ 一条必须先修的机制问题（查库查出来的，不是猜的）

`ref_kind='supersedes'` 和 `stale_at` 是**两个字段，故意解耦**：

#### 九、⛔ 三条闸门，缺一条不能开

1. **AI 只提议，永不自动执行。** `mcp.rs:4174` 那条红线已经在了 ——

2. **每条提议必须逐字摘引，Spool 拿回去精确比对，对不上的整条丢掉、不给用户看。**

#### 三、AdaptiveMem 拆开看，正好和表头是同一个面

AdaptiveMem 不改数据库、不改检索器，只在推理时加四条提示。
**这和 Spool 表头是同一个东西**，所以可以逐格对：

| 论文的陷阱类 | 定义（原文） | Spool 表头现在有什么 | 判定 |
|---|---|---|---|
| **Task Boundary** | 任务变了，模型继续套用上一个任务的规则和假设 | **零** —— 四带全按「来源可信度」排权重，没有一个字讲**适用范围** | ⛔ **真缺口** |
| **Cognitive Bias** | 把过去成功的策略过度泛化到需要别的策略的新题 | **零** | ⛔ **真缺口** |
| **Trauma** | 过去的负面反馈，让模型回避一个对当前题目正确的方案 | ⚠️ **有，但方向可能是反的** | ⚠️ **要补一句** |
| **Safety** | 历史里只在沙盒/反事实下成立的前提，被带进真实问题 | 半格：`only at equal recency` 挡的是**过期**，挡不住**从来就不该当真** | ⚠️ **半缺口** |

⚠️⚠️ **Trauma 那一格是这一轮最想让你看的一条。**

§1.4 第 6 条修法把 `↩ replaces` 的处理从「It is history: do not use it」改成了：

> You may still say the user considered it and ruled it out —
> **that a road was already closed is worth knowing.**

那条修法的理由没错（此路不通本身有价值，白丢可惜）。
但**论文的 Trauma 类测的正好是这件事的副作用**：150 例，全部是
「历史里有对某方案的否定 → 模型在这个方案其实正确的新题上回避了它」。

⛔ **我不建议撤回第 6 条修法** —— 撤回等于回到「此路不通白丢」。
⭐ **该补的是一句限定**：*排除过是一个历史事实，不是当前禁令；当前任务明确需要那条路时，照走。*
这一句既保住第 6 条的收益，又正好是 AdaptiveMem 的第 3 条。

**Safety 那半格说清楚**：📖 Reference 的判定依据是**来源的形状**（邮件客户端、机构域名、
PDF 附件），**不是内容的真假**。一份 PDF 里写着一条只在某个沙盒 / 某个旧辖区成立的规则，
进来就是 📖 Reference，拿到「ground truth, do not contradict」。
`equal recency` 挡的是「后来变了」，挡不住「它从一开始就只在某个范围内成立」。
⚠️ 这和那份分析建议的「提示注入测试」是**同一个洞的两个方向**，当一件事看。

#### 五、⭐ 「作废检测五状态」——§9.12 昨天已经独立走到了，只差一个状态

#### 六、「先识别当前任务」那一段：整份文件里最扎实的部分

Ocean 在第二轮问出了那个关键质疑（任务在客户端产生，Spool 收不到），
分析**接受了这个架构约束**并给出了正确结论：**Spool 不识别任务，只声明边界。**
这一段可取。逐级复核：

| 等级 | 内容 | 判定 |
|---|---|---|
| **L1** | pack 头加 BEGIN/END 边界 + 尾部一句短提醒 | ⭐ **可做**。纯字符串、零行为改动、确定性不变、不需要 AI 不需要联网 —— 和 §1.4 那七条同一类，有 byte-identical + golden 兜底 |
| **L2** | MCP `INSTRUCTION_BODY` + `get_pack` 描述里各重复一句 | ⭐ **可做**，且 ⚠️ **必须和 L1 一起做** —— §2.5 那条老规矩：只改描述不改路由文本，第三方客户端读不到 |
| **L3** | `get_pack` 加可选 `current_task` 参数 | ⛔ **建议不做**，理由见下 |
| **L4** | Spool 控制完整推理调用 | ⛔ 它自己也否了，同意 |

⛔ **L3 为什么我要否**（它给的理由是「保持可选就没坏处」，我不同意）：

1. ⛔ **`current_task` 传进来就是用户在别处说的原话**，会被原样打进 pack。
   而 pack 是**定义上要被粘给第三方 AI 的东西**，也会进压缩 sidecar 的 API payload。
   **这等于开了一条「客户端对话原文 → 我们的输出 / 外发」的通路** ——
   而形态 C 的默认关闭和 §7 的隐私叙事就是绕着这条通路建的。
2. ⚠️ 它引入了一个**输出字节依赖于调用者传了什么**的维度。
   现在「同一项目同一时刻 → 同样字节」，golden fixture 和 byte-identical 测试都建在这上面。
3. ⭐ **收益可疑**：MCP 场景下客户端模型本来就还记得触发调用的那条用户消息
   （分析自己在第五节承认了）。真正需要 L3 的只有「预加载 pack、之后才提问」一种情形，
   **而那种情形正好是 L1 尾部提醒解决的。**

⚠️ 它说对了、值得单独记一条：**L1/L2 是 prompt 级的，不是闸门。**
对外**不能**说「Spool 阻止任务越界」，只能说
「Spool 的 pack 明确区分历史与当前任务，并要求接收模型在使用前检查适用范围」。

| 否决项 | 理由 |
|---|---|
| 用颜色映射项目优先级 | 优先级是要人维护的主观数字，和已经回滚掉的进度条同类；且「按来源给块上色」早因违反 quiet 被拒 |
| 项目「预估完成时间」 | 估计值会腐烂（项目永远延期），**假日期比没日期糟**。不腐烂的是外部给定的真实日期，而 `threads.deadline` 已经有了 |
| 用目标列表推导项目完成度 | 由完成度推导状态 = 要维护的派生状态 = 进度条被回滚的原因。`status` 由人一次性设置就够 |
| ~~文件夹作为第三层容器~~ | **此条作废**：工作区早就能无限嵌套，文件夹一直都有。剩下的是堆积问题，见 §9 `C5` |
| 右侧栏做工作区级事件嵌套 | 和日程板重复；右栏窄装不下深树；且会让日程板失去唯一的存在理由 |
| 「关掉软件才算中断」 | 把**漏报**翻成**谎报**。在伪造的信号上执行一个有论文依据的健康干预，比不干预更糟 |
| 链接直接转视频 | 联网抓取撞零出网；且是 Follow-up 注入面的放大版——一个 URL 决定进入项目的内容 |
| 双击 ⌥ 录屏 | 撞「不做全自动捕获」；且是首次运行信任冲突的加强版 |

### 10.7 这一轮带出来的一条方向修正 —— provenance graph 的诊断变了

原来的理由是「它已经在数据里，却几乎没有被呈现」，所以排第一优先。
**这一轮给出了更准的诊断：不是概念没用，是「建立引用」这个动作不存在或者太贵——你自己在真实使用里
都没有伸手去用 `supersedes`。**

所以顺序要调：**先做「怎么建立引用」**（时间线上把一个块拖到另一个块上，
或者写块的时候提一句「这是在推翻上面哪一条吗」），**再做展示。展示一张空图没有意义。**

> 📌 **案例账本值得记一条**：你自己 dogfood 产出的 pack 里**零 pin、零 `↩` 引用**，
> 而其中一块明确推翻了另一块。这是 provenance graph「已在数据里、几乎没被呈现」的**直接证据**。
